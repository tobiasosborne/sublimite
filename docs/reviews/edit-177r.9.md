**BLOCKER**

- **Ctrl+X can delete text without publishing it to the clipboard.** [src/editor/clip_storage.h:33](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/editor/clip_storage.h:33). The adapter treats admission to the clipboard worker’s queue as success. `editor_clip_action` then deletes the selection at `clip.c:405`. If another application keeps the clipboard locked, native publication later fails; the resulting ownership/failure event is ignored at `clip.c:497`. Tobias sees the selection disappear, but paste retrieves the previous clipboard contents. Saving commits that deletion. Closing can also abandon a queued publication. **Fix:** retain the payload and defer cut deletion until an identified native publication succeeds; report failure and preserve the selection. Successful writes currently need a completion notification too.

**MAJOR**

- **A real minimize can terminate the editor.** [src/win32/win32_plat.c:456](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/win32/win32_plat.c:456). `WM_SIZE` always forwards the current client rectangle, including an empty minimized rectangle. The editor eventually calls native resize, which rejects it at `d3d11_win.c:427`. If a drawn frame is active, `windows_surface` instead destroys the backend and immediately reinitializes it; initialization rejects that same empty rectangle at `d3d11_win.c:389`. Both errors escape the loop: the taskbar window disappears instead of remaining minimized. `editor_win_test.c:117` merely posts `WM_SIZE`; it leaves the actual HWND’s client rectangle unchanged. **Fix:** retain the last usable dimensions, defer native resize/recreation while minimized or empty, and rebuild after restoration. Test actual minimization of the owned HWND.

- **Presentation can remain parked after uncovering or returning on-screen.** [src/editor/editor.c:35](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/editor/editor.c:35). An unobservable frame causes rebuilding followed by `d3d11_set_suspended(true)`. Recovery then depends on either a platform suspension transition or `PLAT_EV_EXPOSE`. `WM_PAINT` supplies that expose and requests full layout, so that route retries with full damage. Focus, activation and a keystroke do not clear the parked state; moving the window has no explicit recovery handler.

  Ordinary covering does **not necessarily enter the `DXGI_STATUS_OCCLUDED` branch**: this is a flip-sequential chain, and Microsoft documents that flip-model chains do not return that status. The practical risk is the missing-completion recovery path. Once parked there, DWM can uncover retained contents without requesting repaint, leaving Tobias with stale or black content while edits continue. A delivered display-on notification retries; an individual monitor’s wake cannot be assumed to provide it. [DXGI status documentation](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-status), [DWM repaint behavior](https://learn.microsoft.com/en-us/windows/win32/dwm/bestpractices-ovw).

  **Fix:** provide a guaranteed recovery trigger for unexplained unavailability—native notification where applicable, otherwise a bounded parked-state probe—and retry on relevant activation/position/input events with full damage. “No retry timer while parked” currently lacks that liveness guarantee.

- **Renderer recovery/shutdown can deadlock on the shared work pool.** [src/editor/backend.c:109](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/editor/backend.c:109). With many background file/index jobs occupying the bulk-eligible slots, shutdown admission can fail. This loop retries forever while pumping only native events; it never drains ordinary work completions. Finished jobs with pending messages remain ineligible for reuse (`work.c:305`). Initialization similarly receives only its own result. A minimize or presentation recovery during heavy background work can therefore leave an editor that pumps window messages but never resumes editing or finishes closing. **Fix:** reserve lifecycle capacity or use a dedicated lifecycle pool, and maintain safe completion draining throughout these waits. Exercise recovery with the ordinary pool saturated.

- **The blocking wait path loses auto-reset readiness.** [src/editor/wait_win.c:60](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/editor/wait_win.c:60). `WaitForMultipleObjects` consumes the event, but its returned index is discarded before `WaitForSingleObject` probes it again. There is another loss at `editor.c:433`: the fallback pump discards the returned tag. This branch is reachable when the input queue fills while dispatch is blocked by a save or journal fence. Losing the D3D latency credit can stall presentation until recovery, potentially feeding the permanent parking above. The new auto-reset test uses the platform callback’s preserved credit and bypasses this case. **Fix:** preserve the blocking wait result, then dispatch the fallback pump’s returned readiness to its owner.

- **A profile override can silently hand off to another profile and skip recovery.** [src/main.c:117](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/main.c:117). Windows IPC identity includes the user and optional IPC namespace, but excludes `SUBLIMITE_PROFILE`. With the normal instance running, launching against another profile forwards there and returns before resolving the requested journal directory. Tobias will not see that profile’s recovered tabs; even an invalid override bypasses the promised validation. The executable tests always use `--new-instance`, hiding this. **Fix:** resolve and validate the profile before IPC selection and include its canonical identity in both server and client namespaces.

**MINOR**

- **One deliberate-discard route leaves the first-paint guard armed.** [src/editor/editor.c:36](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/editor/editor.c:36). If suspension becomes known after submission but before native drawing, `windows_surface` successfully discards the CPU snapshot without clearing its PAINT record. The clearing at `editor.c:580` covers only snapshots submitted after `win_unavailable` was already set. A crash before another snapshot can make recovery close a healthy recovered tab as a suspected paint crash. **Fix:** clear the guard on every intentional CPU discard and retain a retry obligation if clearing is refused. Keep `painted` false: the next actual submission already rearms the guard, so that successful-clear route preserves protection.

- **Console attachment repairs output streams but leaves interactive stdin unusable.** [src/main.c:329](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/main.c:329). When a GUI launch starts with disconnected CRT streams, attachment followed by these `freopen` calls repairs stdout/stderr only. `sublimite.exe -` subsequently passes the disconnected stdin descriptor to `ipc_args_read_stdin` and fails. Inherited input pipes take a different path and can work. **Fix:** reconnect missing stdin to `CONIN$` when attached, preserving valid inherited pipes/files; test console input and redirected input separately.

- **The GUI executable does not provide synchronous PowerShell command behavior.** [mk/win.mk:64](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/mk/win.mk:64), [src/main.c:328](/home/tobiasosborne/Projects/sublimite/.wt/edit-177r.9-s28/src/main.c:328). Plain interactive PowerShell invocation can return its prompt immediately, including with `--wait`; attaching afterward does not make the shell wait. Help/errors can appear after the prompt, and `$LASTEXITCODE` need not describe that invocation. A process-waiting caller such as Git can still obtain the exit status and use the launcher handshake. [PowerShell’s GUI-process behavior](https://devblogs.microsoft.com/powershell/managing-processes-in-powershell/).

  **Fix:** supply a console launcher for shell use while retaining the GUI executable for Explorer. `editor_exe_test.c:148` checks exit status but never captures/asserts help or error output; deleting those output calls would leave its “streams” PASS intact. Add captured-output assertions and actual shell coverage. I found no application `AllocConsole` path that would itself create a flashing console.
