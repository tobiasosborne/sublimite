## 1. BLOCKER — Partial-group replay is insufficient as final editor behavior

**Locations:** [src/undo/undo.c:185](/home/tobias/Projects/editor/src/undo/undo.c:185), [src/undo/undo.h:21](/home/tobias/Projects/editor/src/undo/undo.h:21), [docs/decisions/P1.5.md:21](/home/tobias/Projects/editor/docs/decisions/P1.5.md:21).

A later operation’s NOMEM returns after earlier operations have changed the document. Editing and opposite replay then become BUSY. Persistent failure leaves the user choosing between retrying indefinitely and clearing all history while accepting an incomplete undo.

This matches the revised undo header, but the decision document explicitly acknowledges that strict group atomicity remains unmet. It is unacceptable as the editor’s final undo behavior: an explicit replace-all group can stop between replacements, and the original document cannot reliably be recovered. Publishing or saving that intermediate state would preserve an incomplete command.

**Reproducer:** `replay_failures()` already exercises this. Its `mode=1` group contains a large insertion followed by `"Z"`. Failure during undo can occur after `"Z"` has been removed but before the large insertion is undone. The test explicitly accepts `groups == 0`, successful records, and `partial == -1`.

The frozen piece API limitation is real. Attempting reverse mutations as rollback cannot guarantee recovery because those mutations can also fail.

**Minimal fix:** Extend piece with a temporary checkpoint/transaction whose abort restores the prior tree **without allocation**. Hold one checkpoint during a replay group, stage undo bookkeeping, and commit both only when the group completes. On failure, restore content, cursor, and history. Earlier completed groups in a batch may remain completed and be reported in `change`.

A transient checkpoint during replay is sufficient; snapshots need not become the historical undo representation.

## 2. MAJOR — Reference expansion causes deterministic, unrecoverable replay NOMEM

**Locations:** [src/undo/undo.c:85](/home/tobias/Projects/editor/src/undo/undo.c:85), [src/undo/undo.c:151](/home/tobias/Projects/editor/src/undo/undo.c:151), [src/undo/undo.c:174](/home/tobias/Projects/editor/src/undo/undo.c:174).

Every unknown insertion replay reserves eight records, although the existing record supplies the first resulting span. Expansion can consume the reserve inside a group; trimming is deferred, so every retry fails permanently.

This happens with a healthy piece allocator.

**Reproducer, verified under ASan/UBSan:**

```text
Initialize original text "0123456789", max_records = 12.
Begin explicit group:
    insert(10, "Z")
    insert(5, "abcdefghij")
End group.
Insert "Y" at offset 0 nine times.
Delete [0,17).
Undo 10 groups, restoring the explicit group's result.
Undo 1 group.
```

Observed results:

```text
before: records=12, capacity=20
attempt 0: NOMEM, records=13, change.records=2,
           groups=0, partial=-1, free_slots=7
attempt 1: NOMEM, change.records=0, free_slots=7
attempt 2: NOMEM, change.records=0, free_slots=7
```

The document remains `"0123456789Z"`; editing is locked.

The same excessive reservation rejects a third one-span insertion in an explicit group with `max_records=1`, despite seven physical slots remaining.

**Fix:** Reserve one slot for an insertion and at most seven additional slots when replacing an existing record. That corrects the immediate over-reservation, but larger expansions still require a group-wide capacity guarantee or atomic rollback.

A cleaner API extension is for `piece_insert` to return its stable inserted add span. Store `add_off` and mark the record KNOWN immediately. Piece’s lifetime guarantee then removes the need for first-undo capture and expansion.

## 3. MAJOR — G10f accounting hides retained pool memory

**Locations:** [src/undo/undo.c:34](/home/tobias/Projects/editor/src/undo/undo.c:34), [src/undo/undo.c:65](/home/tobias/Projects/editor/src/undo/undo.c:65), [src/undo/undo.c:197](/home/tobias/Projects/editor/src/undo/undo.c:197), [bench/undo_bench.c:64](/home/tobias/Projects/editor/bench/undo_bench.c:64).

Returning records to the intrusive free list reduces `live_bytes` but releases no committed anonymous pages. Clearing history or reducing the cap leaves the pool’s full high-water footprint resident.

The benchmark’s `live_bytes == 64 * records` assertion checks pool bookkeeping and stride. It does not establish G10f’s owned-memory bound.

**Reproducer:** Initialize capacity 100,000, type 100,000 contiguous single bytes, clear history, then set the cap to one.

Measured **(M)[AC]**:

```text
records=0
live_bytes=0
reserved_bytes=6,402,048
resident pool bytes=6,402,048
document length=100,000
pieces=2
```

Using retained undo records, the corresponding G10f allowance is only **194,824 B (G)**, even generously including piece.h’s extra 4 KiB overhead. The undo pool alone exceeds it substantially.

Charging memory against configured capacity instead would require an explicit capacity-based budget; the current benchmark does not enforce one.

**Fix:** Count committed pool memory and piece allocations in the gate. Use page/chunk-aware record storage that can decommit wholly unused pages while preserving initialization-time reservation. A complete clear can reset pool metadata and decommit its pages; eviction and cap reduction also need a reclamation policy.

## 4. MAJOR — A keystroke performs unbounded history reclamation

**Locations:** [src/undo/undo.c:28](/home/tobias/Projects/editor/src/undo/undo.c:28), [src/undo/undo.c:46](/home/tobias/Projects/editor/src/undo/undo.c:46), [src/undo/undo.c:96](/home/tobias/Projects/editor/src/undo/undo.c:96).

Two typing-path actions synchronously walk an arbitrary number of records:

- The first edit after undoing a large history frees the entire redo branch.
- The edit crossing the cap of a large automatic burst frees the entire burst.

Both run after the piece mutation succeeds. Their cost grows with history size, violating the ≤0.5 ms UI-slice requirement.

**Reproducer:** Fill 100,000 records, then either undo them all and type one character, or type the character that crosses a 100,000-record burst cap.

Undo-only mock measurements, **(M)[AC]**, Clang `-O2`, 11 samples:

| Typing action | p50 | p99 |
|---|---:|---:|
| Discard 100,000 redo records | 1.064 ms | 1.167 ms |
| Discard oversized 100,001-record burst | 0.627 ms | 0.719 ms |

These exclude piece and rendering costs. At one million records, both paths took approximately 12 ms p50.

**Fix:** Detach discarded history in constant time, then reclaim a bounded number of records between input checks. Provide a reusable record reserve and account for retired storage. A segmented or circular representation can also avoid per-record synchronous teardown.

## 5. MAJOR — Replay cannot yield within a large group

**Locations:** [src/undo/undo.c:166](/home/tobias/Projects/editor/src/undo/undo.c:166), [src/undo/undo.h:83](/home/tobias/Projects/editor/src/undo/undo.h:83).

The replay limit counts completed **groups**, not records or elapsed work. One burst or explicit group can contain the entire history. `undo_undo(u, 1, ...)` must process every record before returning, with no deadline, input callback, or normal in-progress result.

G9 permits a long total batch duration, but the foreground contract still requires input checks between ≤0.5 ms slices.

**Reproducer:** Type 100,000 adjacent bytes at qualifying timestamps, producing one burst, then call `undo_undo(..., 1, ...)`. Passing fewer groups cannot subdivide this operation. The existing `no_malloc()` test already exercises this structure with 10,001 records.

**Fix:** Add a record/work budget or deadline and a distinct in-progress result. Preserve the replay position and transaction between calls, defer cursor restoration until group completion, and let the editor check input between slices. Keep one final render for the requested batch.

## 6. MAJOR — The benchmark allows a real G9 miss to pass

**Locations:** [bench/undo_bench.c:53](/home/tobias/Projects/editor/bench/undo_bench.c:53), [bench/undo_bench.c:66](/home/tobias/Projects/editor/bench/undo_bench.c:66), [bench/undo_bench.c:75](/home/tobias/Projects/editor/bench/undo_bench.c:75), [docs/decisions/P1.5.md:41](/home/tobias/Projects/editor/docs/decisions/P1.5.md:41).

The real replay is reported with zero gates, and its report result is ignored. Process exit status depends solely on a mock’s invented 6.3 ms budget.

Fresh GCC results, **(M)[AC]**:

```text
real replay: p50=97.411 ms, p99=295.496 ms, pass=1
mock replay: p50=0.655 ms, p99=3.383 ms, pass=1
process exit=0
```

Real replay already exceeds A’s **63/84 ms (G)** limits before rendering. The decision document’s battery run likewise reports **334.827/620.264 ms (M)[bat]**.

Every row has a qualification:

| Row | Actual fixture and gate problem |
|---|---|
| `MEMORY` | Counts live span records at one point; excludes retained pool pages, piece memory, and eviction peaks. |
| `undo_10k_in_tree_TRACK` | Replays 10,000 isolated one-byte front inserts using the linked kernel; zero limits cannot reject a miss. |
| `undo_10k_bptree_INDICATIVE_M` | Also ungated; backend identity depends on external linking. |
| `undo_10k_bookkeeping_mock_G` | Trivial piece calls, without real content, allocation behavior, or rendering. The 10% budget is absent from the binding gates. |

There are only 31 whole-batch samples, whereas §4 requires at least 10,000 interaction samples. The inner 10,000 steps are not independent request-to-frame samples. There is no controlled bulk-worker fixture, frame correctness check, or paste row.

**Fix:** Enforce the real module replay against the applicable G9 limits as a necessary component check and propagate misses to exit status. Keep the mock as diagnostic data. Add the required integrated request-to-correct-frame measurement, sample count, worker-contention conditions, and applicable A/B fixtures; track provisional C separately.

## 8. MINOR — Failure coverage omits important replay contracts

**Locations:** [tests/undo_test.c:164](/home/tobias/Projects/editor/tests/undo_test.c:164), [tests/undo_test.c:191](/home/tobias/Projects/editor/tests/undo_test.c:191), [fuzz/undo_fuzz.c:25](/home/tobias/Projects/editor/fuzz/undo_fuzz.c:25).

Replay failure injection tests undo with selected one-shot allocation failures. Redo runs after failure injection is disabled. The fuzzer uses physical capacity 8,192; its bounded input cannot exhaust that pool.

Missing coverage includes:

- Redo allocation failures, especially inside mixed groups.
- Persistent allocation failure and repeated retries.
- Fragment expansion near physical capacity.
- A batch completing groups before failing inside another group.
- Exact dirty-range and cursor-state reporting across those failures.
- Owned-memory behavior after eviction and cap reduction.

These gaps explain why the passing suite and fuzz runs miss the deterministic deadlock and memory problem.

**Fix:** Add the finding 2 script as a regression. Exercise every allocation-failure position in both replay directions, with transient and persistent failures. Add a small-capacity fragmented fuzz mode and check bytes, history position, completed-group counts, cursor blobs, and dirty intervals after each result.
