# edit-cyn4 — W1.3 Windows fonts: deep review

Reviewed `git diff main...HEAD`, including implementation commit `ec06f9f` and coordinator decisions in `9a0a5e7`, against the font contracts, frozen `os.h`, migration decision §9, and worker report. Static review only: no builds, test binaries, Windows executables, or native repros were run. API-dependent conclusions below use Microsoft’s documentation; where a conclusion follows from the contracts rather than a native observation, that is stated.

No confirmed BLOCKER. The findings distinguish behavior defects from missing regression coverage; the latter are not assertions that the untested failure already leaks.

By inspection, the call-scoped ownership design is sound on the explicit acquisition/failure branches: analysis → face → file → loader unregistration → factory → DLL are retired before the stack loader disappears. Discovery releases mapped font/fallback; path extraction releases the file returned by `GetFiles`, both loader interface references, and the face; family lookup releases font/family/collection. `S_FALSE` from `CoInitializeEx` is correctly balanced, and `RPC_E_CHANGED_MODE` does not cause an unmatched `CoUninitialize`. COM pointers do not enter the copyable `font_t` or a mailbox. Production asynchronous raster/discovery calls remain on WORK_BULK; the bounded UI cache path still uses stb. I found no newly introduced C-heap allocation on the typing path. These are inspection results, not a substitute for finding 7’s failure tests.

The Linux migration also appears behavior-preserving for ordinary font files: the same monotonic clock is used; diagnostic thread identities do not imply thread ownership; file reads loop over positive short transfers and reject premature EOF; failed loads rewind the arena; symlinks are still followed; directories still produce the module’s existing NULL/INIT outcome, so §9.1 needs no distinct error remapping here. Sleep now completes its requested interval across EINTR, as required by `os.h`. The POSIX discovery process/pipe cancellation machinery and synchronous Fontconfig matching were relocated substantially unchanged. The known repeated `dlopen` retention in that relocated code predates this bead. The two Windows arena adaptations are consistent with the existing VM contract.

1. **MAJOR — Native and stb horizontal origins are assumed equivalent when the accepted TrueType format does not guarantee that.** Location: `src/font/dwrite_win.c:160`, `src/font/dwrite_win.c:165`, `src/font/dwrite_win.c:178`; reference path: `src/font/font.c:297`, `src/font/font.c:319`.

   The new renderer reads native glyph metrics but uses only `advanceWidth`, then rasterizes at native baseline origin zero. stb obtains `lsb` but ignores it when positioning the outline, using the raw `glyf` x coordinates and `xMin` for its bitmap origin. Valid TrueType fonts can have `xMin != hmtx.lsb`: the [OpenType horizontal metrics specification](https://learn.microsoft.com/en-gb/typography/opentype/spec/hmtx) explicitly permits this and defines the horizontal phantom origin as `xMin - lsb`. DirectWrite defines [its left bearing](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/ns-dwrite-dwrite_glyph_metrics) relative to the horizontal writing origin. Consequently, native placement and the existing stb placement need not differ by only an antialiasing edge pixel. This is a contract-based inference; the reported one-pixel MSYH difference does not establish its cause.

   A valid fixture with unchanged contours and a different `hmtx.lsb` exposes the missing normalization: advances can remain identical while the black box moves relative to the cell. Since ASCII/UI rendering and error fallback remain stb, the change can also switch placement within one face depending on the selected backend. **Fix:** add that fixture first and establish the intended common origin. To preserve stb placement for TrueType, translate the native analysis by `(raw_xMin - native_leftSideBearing) * scale` in X where needed, applying the translation before rasterization so its fractional phase is retained. Alternatively, deliberately change the common metric/placement contract and both backends together. Do not explain an arbitrary design-unit origin difference with the one-pixel filter tolerance.

2. **MAJOR — Discovery accepts a font without establishing that the monochrome pipeline can draw it, and does not try another candidate after rejection.** Location: `src/font/discovery_win.c:75`, `src/font/discovery_win.c:77`, `src/font/discovery_win.c:137`, `src/font/discovery_win.c:154`; consumers: `src/font/async.c:332`, `src/font/async.c:343`.

   `HasCharacter` and a local path establish character support and file location, not compatibility with `font_init_index` or usable monochrome outlines. The Windows resolver also removes `:color=false` without replacing its semantic check. A mapped face can use an outline format the common initializer rejects, or supply a visible emoji only through color/bitmap artwork while its mapped base outline is empty. In the first case the asynchronous resolver caches the failed face result and never searches for another supported installed face. In the second, an empty native bitmap is accepted as FONT_OK and can settle as an invisible glyph; retrying stb on the same empty outline would not repair it. The decision document’s narrower promise—accept color fonts **with monochrome outlines**—is not enforced. [HasCharacter’s contract](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nf-dwrite-idwritefont-hascharacter) contains no monochrome-renderability guarantee.

   **Fix:** validate candidates against the supported file/face and monochrome-outline requirements on the worker. Continue through a filtered collection or another covering candidate when the mapped font is unusable. Preserve legitimate blank characters; do not classify all empty textures as missing. Add fixtures for an unsupported outline format and a color-only mapped glyph, each followed by a usable monochrome face, and require the latter’s artwork. A font with both color tables and working monochrome outlines must remain accepted.

3. **MAJOR — Every per-scalar fallback request is falsely labeled Simplified Chinese.** Location: `src/font/discovery_win.c:44`, called from `src/font/discovery_win.c:109`.

   The explicit `zh-CN` locale is appropriate for the specified U+4E2D discovery probe, but `source_locale` returns it for every scalar, including ordinary production misses. [MapCharacters consumes the source’s locale](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_2/nf-dwrite_2-idwritefontfallback-mapcharacters). This biases Han fallback toward Simplified Chinese forms even for a Japanese, Korean, or Traditional Chinese user. The Linux general-scalar query has no equivalent forced `lang=zh-cn`; its explicit language is confined to the representative CJK probe.

   **Fix:** make locale part of the call-scoped text source. Use `zh-CN` for the representative probe and the editor/user locale, or a documented language-neutral policy, for general scalar discovery. Test a general Han lookup with differing locale inputs and inspect the locale delivered to the fallback service; do not require a particular installed font name.

4. **MAJOR — Loading the system renderer uses an unrestricted DLL search.** Location: `src/font/dwrite_win.c:20`.

   Production supplies the bare name `dwrite.dll` to `LoadLibraryW`. Once normal module/redirection/KnownDLL checks reach filesystem searching, the application directory is searched before System32; if the system DLL is absent, additional standard-search locations can also supply it. Thus a planted DLL beside a portable executable, or a later search-path candidate in the supported missing-DLL case, can run its `DllMain` before the export/interface checks ever choose stb. This is a loader-policy defect, not a claim that the current machine’s known-module state was inspected. Microsoft documents both [the ordinary search behavior](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryw) and [the System32-only option](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw).

   **Fix:** use `LoadLibraryExW(..., NULL, LOAD_LIBRARY_SEARCH_SYSTEM32)` for production system-library loading. Keep any deliberate test-library seam explicit and separate. Test the requested load flags and require clean stb fallback on load failure, without searching the document directory or PATH.

5. **MAJOR — The raster conformance tolerances neither prove placement nor have the claimed physical derivation.** Location: `tests/win/font_dwrite_test.c:50`, `tests/win/font_dwrite_test.c:62`, `tests/win/font_dwrite_test.c:67`; documented claim: `docs/decisions/edit-cyn4.md:77`.

   Comparing total coverage sums discards all spatial information. A mirrored, row-scrambled, or entirely different bitmap with the same sum passes. Requiring intermediate alpha only rules out binary coverage, and comparing routed output with the same direct implementation is a routing check, not an independent shape oracle. The later async check only requires ink and a runtime page, so a baseline or clipping error can pass the entire native suite.

   The stated geometry also does not support the bounds. Origin difference ≤1 and extent difference ≤2 allow the opposite edge to move by 3, not 1. Even a one-pixel outward ring around a filled `w × h` rectangle has area `(w+2)*(h+2)-w*h = 2*w+2*h+4`; the claimed perimeter omits its corner pixels. More fundamentally, filtering affects internal contours as well as the rectangle’s outer perimeter, and no cited DirectWrite contract bounds its difference from stb by this rectangle formula. Matching advances does not establish matching outlines or origins.

   **Fix:** compare left/right/top/bottom in a shared baseline coordinate system, then validate spatial artwork and final placed cell pixels with deterministic asymmetric outlines. Include negative controls that flip rows, shift ink while preserving the reported box, and corrupt only a bearing; the oracle must reject them. Derive any cross-rasterizer numerical tolerance from a stated raster/filter model or record it honestly as measured evidence rather than a universal (P) bound. Correct the decision/report derivation together with the tests.

6. **MINOR — The Windows suite does not exercise native ligature-only glyph IDs or the production true-em/combining placement cases.** Location: `tests/font_gsub_test.c:362`, `tests/win/font_dwrite_test.c:34`, `tests/win/font_dwrite_test.c:46`, `tests/win/font_dwrite_test.c:82`.

   Disabling DirectWrite for the existing stb golden hashes is reasonable, but the replacement native suite calls the glyph-ID entry point only with IDs obtained directly from two scalar cmap lookups. Its async requests are also two individual scalars. No native test reaches a GSUB-only ligature, zero-advance mark overlay, or `font_set_em_px`; all native comparisons use hhea-height sizing at one size. Therefore important new public paths and the claimed em-size conversion are only checked indirectly or with native rendering disabled. Deferring editor-linked suites does not prevent headless coverage here.

   **Fix:** keep the stb golden pass and add a native pass over the checked-in GSUB fixture, including an output glyph without a scalar cmap mapping and injected stb fallback for that same ID. Add true-em sizing at a non-baked size, a negative-bearing/descender glyph, and a base-plus-zero-advance-mark composition. Compare the resulting atlas tile to independently placed expected artwork and require the ligature to differ from the first-emoji projection.

7. **MINOR — Failure injection bypasses all acquired COM resources, so cleanup, apartment balance, and late stb fallback remain untested.** Location: `tests/win/font_dwrite_test.c:38`, `tests/win/font_dwrite_test.c:40`; short circuits: `src/font/dwrite_win.c:13`, `src/font/dwrite_win.c:128`; cleanup: `src/font/dwrite_win.c:180`.

   `unavailable=1` returns before opening DirectWrite, and the environment seam returns before COM initialization. The byte-identical scalar fallback assertion is useful, but proves neither rollback after pixel allocation nor Release/Unregister balance after any successful acquisition. It also does not test glyph-ID fallback, missing factory interface/export, or discovery/async completion while the service is unavailable. The exhaustion sweep explicitly disables DirectWrite (`tests/font_test.c:792`). Calling the native raster directly on the test’s main thread does not check that UI lookup/adoption remains free of opaque native calls, which the Windows malloc guard would not count.

   **Fix:** use test-only API/vtable shims to fail sequentially after loader registration, custom file creation, face creation, analysis creation, bounds retrieval, and pixel allocation/texture creation. Check Releases, unregistration, DLL/COM balance, unchanged arena entry marks, and exact public stb results for scalar and glyph-ID calls. For the stack loader/stream, external references should return to their initial owner reference before scope exit. Cover an uninitialized thread, an existing MTA, and an existing STA. Add service-unavailable discovery/async tests through live mailbox delivery, plus a thread-ID hook asserting that cold UI lookup/pump/adoption never calls the native backend. These are missing tests; I did not identify a double-release on the present explicit cleanup paths.

8. **MINOR — The claimed collection-face test has no oracle that distinguishes the selected face from face zero.** Location: `tests/win/font_dwrite_test.c:25`, `tests/win/font_dwrite_test.c:32`, `src/font/dwrite_win.c:154`.

   The test accepts whichever installed face discovery reports and compares native output with stb under the loose aggregate checks. It never requires a nonzero index or artwork/metrics unique to that face. Even on the reported MSYH index-1 run, closely related collection faces need not differ enough for this oracle to catch accidentally rendering index zero. The implementation correctly forwards `GetIndex` to `font_init_index` and `CreateFontFace` by inspection; the test does not pin that behavior.

   **Fix:** add a deterministic collection with distinguishable faces: a scalar/glyph or advance unique to each face. Render both indices through native and public entry points, require their respective expected results, and reject an out-of-range index. Retain the installed-font probe as integration coverage.

9. **MINOR — The new UTF-16 path extraction and family lookup have no Unicode or boundary tests.** Location: `src/font/dwrite_win.c:57`, `src/font/dwrite_win.c:61`, `src/font/discovery_win.c:141`, `src/font/discovery_win.c:148`; current probes: `tests/win/font_dwrite_test.c:24`.

   The recorded discovered paths are ASCII Windows system paths. The new suite does not call `font_selection_resolve` for an exact family, and the existing Windows font-selection/editor suites were deferred. Consequently, a UTF conversion, byte-capacity, or family lookup regression could ship with all module tests green. The strict UTF-8/UTF-16 conversion flags and failure clearing look correct by inspection. The capacity is nevertheless **512 UTF-8 bytes**, not 512 arbitrary Unicode characters: a UTF-16 path can fit `wide` yet fail conversion into the public path buffer. That graceful-refusal boundary also needs to be pinned.

   **Fix:** add a local-loader/custom-collection seam or equivalent deterministic fixture with an accented and supplementary-plane path, and load its emitted UTF-8 bytes through `font_load_file`. Exercise exact Unicode family lookup, absent family, the internal monochrome suffix, insufficient output capacity, malformed conversion input, and paths on both sides of the declared UTF-8 byte bound. Require an empty output path and zero index on refusal. Within the existing path contract, do not silently truncate or claim wider path support.

10. **MINOR — The short-read rollback regression no longer tests the production loader that was migrated.** Location: `src/font/fallback.c:85`, `src/font/fallback.c:89`, `tests/font_test.c:992`, `tests/font_test.c:998`.

    Linux still injects short reads into `font_load_stream`, but `font_load_file` no longer calls it. The Windows replacement fills too small an arena, so it fails allocation before any read. Both variants print that short-read rollback passed even though neither drives the new OS-read loop through premature EOF or an error after a partial transfer. The loop looks correct today, but the migration lost the connection between its production implementation and this regression.

    **Fix:** factor the common exact-read/rollback operation behind a worker-only read seam, or wrap `os_file_read` in the loader test translation unit. Exercise a positive short transfer followed by completion, premature EOF, and an error after some bytes, starting at a nonzero arena mark. Require exact length on success and entry-mark/zero-length restoration on failure on both platforms. Add a directory rejection case to pin the §9.1 migration outcome, and label allocation-exhaustion coverage separately.

Fix first, in order:

1. Resolve the origin contract and monochrome-candidate rejection/retry behavior (1–2), then correct general-scalar locale and DLL loading policy (3–4).
2. Replace the conformance oracle and its unsupported tolerance derivation (5); add native GSUB/true-em placement and late-failure/resource-balance coverage (6–7).
3. Add decisive TTC, Unicode path/family, and production read-loop regressions (8–10), then rerun the existing Linux and native Windows checks in the implementation follow-up.
