## Trigger (found by test, confirmed by trace)

Wrapped mode (default for `.md`/`.txt`/`.tex`/no extension): a Return typed
while the caret is on the bottom visual row. Both post-mutation top
placements compare the fresh caret row against the layout's **pre-edit**
rows and take the far-jump action (caret row to the top):

- `src/editor/input.c` `finish_edit`: `cursor.start > bottom->start`.
  Trace at the failing key: Return at byte 126920, fresh caret row start
  126921, old bottom row start 126876, the view's state before: top line
  2999 / byte 125958 -> after: caret row at top (line 3026 at key 924).
- `src/view/view.c` `finish_move`: `cursor >= bottom` with `bottom` = the
  old last row's `next` (fires when nothing follows the caret: the true end
  of the file).

Period = one screenful (27 text rows): jumps at keys 924, 1851, 2735 of the
fixture, i.e. every ~27 typed lines; minutes apart at a human typing rate.
At the end of a file the caret's line is the last line: "only the last line
is showing".

Ruled out with the unwrapped harness (journal live; 3000 keys with Returns,
paragraph breaks, Backspaces; 3000-line fixtures crossing LINEIDX_CHUNK; the
1 s journal tick between batches; retention and checkpoint running): the
top never moved past the typed newline. Journal checkpoint, retention
publish, index maintenance (sync refresh and worker rebuild), snapshot
adoption and the resident scroll resolver do not move the displayed top.

## Fix

One fresh row query (`layout_visual_row_fresh`) of the row above the caret's
row proves the one-row case (its start equals the old bottom row's start,
which an edit inside/after that row cannot move); then the top advances to
the old row 1 (as the non-edit one-row path does). Far jumps (paste, undo)
keep the existing direct follow. Helpers `wrapped_one_row_below` (input.c)
and `one_row_below` (view.c). Cost (P): one bounded wrapped row query per
Return at the bottom row; nothing on other keys; no allocation.

## What remains

- The new test's long-tail fixtures (300 lines of 420 B after 2000 short
  lines) intermittently hit `settle`'s existing 5 s bound (editor_test.c:61)
  under load1 25-32 on the shared box, in both wrap modes, release and
  sanitizer builds; never at load1 14-18. Not reproduced with the fix absent
  vs present (both pass/fail alike), so it is the fixture's settle under a
  starved worker pool (the per-key index rebuild runs on a worker) or a
  genuine lost wake-up that a re-run under low load would separate. The
  coordinator should re-run `build/san/tests/editor_test` on a quieter box;
  if the deadline still trips, the stuck `editor_stats.pending` term needs
  naming (one instrumented run: print the pending terms at the timeout).
- `view.c relative_wrap_place` (the edit-wv7 path for lazy files with an
  inexact count) has the same `!v->edited`-guarded one-row test and will
  re-anchor at the caret row for a bottom-row Return in a large lazy `.txt`;
  the same one-row proof applies. Not changed (not the trial's file class).

## Found outside the bead (not fixed)

- Unwrapped mode, Return on the bottom row: `editor_scroll_follow`'s fast
  path (scrollctl.c) reads `e->row_byte[]` before relayout; `layout_edit`
  leaves starts after a newline-changing edit stale (only `shift_rows` for
  same-newline edits), so stale row 26 "contains" the caret (`start 64671
  end 64779`, caret 64744 on the real row 27), the top is kept and the caret
  sits on the hidden 28th layout row until the next key, whose view follow
  (`view block followed 1501 vs v.state 1501`) corrects it. Observed on every
  bottom-row Return in the unwrapped harness, mid-file and at EOF. Caret
  briefly invisible; no jump. Fix shape: skip the fast path for rows whose
  span lies at/after a newline-changing edit until relayout, or transform
  `row_byte` in `layout_edit`.
- `input.c finish_edit`'s direct follow also applies to undo/redo that moves
  the caret below the viewport (caret row to the top); the one-row proof now
  covers only the one-row case there too.
