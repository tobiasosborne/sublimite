# P1.5 — inverse log over the frozen piece API

## Contract and layout

`src/undo/undo.h` was written first, followed by adversarial tests and an error-returning implementation stub. The final module owns an inverse-operation log for one UI-thread-owned `piece_tree`. The caller owns the `undo_log` control block. The tree must outlive it, and editing must go through the log. Six source/document files were added; piece, base, build rules and other modules were not changed.

Each inverse **span record** is exactly 64 B: three uint64 fields (document offset, length, add offset), two uint32 links with two flag bits each, and two opaque 16 B cursor/selection blobs. A multi-span delete becomes 1–8 records in one group. This is explicitly a bound per inverse span record, not a bound of 64 B per arbitrary fragmented user command. A full `piece_ref` alone is 144 B, so retaining one inline per edit cannot meet the record gate. The record layout is statically asserted, and pool live counters measure it.

Records come exclusively from `edit_pool`. Initialization reserves `max_records + 8` slots using base's lazy mmap pool. The extra 512 B is fixed reservation scratch, with page rounding and the caller-owned control block as fixed overhead. The live counter measures retained records; `reserved_bytes` reports the actual page-rounded mapping. No undo allocation, growth, or malloc occurs after initialization. Piece allocation still follows the tree's supplied hooks. The typing test uses a base arena as the piece allocator and the real malloc guard.

Deletion refs contain protected add bytes from `piece_delete`; the module never reads mappings or copies text. Insertions start with offset/length only. Their first undo captures the redo ref for free. If intervening piece flattening changed their add locations, the record expands to 1–8 span records after the atomic delete succeeds. Subsequent replay uses those stable refs. One-byte keys cost one record each, including inside bursts; grouping changes undo granularity, not record count.

## Groups, bounds and batch replay

Inserts join when the next offset equals the previous insertion's end. Backspaces join when the next range ends at the previous deletion's start. Forward deletes join at the same offset. Kind must match and timestamps must be nondecreasing with a gap <= 300,000,000 ns. Failed and zero-byte edits retain redo; a successful nonempty edit clears it. `undo_break_burst` handles user movement/focus/save. Explicit begin/end groups can mix operations, preserve caller-provided boundary states, reject nesting, and do not clear redo if empty.

The configurable cap counts span records across applied and redo history. Oldest complete groups are evicted, never fragments. Oversized automatic groups are discarded on crossing the cap; explicit groups defer trimming until end. If dropping an undone prerequisite would invalidate later redo, all redo is discarded. Pending explicit groups and partial replay protect their records and may exhaust the fixed pool; this returns NOMEM before the next mutation. Reference expansion can also exhaust the fixed pool inside a partial group; `undo_clear` accepts the partial document and frees its history. Retained piece add bytes are never reclaimed by log eviction.

`undo_undo` and `undo_redo` apply N groups and report one conservative merged dirty interval, successful record/group counts, and the last completed group's cursor blob. Length changes dirty the suffix through the larger pre/post EOF. No render or callbacks happen inside the module.

**Frozen-API limitation:** piece.h makes each mutation atomic on failure, but has no prepare/commit, tree replacement, transaction, or snapshot-restore API. An arbitrary multi-operation group cannot promise unchanged content after a later operation fails: rolling back would require another piece mutation that can also fail. Replay therefore reports a successful prefix on error, keeps an exact retry position, and rejects new edits/opposite replay/cap changes while a group is partial. The failing operation itself leaves content/history unchanged. Strict whole-group/batch NOMEM atomicity in the worker brief is not fulfilled; it requires a piece transaction/reservation extension or coordinator acceptance of this documented resumable contract. The frozen header was not changed.

Rejected alternatives: malloc-backed growing vectors (typing law), full snapshots as undo records (memory and stub complexity), storing full refs per edit (144 B before metadata), copying insert bytes for redo (add-buffer duplication), and best-effort rollback (cannot guarantee recovery with a persistently failing allocator).

The battery status read before the RED measurement was `Not charging` = [AC]. The shared harness does not recognize that status label; the final bench reads the raw label itself while retaining harness statistics/reporting.

GREEN covers timing/kind/adjacency boundaries, decreasing timestamps, backspace and forward-delete bursts, explicit and empty groups, redo invalidation, copied/mapped originals mixed with add bytes, mutation of deleted mapped bytes, snapshot isolation, two-span and maximum eight-span insert redo capture, whole-group cap eviction, oversize groups, pool exhaustion, and piece allocator failures before progress and in partial groups followed by successful retry. The same suite passes with the optional read-only B+ tree variant linked from `build/undo-bptree/`; its source was never copied into src.

The bookkeeping benchmark compiles the exact undo.c a second time with trivial piece calls, measuring full replay paths including ref capture and pool operations. Its gate is derived as **10% × G9 p50 63 ms = 6.3 ms for 10,000 steps (G)**. Both p50 and p99 are checked against 6.3 ms. The in-tree flat reference kernel's batch row is TRACK with the request-to-frame G9 context (p50 <= 63 ms, p99 <= 84 ms). Module measurements exclude rendering; a quiet-box synthesis rerun is still needed. Optional B+ tree numbers are (M) indicative, never treated as the end-to-end G9 gate.

Fuzz uses independent full-copy byte-vector history and caller-state blobs, with content checked after every operation. Narrow mode has exact cap accounting; wide mode includes multi-byte edits and spans under a cap the bounded input cannot fill. Random operations include bursts, explicit groups, breaking groups, cap changes, clearing history, and batch undo/redo. Unit tests cover ref flattening and allocator failures separately.

Runtime environment: LeakSanitizer fails under the sandbox's ptrace supervision, so ASan/UBSan checks and fuzz runs use `ASAN_OPTIONS=detect_leaks=0`. Default DISPLAY=:0 is inaccessible; the existing live X11 tests fail under it. Sandboxed Xvfb could not bind listening sockets; an escalated attempt produced a mix of passing cases and initialization failures, so live-X verification did not pass. The final full check unsets DISPLAY, activating those tests' documented headless skips. These environmental issues were reported, not fixed in other modules. No Makefile changes or additional link flags are needed.
