# edit-b6ai.1: make check green on the monolith (THP=always, libxkbcommon 1.13.2)

Measured [AC, desktop monolith], 2026-11-03, THP=always, kernel 7.2.8.

## 1. Undo pool residency under transparent hugepages (product fix)

Symptom: tests/undo_test.c review_3 (after undo_clear + undo_set_cap(1) the pool
must have <= 4096 B resident). Resident pool after the release: 1,093,632 B
(sanitizer build) and 761,856 B (release build, gcc, no ASan), measured with
mincore. With PR_SET_THP_DISABLE: 0 B. Cause: the pool is a MAP_NORESERVE
anonymous mapping; under THP=always its first touches fault 2 MB pages, and
the page-granular MADV_DONTNEED the undo log issues (src/undo/undo.c decommit)
does not give back all of a huge page's memory. This is a real footprint issue
for the editor on THP=always kernels (Arch default), not only a test issue.

Choice: os_vm_reserve (src/os/os_posix.c) applies madvise(MADV_NOHUGEPAGE) to the
whole reservation, once, at map time. Rationale: the os_vm contract is a
page-granular commit/decommit region (os.h), so its memory must be releasable
at page granularity; every user of the reservation (edit_arena, edit_pool, and
through them the undo pool) shares that contract. No syscall is added to the
typing path (reserve happens at pool/arena creation), no malloc, no new
global, no process-wide prctl. Windows is unaffected (os_win.c untouched;
`make TARGET=win all` builds). MADV_NOHUGEPAGE is guarded by #ifdef.
Result: review 3 resident pool 1,093,632 B -> 0 B (san), 761,856 B -> 0 B (rel).

Cost: arenas/pools no longer get 2 MB pages on THP=always kernels (TLB reach).
Coordinator note (2026-11-03): under THP=madvise (Mint/Ubuntu default, the ThinkPad where every
recorded perf number was taken) these mappings never received huge pages, because nothing calls
MADV_HUGEPAGE on them; so the change makes THP=always kernels behave like the measured baseline.
Not measured as a regression: no bench in this bead names it; per CLAUDE.md law 1
that would be a tracked number, opened only from observed lag. Alternative
considered and not taken: madvise only the decommitted range in os_vm_decommit
(a per-release syscall pair, leaves the head of the pool huge-page backed).

## 2. savectl reload ownership bound under ASan + THP=always (test fix)

Symptom: tests/savectl_test.c reload_memory_bound: anonymous ownership delta
5.4 to 7.5 MB (sanitizer build) against the bound 2 * FILE_PREFIX_MAX = 2,097,152 B
(G); with PR_SET_THP_DISABLE 1,286,144 B.

Finding: the release build (gcc, glibc malloc) of the same test, same box, same
THP=always, measures a delta of 20,480 B (M). The product does not have this
footprint issue; the excess is the sanitizer allocator's size-class regions
faulting 2 MB pages (smaps diff: two anonymous VMAs grew by 4,112 kB and
3,280 kB with AnonHugePages 6,144 kB). Moving the reload's copy scratch from
malloc to an os_vm map was tried and did not change the sanitizer figure, so
it was reverted (no product change for this item).

Choice: the test calls prctl(PR_SET_THP_DISABLE) around the measurement, only
in sanitizer builds (__SANITIZE_ADDRESS__ / __has_feature(address_sanitizer)),
and restores it right after. Test code only, the bound is unchanged. The rule
"no process-wide prctl in product code" is honoured.

## 3. keys_test oracle versus libxkbcommon 1.13.2 (test fix, table kept)

The keysym name table (src/keys/keysym_names.h) is generated by
tools/keysymgen.py from the pinned vendor/xkbcommon/xkbcommon-keysyms.h
(libxkbcommon 1.6.0 naming). It is deliberately host independent: Windows has
no host XKB and all platforms must resolve the same names. Regenerating it from
the 1.13.2 header would make the test fail on boxes with an older libxkbcommon
(the oracle is the host library), so the table stays and the oracle absorbs
version skew. 29 table names disagreed with 1.13.2; all are the same keysyms
under a different preferred spelling or case-fold winner:

- preferred name of a value: 0xff7e Mode_switch vs ISO_Group_Shift (1.13 prefers
  ISO_Group_Shift; Mode_switch, script_switch, kana_switch, Arabic_switch,
  Greek_switch, Hangul_switch, Hebrew_switch, SunAltGraph all alias it),
  dead_schwa / dead_SCHWA vs dead_small_schwa / dead_capital_schwa,
  guillemetleft/right vs guillemotleft/right, ordmasculine vs masculine.
- case-insensitive ambiguity: 1.13 prefers the lower-case keysym (dead_i,
  dead_o, dead_schwa, kana_ya, kana_yo, kana_tsu); the pinned table prefers the
  upper-case one, as 1.6.0 does.
- two format rules found while fixing the above: 1.13 accepts "Uxxxx" for C0/C1
  control characters (U001f, U007f, U0080, U009f), the pinned rule rejects
  them; 1.13 names non-BMP Unicode keysyms unpadded ("U10000") where the
  pinned rule pads to eight digits ("U00010000").

Both the old and the new spellings stay in the product table, so config keymaps
resolve either. tests/keys_test.c gets two helpers, host_fold and host_name,
that map exactly these known host winners back to the pinned ones (a pair list,
not a tolerance), so an older host (no skew) and 1.13.2 both pass and any other
difference still fails.

Not done: the pinned header lacks keysyms added after 1.6.0 (dead_apostrophe,
dead_lowline, XF86Accessibility, XF86Fn_*, SSHARP, ...). Bumping the pin is a
separate decision (it also changes Windows tables); it is out of this bead.
