# P1.2b (edit-4w1.12): scan_count throughput in tree build, idle-machine recheck

Date 2026-10-08. Gate G6 (perf §0.2): scan_count >= 12 GB/s p50 on 1 GiB cached. No code changed.

## Power and load
- Start: BAT0 "Discharging" [bat], load 1.31 at first check, 2.31 before the runs. The governor is `powersave`; cpuinfo_max_freq is 5.2 GHz and sampled cur freq was about 1.0-1.4 GHz.
- End: BAT0 "Discharging" [bat] (unchanged), load about 2.0.
- Not idle: firefox-bin (about 55 %), its content process (about 50 %), RDD (about 23 %) and another claude process were busy during the runs. The machine could not be made idle from this worker, so the contention is not removed.

## Compile lines compared
- Standalone: `gcc -O2 -g -msse2 -std=c11 -Wall -Wextra -Werror -Wshadow -Wconversion -c scan.c` (scratch copy of variants/P1.2/sse2).
- Makefile: `gcc -std=c11 -Wall -Wextra -Werror -Wshadow -Wconversion -D_GNU_SOURCE -pthread -O2 -g -msse2 -Isrc -MMD -MP -c`.
- Output: both scan.o are 880 bytes of .text. The scan_count disassembly (objdump -d, no raw bytes) is identical: same md5 of the function body, 85 lines. No codegen difference, so there is nothing to fix in src/scan.

## Conclusion
Not a codegen issue, and not a bench-harness issue. The in-tree and standalone builds produce identical scan_count code and agree within noise. Both run at about 7 GB/s on battery with `powersave` clocks at about 1-1.4 GHz out of 5.2 GHz (CPU-frequency confound, this clock deficit alone could account for a large part of the gap, not measured here), while Firefox was loading the machine. The earlier 6 GB/s in-tree result is therefore explained by the power state and contention, not by the promotion to src/scan. The 12 GB/s gate was not met under these conditions, so this bead does not close G6. The gate needs a rerun on AC with the governor at performance and the machine quiet. No code change was made, so no red/green run is recorded.
