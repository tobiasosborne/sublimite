# P4.14 — measure a login-time warm process before adopting it

**Recommendation: needs a real-display run; do not adopt the GL zygote from
this evidence.** A persistent CPU process makes a large startup difference on
this busy box, but costs permanent residency. Xvfb cannot run the production
native GL backend, and GL probing followed by CPU fallback adds substantial
memory without a clear latency advantage over warming CPU alone. No candidate
is an unambiguous production winner across latency, residency and lifecycle
complexity, so there is no `winner.patch` and no production source change.

This is the edit-457.15 experiment, not an autostart or IPC/editor integration
change. The coordinator retains responsibility for production selection and
announcing any real-display run to Tobias. The claimed previously satisfied
G4a is not re-certified here: the loaded-box normal-exec row is much slower
than that gate. This result is not a quiet-box gate verdict.

## Candidates and common interface

All candidates use **the same `bench/zygote_bench.c`**, executable protocol,
empty-document workload, embedded startup ASCII atlas, editor allocation
limits, render adapter, and strict compiler warnings. The runner builds every
candidate and runs A/B/C/A/B/C throughout one measurement interval.

| Directory | Candidate | Work done before each CLI exec |
| --- | --- | --- |
| `variants/P4.14/a/` | Normal exec, CPU renderer | None; the exec opens a new editor, initializes its font/grid/platform/workers/backend, maps and presents |
| `variants/P4.14/b/` | Login surrogate, GL preferred with explicit CPU fallback | Server fork/exec before threads; `trace_init`, embedded fonts/grid/editor allocations, unmapped X window, backend initialization on a worker, IPC listener |
| `variants/P4.14/c/` | Warm CPU control | Same persistent server policy, without probing GL |

The benchmark forks/execs each warm server once before launches, as a substitute
for login startup. Each subsequent launch is a genuine CLI fork/exec connecting
over `src/ipc`'s single-instance protocol, with a private runtime directory and
`--wait` semantics. Only the server maps and renders. The initial frame is
rendered after the launch request; the benchmark does not pre-render or replay
a cached image. The server retains one editor and window and unmaps it after
completion; subsequent requests force a full layout/render of the same empty
document. Thus the warm policy includes window, allocator and worker reuse,
not just font or dynamic-loader cache reuse. There is no fork of an initialized
GL context or a multithreaded warm process.

`open.c` in each candidate is a copy of `src/editor/open.c` with two measurement
seams: a map wrapper that records A's original map location and suppresses
mapping while B/C are warming, and first-frame render hooks. Shared
`variants/P4.14/editor.c` copies the editor loop and wires the GL completion
callback; the warm runtime polls GL's fence event outside submit. Native GL
routing is included for a later experiment but **cannot be verified on Xvfb**.
All remaining implementation comes from the production module library. No
frozen header, Makefile, or production C file was edited; no new globals.

The shipped `src/main.c` currently selects CPU and does not route IPC. This
experiment uses the actual editor/render startup path but disables file loading,
indexing and journaling, and does not perform the CLI's session-directory work.
It measures an empty document with the editor's default viewport and reservation
bounds. It is a controlled startup comparison, not an exact measurement of the
complete shipped file-launch CLI or the panel-size G4a fixture. B/C also retain
an empty editor while idle; production tab reset, journal ownership and file
requests are outside this prototype. Neither a login service nor installer was
created. These qualifications matter before applying the speedup to production.

## Measurement protocol and endpoints

Before the run, the script executes:

```
cat /sys/class/power_supply/BAT0/status
cut -d' ' -f1 /proc/loadavg
```

The common driver reads both files again before every launch. All windows and
launches use `DISPLAY=:99 EDIT_DISPLAY=:99`; `EDIT_ALLOW_REAL_DISPLAY` is unset.
The driver rejects any other display. Local X11/IPC socket access required the
approved execution environment; the sandbox-only test could not connect.
No real-display window was opened and no cold-cache/drop-caches row was run;
cache eviction requires root and is deliberately skipped.

The retained valid run has **200 launches per candidate (M)[AC]**, strict A/B/C
order, beginning load1 **26.79 (M)[AC]**, launch load1 range **26.24–28.10
(M)[AC]**. First to last launch markers span **87.810 s (M)[AC]**. Summary and
idle rows carry load1 **26.24 (M)[AC]**, power `Not charging`. These are TRACK
numbers on the box as it was, including other workers and verification builds.
We did not wait for a quiet window or rerun to improve load.

The child stamps `CLOCK_MONOTONIC` after fork and descriptor setup, immediately
before sending its timestamp through an eight-byte pipe and calling `execl`.
The exec marker includes that small pipe write and exec call, but excludes fork.
Map timing is after `plat_map` queues/flushes the map request. The first-present
request is the actual editor `on_present` timestamp after backend present
succeeds; it is **not a photon timestamp**. The additional matching-frame
completion comes from the real render adapter's completion hook, not a synthetic
sleep or uncorrelated X event. Both must have the same first-frame ID as the
buffer-ready hook. Every launch verifies the window is viewable, then unmapped,
and requires successful CLI exit and IPC wait completion.

`exec_ready_and_map` is the maximum of first-frame CPU-buffer-ready and
map-requested timestamps. Input infrastructure exists before this frame is
submitted. This avoids mistaking the earlier raw map request for G4a. Native GL
would require a separately defined CPU-ready endpoint; its fence timestamp must
not be substituted for G4a. The current CPU-ready-before-present validation
would reject a later GL fence timestamp. Before a real-display run, separate
CPU submit readiness from device completion in that hook/validation; the
native path has not been exercised. The rows here all use CPU rendering.

Percentiles use nearest rank: rank 100 for p50 and rank 198 for p99 of the
200 observations. Faults are per-launch `getrusage` deltas for B/C and whole
fresh-process counts for A; they are **fault counts, not unique pages touched**.
All measured results below inherit `(M)[AC]`, `Not charging`, per-launch
load1 26.24–28.10; the summary stamp is load1 26.24.

## Pareto front and judgment

For the measured objectives (map and first-present p50/p99, persistent RSS,
initialization high-water RSS, binary size), the strict Pareto front is
**A, B and C**. A pays nothing between launches. C has dramatically lower
latency at a permanent memory cost. B has slightly better raw map/tail timings
in some rows, while C has better first-present medians, first-present-request
tail, size and memory. It would be incorrect to declare strict statistical
domination from these crossing tails or to treat the fallback as a GL win.

The paired C-vs-A comparison is more decisive about warming CPU resources:
C's buffer-ready-and-map time is lower in **200/200 pairs (M)[AC]**, and its
first-present request is lower in **200/200 pairs (M)[AC]**, load1 26.24–28.10.
The median paired reduction is **205.812 ms** for buffer-ready-and-map and
**205.335 ms** for first-present request (M)[AC], the same load range.
This is a useful loaded-box result, not a sum of stage percentiles.

The normal editor initializes its backend after the original map point, using
maximum resize reserves and faulting its shared framebuffer on every fresh
process. Warm variants avoid that work as well as worker/window initialization.
The observed benefit therefore cannot be attributed to GL/font initialization
alone. The normal G4a reference budget is **25 / 40 ms (G)**. The loaded A
comparison is above it, whereas B/C fallback rows are below it; these comparisons
remain TRACK because of load, workload qualifications, and Xvfb. They do not
establish a regression against a previously measured production gate.

Warming a CPU server could be worthwhile if real startup lag matters to Tobias;
this run measures a substantial benefit under contention. It is not a free
improvement: an otherwise closed editor now retains its reserved document,
window, renderer and worker state continuously. Autostart readiness, restart,
login/logout cleanup, display-session changes, backend failure policy, actual
file/tab/journal requests, secure single-instance arbitration and graceful
shutdown would also need production implementation and tests. This prototype
is killed after the test and does not establish those lifecycle guarantees.

For **B specifically**, there is no demonstrated reason to pay the GL-preferred
resident policy's complexity or fallback memory cost when C delivers essentially
the same measured startup class. A nominal win on a gate already satisfied is
not sufficient by itself. Keep normal production startup for now; if the
consultant wants to pursue the measured loaded-box lag, compare warm CPU as well
as native GL in the announced real-display experiment. No exact production
patch is proposed while that tradeoff and the native backend remain unresolved.

## Xvfb limits and the later real-display run

Xvfb cannot show real GPU clock/power state transitions, context wake latency,
real vblank/scanout cadence, compositor/WM effects or on-glass first pixels.
Its Present completion timing is an X server observation, not real vblank.
The production GL backend needs DRI3 and verified native Present completion,
which fails here. The permanent GPU context's memory/power cost is unmeasured.
Xvfb also has no normal desktop window manager or focus/blink workload.

A later run must be **announced by the coordinator to Tobias** and explicitly
use the real display only in that authorized session. It needs native GL init
success and a reported device/driver, matching original-frame GL fence/Present
completion validation, realistic panel-size viewport, actual CLI file/journal
startup and IPC requests, effects-on/off conditions, and exec/map/first-present
plus on-glass or compositor timing where available. Interleave normal CPU,
warm native GL, and warm CPU; separately report normal GL exec to distinguish
backend choice from warming. Include both launch cadence and genuine after-idle
GPU wakeups, service startup cost, owned graphics peak memory, hidden idle power
and focused/unfocused G11 blink CPU/wakeups. Do not fork an initialized GL or
multithreaded process. This worker did not perform or authorize that run.
Cold-cache rows remain skipped unless the coordinator explicitly arranges root.

## P4.14b harness

This follow-up (edit-457.23) makes the standalone experiment display-aware;
there is still no production/autostart change or winner. Historical P4.14 rows
above remain unchanged. Their statements that the runner always forces :99
and that native readiness is not implemented are superseded by this section.

`--real-display` is an explicit opt-in, rejected with exit 2 unless the caller
already supplied exactly `EDIT_ALLOW_REAL_DISPLAY=1`. It preserves the caller's
nonempty, identical `DISPLAY` and `EDIT_DISPLAY`. Without that flag the shell
runner sets both to :99; an inherited permission variable alone cannot select
the real display. The common driver and all four candidate executables check
both keys again, before any X/IPC connection. The worker never set the permission
variable, selected :0, or ran a native real-display launch.

The exact command for the **coordinator only, after announcing the batch to
Tobias**, is:

```sh
env DISPLAY=:0 EDIT_DISPLAY=:0 EDIT_ALLOW_REAL_DISPLAY=1 EDIT_GL_SWAP_INTERVAL=1 tools/zygote_bench.sh --run --real-display --launches 50
```

Capture stdout/stderr for the batch. Record the compositor/effects condition
externally; the harness does not change desktop settings. Swap interval is
printed in `CONDITIONS`; the command explicitly chooses vblank pacing. Repeat
under another effects condition only when the coordinator authorizes that batch.

`--run` defaults to 200 observations per variant, with `--launches N` accepting
1..10000. `--self-check` retains a short two-cycle default and also accepts an
explicit count. `--build` validates arguments and permission without connecting
to a display. Before service startup the driver prints one flushed `ESTIMATE`
line: `10 + 2*N + 12` seconds for a run, or `10 + 2*N` for a self-check (E).
This rough shared-box estimate includes warm initialization, launches and hidden
idle observation, excludes compilation, and is not a timeout or measured gate.
Its power/load stamp is read before the estimate/measurement starts.

The real-display comparison is A normal CPU exec / B warm **required native
GL** / C warm CPU, repeated in strict A/B/C order. D in `variants/P4.14/d/`
is fresh normal GL exec and runs separately after the paired interval. B and D
fail the opted-in run on native init failure; CPU fallback cannot masquerade as
a real GL row. On :99 they exercise the GL probe and explicit CPU fallback,
printing `backend=cpu_fallback`, the original `gl_result`, and `NATIVE_GL ...
status=SKIP`. This verifies all launch modes on Xvfb, not native rendering.
D shares A's `open.c` seam, and all candidates share the runtime/editor loop.

On an opted-in display every candidate derives its initial viewport from the
selected root screen's pixel size and embedded atlas cell dimensions. The
actual post-WM grid/pixel dimensions are printed on each `SAMPLE`. Maximum
reserves remain the editor's bounds, expanded when the panel needs more cells.
Native warm init temporarily maps its window so the production backend can
verify native Present swaps, then unmaps it **before IPC readiness**; that initial
window belongs to the announced service-startup interval, not a launch sample.
D also includes the production init probe in its startup cost. Its reported
first present is the first original **editor** frame, excluding init probe swaps
(which can draw placeholder pixels); it is not the earliest visible pixel.
There is no fork of a GL context or threaded editor: the driver forks/execs a
fresh server before that child initializes workers/GL, and CLI children carry
only the IPC launch request. Warm servers still own one empty editor/window.

Native CPU readiness is now the successful original-frame **CPU submit**
timestamp. CPU rows retain the raster buffer-ready timestamp. Neither is the
GL fence: the device hook records a distinct `device_ns`/`device_frame`, and
Present records a distinct `complete_ns`/`complete_frame`. Validation requires
map <= present, readiness <= present <= device <= completion, identical nonzero
original frame IDs, and verified viewable/unmapped states. Native rows also
require successful GL init, nonzero displayed MSC, and nonempty device/driver
identity. Production GL still verifies the matching PIXMAP Present serial and
fence; no fabricated completion or fence-as-CPU-ready substitution is used.

`DEVICE` prints the actual GL renderer and `GL_VENDOR; GL_VERSION` (including
the driver version) after the first successful present has bound the context.
The diagnostic loader lookup happens during open; native queries happen in the
present hook, outside input->submit. CPU/fallback identity is `CPU raster` /
`XShm/Present`. Every variant prints exec->map, exec->first-present request,
exec->device done and exec->matching first-present completion p50/p99. Native
readiness is named `exec_cpu_submit_ready_and_map`, so it cannot be confused
with CPU buffer readiness or a G4a verdict.

`WARM` includes init time and fork/exec->listener-ready service cost, plus RSS,
VmHWM and fault counts. Hidden idle RSS/PSS/private pages and all-thread CPU
ticks/context-switch deltas are retained. After the idle interval the driver
also performs one extra validated B/C launch, printed separately as
`AFTER_IDLE`; these diagnostics are excluded from the N-sample percentiles.
Their `idle_ns` is the actual interval since that server's last matching frame
completion, including D's separate interval, not just the nominal idle sleep.
This distinguishes launch cadence from after-idle context wake latency without
claiming direct GPU clock/power telemetry. All measured rows are power/load
stamped `(M)` and TRACK. The independent audit accepts arbitrary counts,
checks original-frame ordering, native requirements and all percentile rows,
and still validates the retained historical A/B/C results.

The remaining broader real-display requirements are explicitly printed as
`COVERAGE ... SKIP`: on-glass/compositor timestamps, deduplicated owned graphics
peak, GPU/hidden idle power, focused/unfocused G11 blink and cold-cache rows.
This remains an empty-document experiment, not the shipped CLI's file/session/
journal lifecycle. Those external/workload measurements and a production service
are still needed before adoption; process RSS is not G10 owned graphics, and
context switches are not focused blink wakeups. Native execution itself awaits
the announced coordinator run.
