# P1.4e — checkpoint implementation and G10f accounting (edit-4w1.37)

## Scope and disposition

removed. The frozen checkpoint rows pass. Review findings §3, §6 and §7 are
fixed; §4's header waste and §5's unrequested-reference copying are fixed.
**This is not a complete G10f closure:** the fixed snapshot allowance at deeper

handoff file was edited. Findings §8–§10 remain for edit-4w1.38.

## Checkpoint ownership

Begin retains an ordinary cached snapshot, reserves a directory sharing the
saved ADD prefix, and saves counts, initialization/mapping state and append/
cursor controls. There is one handle per tree; NULL/nested calls return RANGE
and clear the output. Both successful endpoints consume the handle exactly
once. Failed begin preserves content and opens no checkpoint.

Commit drops the retained root and prefix reservation. Abort transfers the
retained root back, restores control/counters and swaps the ADD directory back.
It force-trims unused node reservations even with earlier snapshots alive.
Neither endpoint requests an allocation, including under persistent failure.
A saved cursor is reused only while its entire path remains exclusive; a
snapshot of unchanged/intermediate content may require ordinary COW on the
next edit. The saved append run itself survives rollback and empty commit.

Snapshots retain their own directory and original/mapping epoch. A live node's
otherwise-unused free-link word holds its subtree's highest referenced ADD
endpoint; no node-size increase is needed. This also bounds ordinary snapshot
storage after tree destruction. Original epochs allow initialization inside a
checkpoint to be aborted/retried while its snapshots keep their own data and
mapping owners. Sealed directory pruning runs under its ownership lock.

Before publishing a transaction snapshot that observes the saved partial
boundary, snapshot take reserves a writable copy for restoration. Abort can
therefore restore a writable boundary without allocation or a deferred copy
on the subsequent edit path. If no transaction observer survives, abort frees
that copy and shares the original boundary again. The sole inactive checkpoint
branch is in snapshot take; ordinary edits consult no checkpoint state.
Subtree ADD endpoints and deleted-original/fallback counters are general G10f
ownership accounting, rather than per-transaction edit journals.

Refs outside the restored logical ADD mark are RANGE, even if an intermediate
snapshot keeps their physical bytes. Empty/old-range/reused-offset aliases are
caller errors, as specified; no further generation detection is claimed.

## Review fixes

- §3: full-entry cursor deletion falls back before a non-root leaf becomes
  underfull. General merging can use the full node capacity. Two-slot slabs
  (G, layout) bound the sparsely occupied slabs that the thinning sequence
  leaves behind. Merely rebalancing with the previous four-slot slabs did not
  meet the bound. The whole-slab trim algorithm itself is still unchanged.
- §4: snapshot headers use a separate 80 B class (G, layout), instead of the
  272 B leaf class (G). Tests count its slab overhead and inspect actual copied
  paths at every synthetic height from one through fifteen (G, fixtures).
- §5: collection counts ORIGINAL bytes through the complete range, including
  after span overflow. NULL-ref deletion copies only those bytes; it never
  duplicates fragmented ADD payload. Deleted-original and overflow-ADD totals
  are separate private counters and rollback restores them with the tree.
- §6: pool reservations, return completion, trimming and core teardown share a
  recursive ownership mutex. A reservation remains protected until mutation
  finishes, so a final worker release cannot free preflighted slots. External
  ownership is counted separately from the current-version cache. Final
  external release trims immediately, including while that cache remains.
  Tree destruction also seals/prunes its directory and relinquishes original
  data ownership; an earlier snapshot retains only its referenced ADD prefix.
- §7: build failure returns newly unused reservations under the same lock,
  even with pinned snapshots. Copy/mapped initialization and creation have
  allocation-failure sweeps that inspect live bytes before cleanup queries.

## Unresolved frozen contracts — do not silently change their funding

The primary perf formula funds actual live snapshot path copies. The frozen
header instead promises a constant 1920 B per live-snapshot edit (G). This
layout's height-four path alone costs 1872 B (G, configured sizes); adding the
80 B header and amortized slab overhead gives 2000 B (G). At height fifteen,
the node path is 6272 B (G). Compact headers make the review's changed-version
fixture green, but cannot turn that constant into an arbitrary-depth bound.
`piece_mem_test --depth-contract` keeps the incompatible allowance visible.
The default deeper test charges actual paths, headers, slab overhead and
trailing class slots; it does not claim the constant is satisfied.

The boundary reservation can require another 64 KiB ADD chunk (G, layout)
while an inside snapshot owns the old boundary. All of it is allocator-charged
and the copy is reclaimed when no observer needs it. It is not funded by a
1920 B node-only allowance (G) for a tiny transaction. A finer ADD layout or an
explicit snapshot-storage allowance is needed for a universal strict bound;
the frozen checkpoint memory row checks large transactions without surviving
inside snapshots and is not proof of this boundary case. No aborted typed/
deleted credit is retained to hide the reservation. This remains part of the
snapshot funding issue, rather than a claimed gate pass.

Requested overflow references require copying the entire deleted range into
one span, including already retained ADD bytes. Strict G10f funds typed and
deleted-ORIGINAL bytes, not those duplicates. The required lifetime of earlier
refs prevents simply discarding their backing. The requested nine-block probe
still exceeds the strict bound; `--requested` reproduces it. The implementation
preserves the frozen complete-reference behavior and reports fallback ADD
bytes separately. Resolving this needs an approved representation/contract
change or explicit fallback funding. The optional clarification received no
resolution during implementation; no header amendment was inferred.
