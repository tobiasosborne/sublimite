### Table errors found by diffing against tables.h
All three got these wrong:
- U+00AD soft hyphen: Cf, so zero-width in tables.h. All three return 1 because their `cp < 0x300` fast path skips the table. Variant 2 even lists U+00AD in its zero table, but the fast path hides that entry.
- U+115F and U+3164 (Hangul fillers): Default_Ignorable, so 0. All three said 2.
- U+1F1E6..1F1FF (regional indicators): Emoji_Presentation, so 2. All three said 1, and variant 3's suite asserted `width(0x1F1E6) == 1`.
- U+31EF and U+2FFC..2FFF (new in 15.1): W, so 2. Variant 1 missed U+31EF; variants 2 and 3 missed all five.
- U+1AFF4 and U+1AFFC (unassigned gaps in Kana Extended-B): 1. All three said 2.
- 30 to 50 ranges per variant where non-marks or unassigned code points sat inside coarse "merged" zero ranges and came out 0 (e.g. U+0A3D, 0A43..0A46, 0B49..0B4A, 0C45, 1E025). Variant 1 had 118 such code points, variant 2 336, variant 3 362.
- Missing Cf/Prepend zeros: U+0600..0605, 06DD, 070F, 0890..0891, 08E2 (variants 1 and 3), and dozens of supplementary-plane marks such as 10EFD..10EFF, 11070, 110BD.

Variant-specific:
- Variants 1 and 2 return width 1 for most of E0000..E0FFF (about 3,700 Default_Ignorable code points).
- Variants 2 and 3 set U+1161..11FF and D7B0..D7FF (conjoining jamo V/T) to 0 as a terminal convention. tables.h says 1 (EAW N, not ignorable). Cluster width is the layout's job (see Follow-ups).

### Grapheme bugs (cases from the new suite)
- **Variant 1**: no CR LF rule, so CRLF splits (GB3). Controls take combining marks (GB4/GB5). ZWJ joins any following pictograph even without ExtPict before it (GB11). No Prepend rule (GB9b). No Hangul rules (GB6-8). A mark between two RIs does not reset pairing.
- **Variant 2**: ZWJ joins only pictographs that are both wide and at or above U+2600. So the runner + ZWJ + U+2640 + VS16 sequence splits. GB11 does not require ExtPict before the ZWJ. ZWSP (GCB Control) joins the base. No Prepend rule. L+L does not join. LVT+V and T+V join wrongly, through the zero-width-jamo convention.
- **Variant 3**: U+2028 does not break. The GB11, Prepend and L+L gaps are the same as variant 2's, and so is the LVT+V / T+V over-joining. A mark between RIs does not reset pairing.

## What was taken from where
- **Header shape**: variants 2 and 3 (inline fast path, slow path out of line). It was then pushed further: the whole decoder is `static inline` in `utf8.h`. Measured: out of line, the struct is returned packed in RAX, so the caller's `off += s.len` depends on the loaded bytes and serialises the loop. Inlined, `len` comes from the predicted branch. Decode+width for 500 scalars (runs mix) went from about 3.9 to 2.95 µs p50 (M)[bat]. Because of this, `utf8_decode_multi` is gone from the API.
- **Decoder**: variant 3's text (identical in logic to variant 1). Every byte outside Table 3-7 is rejected before any cp is formed. Invalid gives {first byte, 1, 0}. It reads p[1..3] only after the matching `n` check.
- **prev**: variant 3's bounded walk (`lim = off - 4`), plus variant 1's ASCII fast path and an `off == 0` guard. The proof comment is in `utf8.c`. Consistency is tested exhaustively (every scalar after 8 left contexts, valid and invalid) and on random buffers, and checked again in the fuzzer.
- **encode**: variants 2 and 3 (U+FFFD for surrogates and > U+10FFFF). Variant 1's bug is not carried over.
- **Bulk helper**: variant 2's `utf8_ascii_run`, chosen over variant 1's `utf8_count`. `ascii_run` is a primitive that composes with decode: layout does `run = ascii_run(); each byte is 1 cell; decode the next non-ASCII`. `utf8_count` answers one fixed question (scalar count) and re-implements validation. The callers that need a count can write it in three lines. Variant 1's real idea, taking the length from the lead byte to shorten the dependency chain, is subsumed by inlining the decoder. `ascii_run` was widened to OR 32 bytes per step and locates the first high byte with `ctz` (little-endian guard; other targets fall back to the byte loop). It never reads past p[n-1] (tested at every length 0..80, every high-byte position and misaligned starts).
- **Width**: rewritten over `UCD_ZERO_WIDTH` / `UCD_WIDE`. Zero wins where both apply (U+115F, 302A..302F, 3099..309A, 3164, 16FE4, 16FF0..16FF1). The fast path is `cp < 0x300 → cp != 0xAD`. The suite asserts the two table facts it relies on and compares every code point against a table reference. The lookup is a decision tree: `tree10..tree0` are `always_inline` functions over a static const table. With constant lo/n the compiler folds every `t[i].lo` into an immediate (checked: gcc 13 and clang 18 emit no table loads), which leaves compare-and-branch only. Best-of-7 micro numbers on CJK-only input (M)[bat], loaded: branchless binary search 19.9 ns/lookup, full tree 6.9, top-6 hybrid 7.7, top-4 hybrid 10.5. 4-ary and 8-ary searches and a sampled-separator first level were all slower than the binary search. Cost: about 2.5k instructions for both trees. The grapheme property tables keep the branchless binary search, because a tree for EXTEND+SPACINGMARK+EXT_PICT would add about 20 KB of code for an ungated path.
- **Grapheme**: rewritten as UAX #29 (15.1) GB3..GB13 from tables.h's EXTEND, SPACINGMARK, PREPEND, REGIONAL_INDICATOR, HANGUL_L/V/T/LV/LVT and EXT_PICT, with ZWJ = U+200D. Known deviations, documented in the header:
  - GB9c (Indic conjunct break) is not implemented: tables.h has no InCB property.
  - GCB=Control is approximated as Cc + U+2028/2029. Unicode stability makes those sets fixed, so this is not a hand table. Cf code points that UAX #29 also calls Control (ZWSP U+200B, LRM, U+FEFF, U+00AD ...) are classed Other: they still break from their predecessor (GB999), but an Extend after them joins them, where UAX #29 would break (GB4).
  - Invalid bytes are single-byte clusters and never take extenders.
- **Tests**: the union of the three suites, deduplicated. Width expectations were re-derived from tables.h, and the corrected ones are commented (U+00AD, 0600, 115F, 1161, 2FFC, 31EF, 3164, 1AFF4, 1F1E6). New: exhaustive decode against an independent reference at every truncation n = 1..4 with exact-size heap placement, so ASan catches any over-read; Table 3-7 second-byte windows stated directly; lead-class sweep; truncation of every scalar at every shorter length; forward/prev consistency for every scalar after 8 contexts; exhaustive width for all code points through both `utf8_cell_width` and `utf8_cell_width_table`; 43 grapheme cases (GB3-GB13, invalid-byte interaction); `ascii_run` boundary sweep; 240 random buffers from four generators (variant 1's, variants 2/3's, uniform, mutated valid). Random-buffer checks also require that grapheme boundaries land on unit boundaries.

## Gate reset
The P1.1 brief's "2 GB/s whole-buffer decode" gate was invented; all three variants missed it, at 0.4 to 1.2 GB/s mixed. It is replaced by perf/01-perf-target.md §3, "UI thread: wall-time slices ≤ 0.5 ms; ≤ 96 KiB decode or ≤ 500 shaped chars per slice", which gives:
- decode + cell width of 500 mixed scalars: p50 ≤ 5 µs, p99 ≤ 10 µs (G)
- bulk ASCII run-skip: ≥ 8 GB/s at p50 (G), i.e. 96 KiB in ≤ 12,288 ns.

Mix, by scalar count: 55 % ASCII printable, 20 % Latin-1 U+00A0..00FF, 15 % CJK U+4E00..A1FF, 10 % emoji U+1F300..1F44F; 1.80 B/scalar. In the gated windows ("runs") the class is drawn per run of 1..40 scalars, the way text arrives in words and script spans. 4,096 distinct windows are cycled, 20,000 samples. An i.i.d.-per-scalar mix is also reported as an adversarial bound, not gated.

Under heavier load, earlier runs in this session showed p99 spikes up to 10.2 µs on the runs mix (one run missed p99 by 174 ns). That is preemption on a loaded box, not code. The p50 margin is about 40 %. The i.i.d. mix misses the 5 µs p50 by design: about half the scalars switch class, so branch mispredicts dominate. It is recorded so the bound is visible. The bulk-skip gate passes about 3.4x over, well above the variants' own 10 GB/s, despite the power state.

## Follow-ups (not done here; for the coordinator)
- tools/ucdgen.py could emit a two-stage per-code-point property table (width plus GCB plus ExtPict in one byte; stage 1 indexed by cp >> 8). That would make width and grapheme classification O(1) and drop the decision tree and the ten binary searches in `gcb_of`. grapheme_next is the slowest piece at about 31 ns/scalar on runs (M)[bat].
- ucdgen should emit InCB (for GB9c) and GCB=Control (so Cf breaks correctly) tables.
- Layout needs a cluster-width rule. The sum of scalar widths over-counts ZWJ emoji sequences (man ZWJ woman ZWJ girl = 6) and counts conjoining jamo V/T as 1 each. The usual rule is the width of the first scalar, or 2 when VS16 follows a narrow pictograph.
- `utf8_grapheme_prev` (backward cluster step) is not provided. Cursor-left will need it, or the layout's cached cluster boundaries.
- The i.i.d. mix (adversarial) is 7.8 µs p50. If a real workload ever looks like that, a branchless decoder is the lever.
