## §1 — failed writeback

**Valid; fixed.** fdatasync failure poisons the entire live generation.
`journal_retry` returns IO without clearing suspension; only a complete CURRENT
checkpoint synced into a fresh inode and published with its directory barrier
repairs it. Partial append failures still retry exact missing tails; directory
barrier retry remains available. The oracle consumes EIO, removes volatile
bytes, and includes a previously released unsynced batch. Fuzz sync failures
also lose bytes and require fresh checkpoint recovery.

GREEN ([AC] load1=5.54): `journal_test: writeback loss requires a fresh checkpoint (released unsynced batch included)`

## §4 — busy bulk worker / power-loss bound

**Valid; proposal only, unresolved.** A reserved durability execution lane must
be added to work as `WORK_DURABILITY`, with its own worker/queue (or a separately
owned pool/event source must be integrated
by the caller), independent of index/find/save bulk jobs. It needs reserved
submission/mailbox capacity and a deadline timer. Track actual page-cache
bytes not covered by a completed durability fence, not worker-accounted chunks.
Admission must prevent that volume exceeding the selected bound. Wire records
must fit the available credit too: a torn large CRC-protected record otherwise
discards more logical content than its missing tail.

A dedicated lane alone is insufficient: P1.9g admits an atomic (E) 1 MiB paste
and writes each record before returning; even one such write can place more
than (G) 64 KiB in cache before any worker can sync. The caller needs a protected
large-edit continuation with a durability credit/fence handshake and explicit
BUSY/input progress, retaining the successful per-record synchronous commit.
A syscall or device stall also cannot have an unconditional wall-clock bound.
Do not relabel the PRD maximum as a qualified cadence target. These changes
need work and editor/file integration, prohibited by the brief; no partial
scheduling workaround or contract relaxation is installed here.

RED ([AC] load1=1.90):
`journal_test: bulk-loss repro unprotected_bytes=1602856 (M) limit=65536 (G) durable_records=0`
`journal_test:1415 FAIL unprotected<=JOURNAL_DEFAULT_SYNC_BYTES`

No GREEN claimed. Reproduce: `build/tests/journal_test --bulk-loss-repro`.
The independent durable image is empty with the shared bulk lane occupied.

## §6 — retained identity metadata

requires full metadata persistence; existing copy-failure fixtures now inject

## §7 — UI CRC/write time bound (continuation below)

**Valid; proposal only, unresolved.** A supported SSE4.2 CRC32C dispatch plus
portable fallback can reduce CRC CPU work, but cannot bound a regular-file
pwrite. The syscall seam reproduces a stall with even a single-byte record,
independent of CRC speed. A true fix needs editor large-edit continuations,
input servicing between encoding slices, protected completion, and resolution
of the unavoidable synchronous-syscall limitation while keeping P1.9g. Proposed
journal interfaces expose an immutable edit plan and bounded encoding step;
the editor resumes it and publishes completion only after all writes succeed.
No O_NONBLOCK claim or arbitrary timing waiver is made. The continuation
implements the CPU optimization, with independent wire compatibility checks;
it does not substitute that optimization for the complete time-bound fix.

`journal_test:1432 FAIL elapsed<=500000`

## §8 — save preparation before acknowledgement

**Valid; proposal only, unresolved.** Preserve the saved immutable snapshot and
cutoff at request time, enqueue retention/checkpoint IO immediately, publish
an immutable completion through mailboxes, then authorize replacement of that
same snapshot. Rebase concurrent deltas when adopting the prepared generation.
The editor must acknowledge enqueue and service typing while preparation runs;
file save must use the captured snapshot rather than a later current tree.
Proposed entry points are `journal_save_prepare_begin` and a routed PREPARED
completion; a file save entry point accepting the captured snapshot must follow.
An additive journal begin/receive API without updating that caller protocol
would leave G8s broken or save the wrong snapshot. The existing synchronous API
is retained, as changes to those modules are forbidden.

directory before publishing BASE. No new directory ancestry is created.
