# P1.6: lineidx, sparse line index (edit-4w1.6)

`src/lineidx/lineidx.{h,c}`. Tags: (G) gate, (M) measured, (P) physics. Bench numbers here were
taken on a loaded box ([AC], load ~6, other workers compiling); the coordinator re-runs on a quiet box.

## What
- One 16 B entry per chunk `{uint64 start, uint32 newlines, uint32 flags(built|nonascii|edited)}`,
  nominal chunk 64 KiB, `_Static_assert`ed. Plus 8 B per 64 chunks of prefix sums (0.125 B/chunk):
  live 16.125 B/chunk (M), 264 200 B for 1 GiB.
- Content is described by a `lineidx_src` span callback (mapped file, flat buffer, piece_snapshot
  adapter); no dependency on piece internals. Tests drive it from a `piece_snapshot` too.
- Build = one bulk job on `src/work`, slice = one chunk, `work_should_stop` every 16 chunks (~1 MiB,
  ~0.2 ms), progress `work_publish` every 64 chunks (256 msgs/GB), best effort. Results go into a
  per-job block (`res[]` + release-published `done_n`); only the UI thread writes the table
  (`lineidx_poll` copies `[applied, done_n)`), so the table has no data race and no locks.
  The job block is retired when finished or cancelled and freed once `busy==0` (slot check) or its
  `fn_done` flag is set; `lineidx_destroy` waits for that (ms-scale).
- Exact vs estimate: `lineidx_result.exact`. "Prefix" = leading built chunks; exact answers lie inside
  the prefix (at most one chunk is re-scanned from the source). Past it: byte-proportion estimate
  from prefix density (default 40 B/line before evidence), aligned back to a real line start.
  A complete index (prefix == all chunks) is exact everywhere, including "line past end".
- `lineidx_seek_line(budget)`: scans forward from the prefix end on the calling thread, recording each
  chunk it counts (the prefix grows), so a later jump is free. Exact when the target is within budget.

## Edits (chunk boundaries vs content offsets)
Chosen: explicit per-chunk `start` offsets (not fixed `i*64K`). `lineidx_edit(off, del, ins_len)` merges
the touched chunks `[c0..c1]` into ONE entry (length arithmetic only, flagged edited+unbuilt), memmoves
the tail and shifts later starts (O(chunks), ~16 K adds for 1 GB), splits to 64 KiB pieces when the merged
chunk exceeds 128 KiB and the fixed table (capacity 2n+64) has room, removes a chunk that became empty.
`lineidx_refresh(cur)` rescans edited chunks from the current content (one chunk, bounded by chunk size).
Unedited chunks keep their counts, so only touched chunks are invalidated; chunks before the first
unbuilt chunk stay exact for queries even before refresh. An edit cancels the running job (finished work
is applied first); the caller restarts the build later over a new snapshot and built chunks are skipped.
No allocation in edit/refresh/poll/queries (tested with the counting guard).

Rejected: (a) index only the original and combine with piece-tree counts: needs piece internals and a
second source of truth; (b) fixed `i*64K` geometry with later chunks invalidated by every insert:
O(chunks) rescans per keystroke; (c) a Fenwick tree over starts: 16 K entries make the linear shift
cheaper than the pointer chasing.

## What each gated cell measures
- G7 `G7_index_1g_warm`: `mmap` of /tmp/edit-corpus/log_1g.txt (new mapping, warm page cache, 2 warm-up
  reps) -> `lineidx_create` -> job submit -> exact index complete and applied on the UI thread (UI
  polls every 50 us); line_count verified = 8,947,842. Single bulk worker.
- G7j `G7j_partial_jump_90pct`: line 10^7 does not exist in log_1g (8,947,842 lines), so
  target = floor(0.9 x line_count) = 8,053,057 (derived at run time from a reference full build).
  Fresh mapping, build started and cancelled once 50 % of the chunks are applied (`--partial=F`), then
  timer starts at the `lineidx_seek_line` request and stops with the exact byte offset of that line's
  start (verified against the reference). Includes the exact scan of the remaining ~40 % of the file
  (bounded by the budget = whole file here) and page faults of the new mapping. Excludes layout and
  rendering of the viewport.
- Cancel ack: `lineidx_build_cancel` + wait until the worker has let go; TRACK (binding G6c is P1.8's).
- Memory: live bytes / chunks <= 16.5.

## Numbers (M)[AC], loaded box, indicative
See the report. Raw `scan_count` over the same mapping ran at 5.4 GB/s on this box (190 ms/GB) instead of the
16 GB/s planning figure, and the build costs within a few % of that, i.e. the module adds no measurable
overhead over the scan; whether G7/G7j pass is decided by memory bandwidth on a quiet box.
