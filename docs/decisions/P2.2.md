# P2.2 x11 input (edit-e6x.2)

Files: `src/x11/{plat.h,input.[ch],xi2.[ch],clip.[ch],x11.c}`, tests `tests/x11_input_test.c`, `tests/x11_xi2_test.c`, `tests/x11_live_test.c` (skips without DISPLAY), fuzz `fuzz/x11_input_fuzz.c`, bench `bench/x11_bench.c` (tracked, no gate).

## plat_event (platform-neutral, freeze candidate)
`plat_event` keeps the P2.1 fields and adds: `keysym`, `utf8[8]`+`utf8_len`, `repeat`, `mods` (PLAT_MOD_* bits, not X bits), `buttons` (bit n-1 = button n), `dx/dy` + `smooth` (wheel), `clip_ok/clip_which`, `t0_ns`. New kinds: WHEEL, CLIPBOARD, KEYMAP. Events are delivered by `on_event` from `plat_run_for` and are also poll-able with `plat_poll_event`; both read one fixed 256-slot ring (overflow drops and counts, never blocks, never mallocs).
- KEY `utf8` is text to insert: printable only. Control characters (Return, Tab, Esc, BackSpace, Ctrl-letter chars) and anything with Ctrl/Alt/Super held give `utf8_len == 0`; consumers dispatch on `keysym`+`mods`. AltGr (Mod5/ISO_Level3) does not suppress text (de AltGr-q gives "@"). `keysym` is xkb's keysym for the event's modifiers (shift-a = `A`, ctrl-shift-a = `A`, ctrl-a = `a`); lowercase it with `xkb_keysym_to_lower` for binding lookup. Release events carry keysym but no text.
- WHEEL: `PLAT_WHEEL_UNIT` (256) = one notch; +dy = scroll down, +dx = scroll right. `smooth` = XI2 valuator deltas, else a core button 4-7 step of exactly one unit.
- CLIPBOARD `code`: 0 data arrived (`plat_clip_data`), 1 request failed, 2 we lost ownership.
- Button numbers: 1 left, 2 middle, 3 right, 8/9 back/forward. Buttons 4-7 never surface as BUTTON.

## Keyboard
- Keymap from the server via xkbcommon-x11 (`xkb_x11_keymap_new_from_device`); reloaded on XKB NewKeyboardNotify/MapNotify (emits PLAT_EV_KEYMAP). The xkb_state is re-synchronised from each event's core `state` word (mods = state&0xff, group = bits 13-14), so translation is a pure function of (keycode, state) and works for replayed logs with no X server.
- Dead keys/compose: `xkb_compose` from the locale (LC_ALL/LC_CTYPE/LANG, else C). A dead key or compose prefix is swallowed; the final key delivers the composed keysym+text; a cancelling key is consumed (Xlib/GTK behaviour). Tested with an in-memory compose table (`<dead_acute> <e>` = e-acute, `<dead_acute> <space>` = acute, cancel resets).
- Repeat is ours. XKB per-client DETECTABLE_AUTO_REPEAT is requested so the server stops sending release+press pairs; server repeat presses (press of an already-down key) are dropped. Our repeat: `plat_set_repeat(delay_ms, rate_hz)`, default 400 ms / 30 Hz, one timerfd (CLOCK_MONOTONIC, absolute deadline) in the poll loop, zero idle wakeups when nothing is held. Only the newest pressed key repeats; keys with `xkb_keymap_key_repeats == 0` (modifiers) do not; release of that key, focus change, compose start or keymap reload cancels. Catch-up: up to 2 missed intervals are replayed, a longer stall skips ahead (no bursts). Focus in/out clears the held-key set (releases while unfocused are never seen).
- Gap: if the server refuses detectable autorepeat (ancient), repeats arrive as release+press pairs and are not de-duplicated. Not seen anywhere modern.
- Gap: group switching is honoured through the event state word only; no per-layout indicator event.

## T0 from the X timestamp
X event time is 32-bit ms since server start (wraps after 49.7 days; modern Xorg takes it from CLOCK_MONOTONIC but we do not rely on that). `x11_clock_map` keeps a reference pair (X ms, our ns) and maps `t0 = ref_ns + (int32)(ms - ref_ms) * 1e6`, wrap-safe. A physical event is never in the future, so an event that would map after `now` proves our offset carried latency: the reference is rebased to that event (the estimate converges to the minimum observed latency). More than 5 s of apparent age resyncs to now. Result: `t0_ns` is the best estimate of when the key physically reached X, accurate to the 1 ms X time resolution minus residual latency in the first event, never later than ingestion. Recorded as trace T0 (frame_id 0) for key presses and repeats (repeat t0 = timer read time). Input-to-photon therefore includes X-server/WM delay that a plain read-time stamp would hide. This makes G1 slightly pessimistic by design. `tools/evtrace` (evdev, EVIOCSCLOCKID) not written: /dev/input/event* is root:input and this user is not in group input, so it could not be run or verified here.

## XInput 2: option (b), generic xcb, hand-built
No `xcb/xinput.h` and no dev symlink exist and nothing may be installed, so `xi2.c` builds the requests (QueryVersion 2.1, QueryDevice(all), SelectEvents for XI_DeviceChanged + XI_Motion on all master devices) and decodes `GenericEvent` bytes itself, from the protocol spec. No dlopen, no new libraries. Sent with `xcb_send_request` (extension opcode from `xcb_query_extension`). Catch worth remembering: libxcb inserts a 4-byte `full_sequence` after byte 32 of every GE event, so `xi2_decode(..., xcb_layout=true)` shifts offsets >= 32; found live, covered by a test.
- Scroll classes (type 3) from QueryDevice give (source device, valuator number, vertical/horizontal, increment); XI_Motion valuator values are accumulators, so delta = (v - last) / increment, in 1/256 notch units. History resets on DeviceChanged (and the table is re-queried). Valuators 0/1 present = pointer motion; scroll-only events produce WHEEL only.
- When XI2 is active core MotionNotify is ignored (XI supplies it). Core button 4-7: dropped if within 2 ms of an XI2 scroll event (those are the server's emulated buttons for the same motion), otherwise treated as a legacy wheel step. That 2 ms rule is a heuristic (E): verified live only for the legacy path (xdotool click 4/5 on the XTEST device, no scroll class); a real touchpad/wheel emitting both was not available to a script, so the de-dup is untested on hardware.
- Fallback: no XI2 or version < 2.1 = core buttons only (`plat.core_wheel`).
- Unfocused-window motion/XI selection is per window; only our window is selected.

## Clipboard
`clip.c`. PRIMARY and CLIPBOARD as UTF8_STRING. Owning: `plat_clip_set` copies the bytes (malloc), sets ownership (our last server timestamp; retried with CurrentTime if the server refused), serves SelectionRequest for TARGETS, TIMESTAMP, UTF8_STRING, text/plain;charset=utf-8, STRING (UTF-8 to latin-1, `?` for unrepresentable); anything else is refused with property None. SelectionClear frees the buffer and raises CLIPBOARD code 2. Requesting: `plat_clip_request` sends ConvertSelection and returns; SelectionNotify reads and deletes the property, stores a copy (malloc, replaced per arrival), raises CLIPBOARD code 0/1; UTF8_STRING and STRING replies accepted. Requests for a selection we own are answered locally on the next loop turn. Allocation is limited to these buffers; none of it is on the typing path.
- Gaps: INCR (large transfers) is not implemented either way: we refuse to serve data larger than one X request (BIG-REQUESTS makes that about 16 MB; a 1 MiB self round trip passes), and an INCR reply from another client is reported as failure (code 1). MULTIPLE target not served. No request timeout (caller should time out a pending request). Clipboard manager handoff on exit (SAVE_TARGETS) not done.

## Law 2 and numbers
Key translate+compose+repeat+wheel+queue made 0 allocations in a counted loop (release build; under ASan the guard is inactive and the test says so). Bench `x11_bench`: key press translation p50 510 ns, p99 575 ns (M)[bat: Discharging], machine loaded (load avg 3.4), includes one clock read; tracked, no gate. Startup cost of the added setup (xkb extension, keymap fetch, XI2 queries, atoms) was not re-measured here; P2.1's 1 ms main-to-map figure no longer holds as is and should be re-taken by the owner of P2.1/startup.
