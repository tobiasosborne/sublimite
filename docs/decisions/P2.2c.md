# P2.2c: drain XCB before sleeping (edit-e6x.12)

Addresses finding #1 in `docs/reviews/session3-typing-path.md`. A blocking
reply wait can read unrelated events into libxcb's internal queue and consume
all socket readiness. Polling the fd alone then strands input until another
event or timer wakes the loop. G1 in `perf/01-perf-target.md` measures ingress
through submission, so this wait cannot be hidden by moving an ingestion stamp.

## Loop invariant

`drain()` reaches quiescence across XCB's event queue, the socket, clipboard
replies, and the platform event ring. It checks `xcb_poll_for_queued_event`
before `xcb_poll_for_event`, repeats after dispatch callbacks and each queued
`on_event`, and rechecks queued events after nonblocking reply polling (which
can itself read events). Blink and work callbacks return through the same drain.
The loop also drains at entry, before every `poll`, and after fd handling. Quit
and connection-error checks precede sleeping. No new allocation is introduced
in input translation, repeat, queue handling or loop bookkeeping.

## Clipboard requests and replies

`plat_clip_set` copies the data, sends SetSelectionOwner and GetSelectionOwner,
stores the cookie in fixed per-selection state, flushes, and returns. `PLAT_OK`
now means the request was queued; ownership confirmation runs from the loop via
`xcb_poll_for_reply`. A failed timestamped claim retries with CurrentTime, as
before. Final failure frees the buffer and emits CLIPBOARD code 2 (ownership
unavailable). Success emits no extra event. Local pastes during confirmation
are counted and deferred until completion, then each uses the confirmed local
buffer or requests the actual owner. A saturated counter rejects another
request rather than wrapping; repeated requests retain separate completion
events. Superseding a claim discards the old reply cookie.

SelectionNotify similarly sends GetProperty and stores its cookie; the loop
reads the reply and emits the existing CLIPBOARD data/failure event. Superseding
notifications discard prior property replies, including when the replacement
notification reports failure. Shutdown discards outstanding cookies. Clipboard
buffer allocation remains confined to clipboard operations. BIG-REQUESTS maximum
request length is cached during initialization, avoiding lazy negotiation while
serving SelectionRequest.

Tests requesting from a separate connection must establish that the ownership
request reached the server before asking that other connection to paste. The
live test uses a server barrier and pumps confirmation for this ordering.

## Remaining blocking waits

Initialization still waits for atoms, extension/version/device replies, keyboard
setup, and BIG-REQUESTS negotiation. The loop-entry drain handles events read by
these waits. Runtime XKB MapNotify/NewKeyboardNotify still reloads the keymap
through `xkb_x11_keymap_new_from_device`, whose synchronous request protocol is
owned by xkbcommon-x11. XI_DeviceChanged still runs the synchronous QueryDevice
rescan through `xi_send`/`xcb_wait_for_reply`. These uncommon dispatch operations
can delay the UI for their round trip; returning to the drain prevents them
from leaving buffered events behind a sleeping poll. Splitting keymap loading
or device rescanning into new state machines is outside this bead. Application
callbacks may also perform their own reply waits; the loop must remain correct
when they do. `xcb_flush` still has normal transport backpressure semantics.

## Regression and verification

`tests/x11_stall_test.c` skips cleanly when DISPLAY is unset or empty. It uses an
unmapped window with repeat and blink disabled for the key regression. A peer
connection grabs the server, acknowledges the grab, then injects synthetic key
press/release and a WM_DELETE_WINDOW ClientMessage while the callback waits for
an input-focus reply. A peer barrier orders those events before ungrabbing and
releasing the reply. No peer activity follows the ungrab. The callback verifies
that the connection fd is no longer readable; the events must therefore be
delivered from XCB's internal queue. The delivery budget is 5 ms (G)[AC] after
the wait returns, with an 80 ms (G)[AC] run watchdog. This is a regression
budget, not proof of end-to-end G1.

Additional cases exercise a direct dispatch callback, blink/work callbacks,
events queued before loop entry, and clipboard setting while the server is
grabbed. Clipboard setting must return before the peer releases its grab; a
bounded pipe wait releases the server even if a synchronous implementation
regresses. The clipboard live test also checks superseded owner cookies, the
stale-timestamp fallback, repeated deferred local pastes, and remote paste of replacement
data.
