# P1.8d — selective mailbox receive and atomic batch enqueue

Scope: edit-4w1.51 (lineidx review §13) and edit-e6x.25 (raster review §4),
handled by one worker. P1.8c's bounded drains, reservation policy, nonwrapping
identities, and UI serialization remain the foundation. `work.h` changes are
additions; existing signatures, members, message size and callers remain valid.
No frozen header, Makefile, benchmark or fuzzer source changes.

## Selective receive and dispatch

`work_mailbox_receive` and `work_mailbox_receive_bounded` select the complete
identity `(slot, epoch, application generation)`. Work validates cancellation
before invoking any receiver. A foreign live message stays in its original
worker ring with its payload and pending-slot reservation intact. A UI-only
hole bitmap records messages consumed behind a foreign head. Only contiguous
consumed positions release ring capacity; clearing their bitmap precedes the
head release store. The producer still uses the original tail release/head
acquire protocol, and never touches the bitmap.

Each submission has UI-only scan cursors for its worker mailboxes. Foreign
messages and existing holes count against the examined-message budget; slices
resume past foreign prefixes. Changing the requested generation resets these
cursors, so an earlier scan for a different generation cannot reorder matching
messages. Stale messages may be discarded by any receive. A receive scans a
tail snapshot, rather than chasing a producer indefinitely. Both receive and
ordinary drain use the same callback/reentrancy guard, hold the pending lease
through callback return, observe the deadline between callbacks, and re-arm
eventfd while backlog remains. Per-worker message order is preserved for each
selector and for retained foreign traffic; there is no cross-worker total order.
When a mailbox's head counter wraps, work resets that mailbox's cursors for
every slot. A selector dormant for an entire counter cycle therefore cannot
alias a new position in the middle of a result sequence. The active receive
uses its current cursor and snapshot end, including after such a reset.

`work_mailbox_bind` optionally registers a UI handler for an identity and its
job generation. An ordinary shared-pool drain dispatches a matching validated
message to that handler instead of its fallback callback. A selective receive
uses the same handler. This is necessary for existing editor, test, fuzz and
bench callers that pump the pool before polling lineidx; a selective API alone
would let those callers consume the only result notification. Binding happens
after submit and before UI pumping. Worker publication before binding is safe.
Unbinding is identity/generation checked, so an old lease cannot erase a new
slot owner's receiver. Receivers are removed before their UI state is freed.

Selective receive deliberately retains foreign head ownership rather than
moving or duplicating foreign messages into another queue. Consequently a
client cannot indefinitely ignore other clients while expecting its producer
to progress through a full shared ring. The shared dispatcher must still run.
This is fixed-capacity backpressure, not lost result delivery.

## Physical lease acknowledgement and lineidx adoption

`work_handle_finished` replaces lineidx's direct slot/busy/epoch observations
and private `fn_done`. Work release-publishes the submitted identity after the
job function returns, or after queued cancellation/shutdown removes it. The UI
acquires that acknowledgement. P1.8c retires slots before epoch wrap, so a
monotonic completed-identity comparison remains valid through reuse. Logical
cancellation of a running job does not acknowledge completion. The pool
lifetime restriction on handles still applies.

Lineidx's result array is now ordinary immutable result storage, not a private
atomic transport. The worker seals ranges and publishes their offsets through
work messages. Only the validated receiver reads a sealed range and updates
the UI index; poll has no independent result/prefix acquire path. Each array
entry is written at most once by the worker. Work's mailbox acquire publishes
those writes to the receiver. The source and result storage remain owned until
physical completion; cancellation unbinds the receiver before reclamation,
so stale offset-only messages cannot access freed storage. Publication retries
with cancellation checks when the mailbox is full. No successful result range
is silently dropped. Scratch allocation stays on the existing open/build path;
poll, adoption, receive and cancellation allocate nothing.

One sealed range contains at most (G) 16 chunks; default receive slices retain
the work message-count/deadline limits. Existing metadata/query maintenance and
fragmented-source cancellation limits belong to the separate lineidx scope.

## Atomic batch enqueue and raster adoption

`work_submit_batch(pool, jobs, count, handles)` performs validation and a dry
slot selection under the queue mutex before mutating any slot or queue. Busy
leases, unread messages, retired identities, unavailable worker classes, and
queue limits participate in refusal. Mixed-class batches reserve bulk's
narrower shared prefix first, then raster's preferred reserved suffix/shared
capacity. Fixed stack scratch holds the selection; there is no allocation.

After successful selection, work initializes every immutable job and output
handle, appends the entire batch in input FIFO order within each class, and
wakes the affected workers before unlocking. No worker can dequeue a partial
batch. Failure leaves jobs, epochs, busy reservations, queues and output
handles unchanged. Empty batches succeed without accessing arrays or pool.
The single-job API delegates to this implementation while preserving its
existing class interpretation and invalid-handle failure behavior.

Raster initializes all owned strip-job inputs, then submits them in one batch.
Capacity refusal clears UI pending state and returns with no owned worker lease,
so there is no cancellation loop, sleep, or waiting rollback. Retrying submit
can safely reuse the snapshot. Fence submission remains the existing separate
single-job operation. Adoption changes in raster are limited to this submit
path and its ownership comment.
