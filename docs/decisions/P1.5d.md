# P1.5d — undo review fixes (edit-4w1.35 and edit-4w1.26)

This decision supersedes P1.5's pool, eviction, capture-capacity and replay-API
choices. It addresses findings 2–8 of `docs/reviews/P1.5-1.md`. Finding 1 remains
blocked on the frozen piece interface, under the explicit exception in the bead.
No piece/base/build files or frozen headers were changed.

## piece.h amendment proposal

Proposed addition to `src/piece/piece.h` (proposal only; **not implemented**):

```c
typedef struct piece_checkpoint piece_checkpoint;
int piece_checkpoint_begin(piece_tree *t, piece_checkpoint **out);
void piece_checkpoint_commit(piece_checkpoint *checkpoint);
void piece_checkpoint_abort(piece_checkpoint *checkpoint);
```

Semantics:

- UI-thread ownership; at most one active checkpoint per tree. The tree must
  outlive the checkpoint. Both void functions consume it exactly once.
- `begin` returns PIECE_OK and a checkpoint, or PIECE_ERR_NOMEM/PIECE_ERR_RANGE
  with `*out == NULL` and unchanged tree content. It may reserve memory through
  the existing tree allocator. A NULL argument or nested begin is RANGE.
- `commit` preserves current content and ends the transaction. It allocates
  nothing and cannot fail.
- `abort` restores the exact pre-begin bytes, length, line counts, piece counts,
  root and query/coalescing state. It allocates nothing and cannot fail, even
  when **every subsequent allocator request returns NULL**. Existing snapshots
  and refs made before begin remain valid. Ownership/references must be restored
  without consulting an allocator for new storage.
- Refs first produced inside an aborted transaction are unpublished transaction
  results; the caller discards them. The amendment must state this exception
  explicitly. Any snapshot of intermediate content must retain its own required
  add storage. Unneeded transaction-only add bytes and retained reservation
  memory must remain included in G10f and be reclaimable; repeated aborts must
  not introduce unbounded hidden retention.

A persistent-root checkpoint can save the tree's root and control metadata and
hold ownership while subsequent edits copy paths. Abort can transfer that saved
ownership back without allocating. The piece implementer must settle add-tail
and intermediate-snapshot handling as part of the exact contract above.

Why an undo-only fix cannot work: `undo_init` receives an opaque existing tree,
not its allocator or reservation handles. Undo's pool/arena cannot satisfy
requests made through that tree's private allocator. The only byte-changing
piece calls (`piece_insert`, `piece_delete`, `piece_insert_ref`) may fail with
NOMEM, including the inverse of an already successful replay operation. A
persistent failing allocator can reject the second forward operation and every
rollback operation. Warming the current kernel is no guarantee in piece.h;
private free pools may be trimmed, shared paths may require new copies, and
bulk/ref flattening may need add storage. A snapshot can read the prior bytes
but cannot restore the existing tree. Replacing `u->tree` with a clone would
leave callers' existing tree pointers changed/incorrect and requires a second
storage budget. None of these operations gives a no-fail restore primitive.

With the amendment, undo would begin one checkpoint per group, reserve/stage
capture bookkeeping before mutation, and commit both tree and log only at the
boundary. On failure it would abort the tree and restore staged cursor/record
metadata from undo-owned scratch. Previously completed groups in a batch would
remain completed. This needs a subsequent implementation bead after consultant
approval; the proposal is not an atomicity fix by itself.

`review_1` remains compiled and skipped by default, with a source comment naming
this proposal. `UNDO_TEST_REQUIRE_ATOMIC_GROUP=1 ./build/tests/undo_test 1`
opts into the intentionally red assertion. Normal `make check` prints SKIP. The
current implementation still changes the tree on a successful prefix followed
by failure; a borrowed pre-group snapshot protects rendering/saving, but does
**not** restore that tree or resolve the blocker.

## Capture capacity (finding 2)

Insert admission reserves one slot. Delete admission reserves eight; unknown
first-undo capture reserves seven because the existing slot supplies span zero.
Editing can admit at most `max_records + 8` active span records, including an
open group. Initialization lazily maps eight times that capacity. Every admitted
unknown record can therefore expand into its worst-case eight spans inside a
protected group. No group-size scan or allocation is added to the input path.

Retired slots are reclaimed before each edit and each replay mutation, at a
rate of at most sixteen per operation. New capture needs at most seven slots,
so outstanding retirement cannot consume the expansion reserve indefinitely.
If fewer retired slots exist, all are reclaimed and the original worst-case
active-record bound applies. Virtual capacity is constrained to the 30-bit link
range with overflow checks; untouched virtual pages are not a physical charge.

The reviewed capacity-12 fragmentation script and capacity-1 nine-insert
admission script pass. Eight-span capture also runs with an operation budget
of one, reporting eight span records and one piece operation.

## Packed committed storage and bounded eviction (findings 3–4)

The base pool owns the lazy mapping; undo manages its occupied slots as a packed
array. Reclaiming a record moves the last occupied record into the hole and
repairs its neighbors, root/cursor/retirement handles and group boundary indexes
in constant work. Scratch is a suffix and can be popped without relocation.
Entire unused tail pages receive MADV_DONTNEED. No separate page directory,
occupancy bitmap or persistent free-list pages consume unreported memory.
Failed madvise leaves the conservative committed charge intact.

Each 64 B span record still holds two 16 B state blobs. Only first.before and
last.after are boundary states that replay returns. In a multi-record group,
first.after instead indexes last/count, and last.before indexes first. This
supports constant-time whole-group detach while preserving both caller states;
a one-record group needs no index and keeps both states. These are private
fields and no blob is interpreted as a caller state after being repurposed.

Redo invalidation detaches the entire suffix in constant time. Cap trimming
visits at most sixteen group boundaries per trim and detaches complete groups
only. Editing/configuration invokes trim once; replay trims at each completed
group within its operation budget. A
very large cap reduction can discard additional oldest closed history to keep
that call bounded. An open explicit suffix is protected. Edits reclaim at most
sixteen records, regardless of redo length or automatic-burst size. Discarded
slots remain on a retired chain until later edits or `undo_maintain` reclaim
them. Callers can schedule `undo_maintain(log, 16)` between input checks. Explicit
`undo_clear` resets the mapping's occupied prefix and decommits its touched
pages, without a per-record walk.

`undo_stats` distinguishes active `records`, `retired_records`, occupied
`live_bytes`, conservative **committed_bytes** and virtual **reserved_bytes**.
All owned retired storage remains charged; a cap change does not promise that
all physical bytes disappear synchronously. Once maintenance drains, packed
committed storage is exactly 64 B per remaining span plus less than one page
of rounding. Clearing a full 100k history leaves zero resident undo pages in
the Linux mincore regression. Half-history reclamation verifies packed storage,
byte lengths and both cursor states after relocating live boundary records.

The benchmark now meters all live piece allocator bytes plus committed undo
pages, including retirement. The edit charge is bounded by **(G)**
`96*pieces + 64*(active + retired undo spans) + ceil(1.25*(typed + deleted-original bytes))`
plus live snapshot path copies. The frozen piece.h initial/fixed allowance
(64 KiB + 4 KiB, plus original-copy charge) and undo's less-than-one-page
rounding are explicit fixed allowances, not hidden edit capacity. The bench
checks combined ownership before/after replay and throughout cap-reduction
maintenance, rather than treating `live_bytes == 64*active` as a memory gate.
No current fixture has deleted-original bytes or a snapshot during its timed
10k single-record groups; the unit suite separately covers both.

## Sliced replay (finding 5)

`undo_undo_slice` / `undo_redo_slice` accept a piece-operation budget and an
absolute CLOCK_MONOTONIC deadline. UNDO_MORE is a normal yield. Each call reports
its own successful prefix and completed-group state; callers subtract completed
groups from their remaining batch, merge dirty intervals and render once at the
end. Legacy undo/redo entry points remain available with unlimited budgets.

A multi-record group takes a pre-group snapshot before its first mutation and
holds it across MORE/NOMEM until completion, clear or destroy.
`undo_replay_snapshot` borrows that view for correct rendering/saving while the
mutable tree is intermediate. Edits, opposite replay and cap changes are BUSY
while partial. The snapshot is not historical undo storage and not rollback.
Normal groups of one record need no snapshot.

Deadlines are checked before every piece mutation, not only group boundaries.
Capture can expand a record into eight spans in one atomic piece operation;
`change.operations` reports work separately from `change.records`. The frozen
API cannot preempt a single costly piece mutation or snapshot acquisition.
The caller must still budget those dependency costs for the UI slice; the
module now yields within an arbitrarily long group between operations.

## Failure/fuzz coverage (finding 8)

Tests cover transient and persistent allocation failures, repeated retries in
both directions, mixed groups, exact state/dirty reporting after a batch's
completed group, physical admission exhaustion, eight-span capture, sliced
state visibility, deadline yields, and cap/clear/decommit behavior.

The fuzzer uses a small physical admission capacity (32) in narrow mode, handles
NOMEM without changing its independent byte/history model, and injects transient
or persistent piece allocation failures during undo and redo. Replay uses small
operation slices; every prefix checks dirty containment, completed state and
pre-group snapshot bytes. Persistent failures retry repeatedly with unchanged
bytes. A varied-noise version of the capacity-12 fragmentation script exercises
expansion at physical/logical pressure. Wide mode retains its larger capacity
for arbitrary multi-span deletes. Ownership checks include retired records and
committed page rounding.
