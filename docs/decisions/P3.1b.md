## Implementation and decisions

- A caller reserves one line's checkpoint table from `edit_arena` at open/init
  time. `layout_checkpoint_request` retains a caller-provided immutable
  snapshot and submits a WORK_BULK job. It builds the line lazily on demand,
  using only piece.h; it also finds the line end so layout never scans the
  unused tail after adoption. The mailbox router calls
  `layout_checkpoint_event`, which adopts count/end/columns on UI. Then call
  `layout_begin` for a full new frame (previous approximate rows may have had
  unknown starts). No snapshot creation or allocation is hidden in layout_run.
- Checkpoints target 4096-byte intervals but restart at genuine cluster
  boundaries, the first boundary after an interval. A giant cluster can span
  multiple intervals; its internal bytes are not independent restart points.
  Search is binary by column. Tabs use the same column modulus as UI; CR before
  LF contributes zero. A source identity and tab width prevent cache reuse
  across sources/configurations.
- The worker writes only the unpublished suffix of a fixed table. UI reads
  the immutable valid prefix. Mailbox release/acquire publishes the suffix;
  UI changes its visible count. An edit truncates at the first checkpoint
  whose byte is >= the edit point, retaining strictly earlier checkpoints.
  Edits before the cached line invalidate it completely. A generation rejects
  an old snapshot's result. Rebuild resumes at the last retained checkpoint.
  The caller must invalidate every mutation of the source, including while
  detached, and must route completion messages; do not externally cancel the
  job. Pool shutdown joins it before freeing the store. One job per store.
- One store caches one long line. More stores can be reserved by a caller,
  but a layout attaches one at a time. Whole-line publication was chosen so
  one message carries both exact columns and the next row's start; incremental
  region publication without a line-end index would still require a UI tail
  scan. Scheduling and cache selection belong to P3.2/P3.3 callers.
- Without a published index, a known final long line jumps to a byte-position
  estimate immediately. Other lines first establish a 64 KiB prefix, so a
  short line in a large file is never mistaken for a long line. Unindexed
  tail work stops at 64 KiB; unknown subsequent rows remain blank until a full
  re-layout after publication. `layout_approximate` stays true. UI run calls
  also have a 64 KiB consumed-byte budget (+ at most 3 UTF-8 bytes), and a
  cluster step is at most 4096 bytes (+3). Source reads use 16 KiB windows;
  counters report both consumed/scanned bytes and physical source-read bytes.
- P3.1's hscroll clamp is deliberately superseded: the uint32 viewport offset
  is kept, short lines are exact at any offset, and approximation now means
  unavailable long-line columns/rows or oversized glyph composition. All
  glyph identities, wide edges, tabs, cursor/selection, gutter, dirty-strip
  and row-used decisions otherwise remain.
- `utf8_cluster_step` carries segmentation and width across refills and
  yields, instead of making synthetic boundaries at the old window edge.
  A <=16 KiB cluster that spans windows is copied into fixed scratch and
  reaches the callback whole. Larger visible clusters retain exact column
  width and segmentation, but draw '?' with approximation flagged. This
  is an explicit composition limit, not an artificial grapheme break.
  Arbitrarily long visible clusters remain TRACK for total completion time;
  their per-call work is bounded. A checkpoint cannot make rasterising an
  unbounded grapheme a 150 us operation with the frozen contiguous callback.
- A 512-entry, four-way bounded memo caches segmentation and width of <=28 B
  clusters plus their following unit. Invalid following units require four
  validation bytes. Keys compare bytes, not hashes; there is no correctness
  dependence on collisions. Entries persist across edits because the complete
  context key is immutable. Glyph callbacks/atlas slots are not cached.
  Invalid bytes bypass the Unicode tables. Offscreen glyph callbacks are
  omitted. This reduces table calls while preserving callback identity checks.

### Memory (E, arithmetic; allocation sizes measured below)

One table = `16 * (floor(max_line_bytes / 4096) + 2)` bytes, no double bank:
3.906 MB per decimal GB, 4,194,336 B for the 1 GiB fixture (M)[bat], including
32 B guards. `sizeof(layout)` = 53,568 B (M)[bat], including 20,480 B memo and
two 16 KiB byte buffers. The mailbox payload is 40 B inside work_msg's 48 B.

G10 A is 87 MB (G). Adding the 4.194 MB table, 0.054 MB layout state, and the
2.49 MB/GB kernel/index allowance to the 78.4 MB handoff estimate gives
85.14 MB (E), within 87 MB. This is accounting, not an observed whole-app
RSS/owned-memory peak. The app uses its existing work pool. Two full banks
would make the same estimate 89.33 MB, so were rejected. The store has a
fixed caller capacity; exhaustion publishes only a partial index and retains
approximation rather than allocating. Large snapshots/allocator overhead of
the P1.3 stub are not charged as if it were the synthesised persistent kernel.

### 6. Decisions

Preserve the existing renderer/grid contract, replace clamping with explicit
bounded estimates, reserve one table, publish immutable suffixes through work,
resume segmentation/width without inventing cluster boundaries, memo exact
contexts while keeping glyph callbacks live. Details/alternatives above.

If the quiet [AC] rerun still misses, my consultant proposal is to keep the
150/150 us ASCII/log/warm-indexed-long-line gate and evaluate separate
**uncached Unicode 400/450 us** and **malformed 225/250 us** p50/p99 limits

limits derived from this session's loaded battery misses. Keep warm memoised
Unicode at the original 150 us target if its quiet rerun passes.

Why consider a separate uncached gate: every miss must establish a genuine
grapheme boundary and its cluster width. The manual replay identifies both
segmentation and width/table work as dominant, and memoisation can only remove
repeated exact contexts (75.86% / 70.98% here), not arbitrary fresh clusters.
Skipping the tables or treating each code point as an independent width would
break the tested Prepend/Hangul/Indic/emoji/combining rules. A stronger,
scalar-property-level optimisation belongs in the read-only utf8 module.
This is an engineering argument for a scoped gate or a utf8 follow-up, not a
claim that no correct future implementation can achieve 150 us. The consultant
can reject the proposal and request that utf8 optimisation; the remaining
miss counts and replay numbers make that decision reviewable.
