# P2.2h clipboard bulk work off the UI thread (bead edit-e6x.24, finishes P2.2d #13)

Files: src/x11/clip.c, src/x11/clip.h (compatible additions only), tests/x11_clip_test.c.

## What moved
- Receive path: growth by realloc, the copy into the paste buffer and Latin-1 -> UTF-8 conversion now run on a
  src/work bulk worker. The UI thread decodes the reply header, plans and charges capacity, and submits one job per
  property reply; the reply itself (malloc'd by libxcb) is handed to the job and freed by the worker.
- End of a receive: a close job (shrink to length, or free on failure) runs on the same worker after the chunks.
- Freeing a blob of 1 MiB or more (replaced paste buffer, replaced owned selection, serve snapshot) is a free job.
- plat_clip_set still copies synchronously (the caller's buffer is borrowed; the copy cannot be deferred without a
  lifetime contract). New zero-copy route for large owners: x11_clip_buf_new / _data / _free / x11_clip_set_buf. The
  producer fills the buffer on any thread, the UI thread adopts it (no byte moves; accounted and budget-checked).

## Mechanism
- The pool is private to clip (calloc'd and started on first use, joined by x11_clip_destroy). x11.c's runtime pool is not
  shared because work_mailbox_drain delivers every message to one callback and would eat keyboard-worker messages.
- A clip_sink (buffer, length, failed) belongs to the worker while jobs of that receive are in flight. The UI thread reads
  it only after the completion message of its last job (mailbox release/acquire gives the ordering). The UI-side mailbox
  handler is bookkeeping only; state changes (finish, reject, deliver) happen in x11_clip_poll in the old order, so the
  "deliver queued completions before replacing the paste buffer" rule (P2.2d #4) is untouched. The mailbox is only drained
  after that rule's early return, i.e. never while input is queued.
- Backpressure: 8 chunk slots in flight (about 2 MiB of replies); with none free the UI leaves the next reply in the xcb
  queue and retries on the next wake. One reserved close slot per selection; frees use the chunk slots or free inline.
- Wake: x11.c does not poll the pool's eventfd (not edited), so x11_clip_deadline returns now+1 ms while any job is out.
  Idle clipboard = no wake, as before. Proposal for x11.c below.

## Memory accounting (P2.2d #14), still exact
- mem counts capacity. The UI thread charges the full new capacity (same doubling and budget rule as before) before the
  worker grows the buffer, so mem never under-counts. Chunk size is a worst case (2x for Latin-1); the worker enforces
  the exact 64 MiB limit and reports failure. The close job reports the final capacity and mem drops to it; a discard drops
  everything. A deferred free keeps its bytes in mem until the worker reports it. Quiescence (x11_clip_busy == 0, which now
  counts pending frees) implies mem == live bytes. make_room (plat_clip_set / x11_clip_set_buf) drains finished frees and,
  only at the budget limit, waits at most 50 ms for pending ones, so a replace never fails because a free is in flight.
- Cost: a Latin-1 receive is charged 2x until its close job shrinks it; a failed one is released when the free reports.

## Instrumentation (new, clip.h)
- x11_clip_ui_bytes(): bulk bytes copied/converted/realloc-moved by clip code on the calling thread.
- x11_clip_max_poll_ns(): longest x11_clip_poll / x11_clip_event call, wall and thread-CPU (CPU is preemption-free; wall
  on a loaded box is dominated by scheduling, see the test log lines).

## Not fixed / proposals
- plat_clip_set copies up to 64 MiB on the caller (documented; the editor should publish big selections with
  x11_clip_set_buf, building the buffer on a worker from a piece-tree snapshot).
- Serving still converts UTF-8 -> Latin-1 per 256 KiB chunk on the UI thread (bounded by P2.2d's 1 MiB slice budget).
- x11.c proposal: add work-pool eventfd of clip to the poll set (an x11_clip_wake_fd accessor is the one-line addition) so the
  1 ms polling wake can go away.
- The 64 MiB receive still reads each 256 KiB reply from the socket inside libxcb on the UI thread (memcpy by the library).
