# edit-177r.2 — W0.2: `os.h` spec, Linux implementation, conformance suite

Frozen: `src/os/os.h` and `tests/os_test.c` (round 2, after the Codex review `docs/reviews/edit-177r.2.md`; §10 lists each finding and what changed). Linux implementation: `src/os/os_posix.c`, wrapped whole in `#if !defined(_WIN32)`. W0.3 writes `src/os/os_win.c` against the same header and runs the same suite as a Windows executable. No module was migrated in this bead.

Free to vary in W0.3: the private struct fields under `#if defined(_WIN32)` in `os.h` (callers never touch fields), and how each Windows entry is built. Not free: any signature, any documented semantic, and the suite. A change to either goes through a new bead (P1.3 rule).

### 1.2 What is deliberately not in `os.h`

- **An event-loop wait set.** On Windows the window message queue must be part of the one blocking wait (`MsgWaitForMultipleObjectsEx`), so the set belongs to the platform layer. `os.h` only provides objects the loop can wait on (`os_wake` and the native accessors) plus one short single-handle wait (`os_wake_wait`) for the existing `poll(&fd, 1, 1)` sites.
- **Timers.** The only timerfd outside the platform layers is in ipc, which is rewritten for named pipes anyway. Blink and scroll timers are the platform loop's timeout.
- **Signals.** The only portable need, SIGBUS recovery, is the fault service. Close signals are platform input.
- **Sockets, spawning helpers, dlopen, SysV shm, xattrs, inotify:** each is replaced wholesale on Windows (rows above), so a portable wrapper would carry one implementation only.


## 2. Contract choices

1. **Errors.** Every entry returns `os_err`, a portable enum. The native code (errno / `GetLastError()`) is read with `os_native_error()` right after the call. This adds no thread-local storage: both native codes are already per-thread, and the Linux layer saves and restores errno around cleanup `close` calls so the failing call's code survives. The mapping table is in the header. `OS_E_BUSY` is the one portable spelling of "someone else holds it": a lock (EWOULDBLOCK), a sharing violation, a mapped-file refusal. Round 2 added `OS_E_INTR` (only `os_file_pwrite_once` returns it), dropped the `ERROR_IO_PENDING → OS_E_AGAIN` row (pending I/O never reaches a caller, item 9), and widened `OS_E_RANGE` to "a size or range the caller passed does not fit", which now also covers a mapping range past the end of the file (§9).
2. **UTF-8 at the API.** `OS_PATH_MAX` is 4096 bytes (P: Linux `PATH_MAX`). `OS_NAME_MAX` is 768 (P: 255 UTF-16 units × 3 bytes = 765, + NUL, rounded up). The Windows side converts on the stack (no heap), resolves a relative path against the current directory, and adds `\\?\` itself, so paths past `MAX_PATH` (P: 260 UTF-16 units) work. The suite creates one of 370 units (M).
3. **Caller-allocated handles with private fields; allocation listed per entry.** The layer allocates only in the entries the header names (round 2, finding 9). Measured with the counting guard on this build (M, `[AC, desktop Spiral]`, one call each): `os_thread_start` 1, `os_env_set` of a new variable 3, `os_dir_iter_open` 1, `os_file_to_stdio` 1, `os_proc_spawn` 1; every other entry 0, including `os_path_canonical` (glibc's `realpath` uses a stack buffer up to its limit; the header keeps it on the "may allocate" list for longer paths), the inits and `os_fault_register`'s first call. The typing-path set (clocks, `os_thread_self`, `os_yield`, mutex and recursive-mutex lock/unlock, cond signal/broadcast, wake signal/drain, `os_file_pread`, `os_file_pwrite`, `os_file_pwrite_once`) is counted by the suite cold (first use inside the guard) and contended (a second thread hammering the same locks, a waiter parked on the condition): 0. `os_thread` stores `fn`/`arg` so the Windows trampoline needs no heap.
4. **Non-inheritable handles, full sharing on Windows.** Every open is `O_CLOEXEC` and, on Windows, uses `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`. That makes rename-over, unlink-while-open and rename of a held directory behave as on POSIX. Denying write sharing while a file is mapped (perf §2.14) stays out of the contract (§8.3). The pinning and moved-source questions this sharing raises are finding 4, backlog bead edit-pc3s; nothing here assumes an answer.
5. **`os_file_open` on a directory is `OS_E_ISDIR` on both platforms.** Linux opens a directory read-only, so the layer adds an `fstat` after `open` (one extra syscall per open; never on the typing path) to give one portable answer. Callers classify it like a non-FILE kind after a successful open (migration rule §9.1).
6. **Positioned I/O leaves the sequential position unspecified.** Windows `ReadFile` with an `OVERLAPPED` offset moves the file pointer. Today's modules never mix the two styles on one handle. Positioned calls on one handle may run concurrently (the suite runs four threads on one handle); Windows serialises them on the synchronous file object.
7. **Rename and unlink semantics are POSIX on both** (§3.2, §3.3), pinned by the suite, including replacement and removal of read-only (0444) files.
8. **Directory sync is a documented no-op on Windows** that returns `OS_OK`. This is the "provisional durability" gap perf §2.8 already states. Callers keep calling it, so Linux keeps its barrier.
9. **Transfers are complete on return** (finding 14). Every transfer has completed, or been cancelled and reaped, before its entry returns, including on error, so the caller may reuse or free the buffer at once. Windows opens every file synchronously (no `FILE_FLAG_OVERLAPPED`); if a filter or redirector still answers `ERROR_IO_PENDING`, the implementation waits (`GetOverlappedResult(..., TRUE)`) before returning. There is no completion object in the API, so there is no other correct reading.
10. **Retry policy per entry** (finding 2). `os_file_pwrite_once` makes exactly one attempt (no EINTR retry, no short-write loop, no allocation, lock or sync): it is the journal's `cache_write` call (`src/journal/journal.c:570`), whose contract (`journal.h:245`) turns EINTR into sticky IO and forbids a UI retry. The closes never retry (Linux releases the descriptor even when `close` reports EINTR). Sleep and the two waits restart with the time left. Every other entry restarts EINTR until the call completes; round 1 promised that but did not keep it in `open_anon`, `dup`, `set_mode`, the stats, `mkdir`, `unlink`, `rename`; round 2 wraps every such call in one `RETRY` macro. No entry loops on a short transfer.
11. **Timestamps are signed** (finding 23): `int64_t` ns since 1970, saturating outside ±292 years (P: 2^63 ns ÷ 3.156e16 ns per year). A native mtime of −1 s is −1,000,000,000, not 0. `(uint64_t)mtime_ns` is `file_id_from_stat`'s unsigned encoding for every time in range; journal capture's negative-mtime rejection is `mtime_ns < 0`.
12. **Two clocks for CPU budgets** (finding 7). `os_thread_cpu_ns` is accounting; `os_thread_cpu_resolution_ns` reports its step; `os_slice_ns` is the clock that ends short slices. Linux uses `CLOCK_THREAD_CPUTIME_ID` for both, exactly as lineidx does today; Windows ends slices with QPC (§3.8).

## 3. Windows design per hard family (for W0.3)

### 3.1 Directory handles without `openat`
`os_dir` is a directory `HANDLE` opened with `FILE_FLAG_BACKUP_SEMANTICS` and full sharing. `*_at` entries are handle-relative through the NT API: `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory`, and `NtSetInformationFile` `FileRenameInformationEx` (its `RootDirectory` field) and `FileDispositionInformationEx`. Win32 `SetFileInformationByHandle` documents `FILE_RENAME_INFO.RootDirectory` as unused, so it cannot do a relative rename. Handle-relative resolution keeps the P1.7c §7 property: replacing the parent path with a symlink or another directory cannot redirect a save. The suite pins this by renaming a directory while a handle is open and resolving through the handle. The alternative, keeping the path and concatenating, would lose that property, so it is not the contract. `os_dir_iter_open` opens a second handle to the same directory (relative open of an empty name) so the listing has its own cursor. The `os_dir` also holds the handle of its directory lock file (§3.4), `INVALID_HANDLE_VALUE` when unlocked.

### 3.2 Rename over open, mapped or read-only files
`FileRenameInformationEx` with `FILE_RENAME_POSIX_SEMANTICS`; for `OS_RENAME_REPLACE` also `FILE_RENAME_REPLACE_IF_EXISTS | FILE_RENAME_IGNORE_READONLY_ATTRIBUTE`. POSIX semantics need Windows 10 1709 or later (this box: 19045); the read-only flag needs a later build, (E) 1809, which W0.3 confirms. Without the read-only flag NTFS refuses to replace a `FILE_ATTRIBUTE_READONLY` target with access denied (M, Codex on native NTFS), whereas Linux replacement depends only on the directory's permissions; the suite now replaces a 0444 target that is open and mapped. Rights: the source is opened with `DELETE`; ignoring the read-only attribute needs `FILE_WRITE_ATTRIBUTES` on the replaced file, checked against its ACL. A genuine ACL refusal (no `DELETE` on source or target, no `WRITE_ATTRIBUTES`, no add-file right on the target directory) is `OS_E_ACCESS`, the code Linux gives for a directory the caller cannot write. Open handles to the replaced file keep reading its bytes; the suite checks a plain handle and a mapped view. A handle that another program opened without `FILE_SHARE_DELETE` makes the rename fail with `OS_E_BUSY`; the save layer surfaces it, it does not silently retry.

### 3.3 Unlink of open files
`FileDispositionInformationEx` with `FILE_DISPOSITION_FLAG_DELETE | POSIX_SEMANTICS | IGNORE_READONLY_ATTRIBUTE`. The name disappears at once and can be reused at once, as on POSIX. The read-only flag is ignored because POSIX unlink does not consult file permissions (the suite unlinks a 0444 file). `os_rmdir` uses the same POSIX-semantics delete on the directory (no read-only flag needed), so an `os_dir` open on it, locked or not, does not stop removal and the name goes at once.

### 3.4 Locks
**Files.** `flock` semantics: non-blocking only (every `flock` in the tree is `LOCK_NB`, M: grep), released by unlock, process death, or the **last close of the open file**. Round 2 (finding 3) fixed the ownership rule: a lock belongs to the open file, which a handle shares with its duplicates (flock's open file description; Windows' file object, which `DuplicateHandle` shares). A duplicate may unlock it; closing one of several duplicates does not release it. Linux and native NTFS both behave so (M, Codex), and the session-lease handoff depends on it: `editor_session_restore` duplicates the creator's locked descriptor and the creator closes its copy later (`src/editor/recovery.c:754`). The suite runs both close orders, unlock through a duplicate, and the handoff itself with a third handle excluded throughout. `LockFileEx` locks are mandatory byte-range locks, so W0.3 locks **one byte at an offset above any reachable file size**; the lock never covers data and other handles keep reading and writing (checked). The filesystem releases the lock at the file object's cleanup, which runs when its last handle closes. A held lock cannot change kind in place (`LockFileEx` stacks rather than converts): unlock first. No lock upgrade appears in the call sites read for this inventory; W2 checks each one as it migrates.

**Directories** (finding 5; §8.2 records the choice). A directory handle cannot be byte-locked. Round 1 locked a hidden reserved entry inside the directory; the review showed that this hides and may delete a user's file of that name, needs write permission Linux does not, and splits exclusion if the entry is replaced. Round 2 keys the lock by the directory's **identity** instead, like `flock` on the inode (`journal_retire_directory` relies on exactly that, `src/journal/retire.c:377`):
- `os_dir_try_lock` reads the directory's `FILE_ID_INFO` through its handle and opens (creating on first use) `%LOCALAPPDATA%\sublimite\dirlocks\<volume>-<index1><index0>` (hex, 16 + 32 digits), creating the `dirlocks` directory if missing.
- The lock file is opened with share `READ | WRITE` but **not** `DELETE`, so while anyone holds it open nobody can rename or delete it, and exclusion cannot split between two files. It is never deleted, so the number of lock files is the number of distinct directories ever locked: today only the journal's own profile directories (§8.2).
- The lock is `LockFileEx` on the same high byte as file locks; the handle lives in the `os_dir`, `os_dir_unlock` unlocks it, `os_dir_close` and process death close it.
- Nothing is created in the locked directory, no write permission on it is needed, `os_dir_next` hides nothing and `os_rmdir` special-cases nothing.
- A directory renamed away keeps its identity and so its lock; a new directory at the old path has a new identity and is unlocked. The suite checks both, plus a user file literally named `.sublimite-dirlock` that stays listed, untouched and blocks `os_rmdir`.
- Identity on a volume without stable 128-bit file IDs (FAT, exFAT) is the 64-bit index, which those filesystems do not keep stable across renames; the journal's profile directory lives under `%LOCALAPPDATA%` (NTFS), so this does not arise for the one caller.

### 3.5 Durability
`fsync` and `fdatasync` both become `FlushFileBuffers`; `os_dir_sync` is a no-op (§2.8).

### 3.6 Mapping and the fault service
**Mapping** (finding 27). `CreateFileMappingW(file, NULL, PAGE_READONLY, 0, 0, NULL)` (maximum size 0 = the file's current size), `VirtualAlloc2(MEM_RESERVE | MEM_RESERVE_PLACEHOLDER)` of the page-rounded extent, `MapViewOfFile3(section, process, base, offset, extent, MEM_REPLACE_PLACEHOLDER, PAGE_READONLY, NULL, 0)`. `MapViewOfFile3` takes page-protection constants, not `FILE_MAP_*` access flags (round 1 named the wrong family). `os_map.addr`/`len` are the logical view; the native extent is `len` rounded up to the page size; bytes between the end of the file and the end of its last page read zero on both platforms; `os_unmap` releases the whole extent. The suite maps at a nonzero granularity-aligned offset, with a partial last page, and at 2^32 in a sparse file. If the file is shorter than `offset + len` (it shrank after the caller sized it), the section cannot cover the range and Windows returns `OS_E_RANGE`; Linux maps it, today's call (§9.2).

**Fault service.** On Windows, shrinking a file that has a mapped view fails (`ERROR_USER_MAPPED_FILE` → `OS_E_BUSY`), so the Linux truncation fault does not arise on NTFS. `EXCEPTION_IN_PAGE_ERROR` still does on network and removable volumes, which includes the `\\wsl.localhost` share from design decision 1. The registration shape is portable: `os_fault_register(const os_map *)`.
- **Linux:** the file module's `file_bus` algorithm, keyed by `os_map`. The phases, pins and epochs are unchanged (P1.7c §§1, 2, 9). It chains to the previous SIGBUS action.
- **Windows recipe:** views live in placeholders (above). A vectored exception handler serves `EXCEPTION_IN_PAGE_ERROR` (`ExceptionInformation[1]` = address) inside a LIVE slot. It counts the epoch, then calls `UnmapViewOfFile2(MEM_PRESERVE_PLACEHOLDER)`, splits the placeholder at the faulting page (`VirtualFree(MEM_RELEASE | MEM_PRESERVE_PLACEHOLDER)`), remaps the prefix from the section with `MapViewOfFile3`, commits zero pages over the suffix (`VirtualAlloc2(MEM_REPLACE_PLACEHOLDER)`), and returns `EXCEPTION_CONTINUE_EXECUTION`. An access violation inside a slot that is mid-recovery is retried. Everything else returns `EXCEPTION_CONTINUE_SEARCH`. `os_unmap` of a recovered view releases each piece.
- **Test trigger** (finding 18): `os_fault_test_trigger(m, off)` delivers the native fault for one byte of a view through the same handler. Linux: `rt_tgsigqueueinfo` of SIGBUS with `si_code = BUS_ADRERR` and `si_addr` set, to the calling thread (a positive `si_code` may be sent to oneself); the handler runs before the syscall returns. Windows: `RaiseException(EXCEPTION_IN_PAGE_ERROR, 0, 3, {0, address, STATUS_DEVICE_DATA_ERROR})` into the vectored handler, which recovers and continues. With it the suite exercises on NTFS what only truncation exercised before: recovery, epoch counting, prefix preservation, two successive splits of one view, unmap and re-map after recovery, capacity (`OS_FAULT_SLOTS` then `OS_E_NOSPC`), and chaining of an unregistered fault (a child must die from it).
- **One installer per process** (finding 16). The service installs once (`os_once`); four threads racing the first registration at a barrier all register distinct slots and are all recovered (suite). Linux installs with a single `sigaction(SIGBUS, &new, &old)` and chains to what that call actually replaced (two immutable slots and an atomic index, so a running handler never reads a half-written struct). That makes an installer that ran *before* us compose. One that queries and installs in two steps, like `file_bus` today, can still lose this one under a concurrent first use, so the rule is structural: `file_bus` goes in the same W2 change that moves `src/file` onto `os_fault_*`, and until then no binary links both (M: `nm` over `build/sublimite`, `build/tests/*`, `build/tools/*`, `build/bench/*`: only `build/tests/os_test` defines an `os_` symbol, and it has no `file_bus`). Retirement racing a concurrent fault in the same slot is not in the suite (§6.5).

### 3.7 Wake handles
A manual-reset event. Level-triggered like eventfd under epoll, and a wakeup of `MsgWaitForMultipleObjectsEx` does not consume it. The contract makes "drain before consuming the announced state" explicit; that is how `work` uses its eventfd today (`mailbox_clear_notification` before delivering).

### 3.8 Clocks and sleep
`QueryPerformanceCounter` for `os_now_ns`. **CPU accounting** (`os_thread_cpu_ns`) is `GetThreadTimes` (kernel + user), whose value moves in scheduler-tick steps: 15.625 ms = 156,250 FILETIME units × 100 ns (M, Codex on native Windows; P: 1/64 s). `os_thread_cpu_resolution_ns` reports the step W0.3 measures at first use; the suite checks that no observed step is finer than the reported value. `QueryThreadCycleTime` scaled is not used: cycles are not a portable time unit, and Microsoft advises against converting them. **Slice deadlines** (`os_slice_ns`) use QPC on Windows: elapsed time bounds the thread's CPU time from above, so a 500,000 ns lineidx slice ends no later than on Linux, and earlier when the thread is preempted (less work per slice, never more latency). Linux keeps `CLOCK_THREAD_CPUTIME_ID` for both (M: smallest observed step 400 ns release, 500 ns sanitizer, `[AC, desktop Spiral]`, load1 9–12). The suite requires the slice clock to resolve below 500,000 ns and to advance at least as much as the CPU clock over a busy 20 ms. `os_sleep_ns` uses a high-resolution waitable timer because modules back off for as little as 50 µs (M: `src/raster/raster.c:511`).

### 3.9 Processes
**Inheritance** (finding 12). Only the three standard streams reach the child. Linux: `posix_spawn` with `posix_spawn_file_actions_addclosefrom_np(3)` (glibc 2.34+; this box 2.39), so even descriptors opened without `O_CLOEXEC` outside `os.h` (the probe: C stdio) close in the child; round 1 leaked them (red run: the `fdscan` child found the sentinel). Windows: `CreateProcessW` with `EXTENDED_STARTUPINFO_PRESENT`, a `STARTUPINFOEXW` whose `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` names only inheritable duplicates of the three standard handles, `STARTF_USESTDHANDLES`, and `bInheritHandles = TRUE`. Round 1's `bInheritHandles = FALSE` cannot hand redirected standard handles to the child at all. The suite's sentinel is a C `fopen` handle (a CRT handle is inheritable by default and lacks `FILE_SHARE_DELETE`): Linux scans the child's `/proc/self/fd`; on Windows the parent's unlink of the sentinel while a child lives would fail `OS_E_BUSY` if it leaked.
**UTF-8 argv** (finding 13). The child must receive argv byte for byte as UTF-8. `CreateProcessW` alone does not do that: an unchanged narrow `main` gets the command line converted to the ANSI code page. Every executable that uses `os.h` on Windows therefore embeds the UTF-8 activeCodePage manifest (`src/os/utf8.manifest`, Windows 10 1903+, W0.3 adds it to the link), which makes the CRT's narrow argv, `fopen` and `getenv` UTF-8. The command line is quoted by the `CommandLineToArgvW` rules; the suite re-executes itself with an empty argument, spaces, an embedded quote, one and two trailing backslashes, a backslash before a quote, leading and trailing blanks, a tab and a non-ASCII argument.
**The editor's own `main` needs the same** (W1 item, not built here): Explorer and shells pass file names with umlauts on the command line, and a narrow `main` without the manifest (or a `wmain` bridge converting `wchar_t **argv` to UTF-8) receives them lossily converted. W1 links the manifest into `sublimite.exe`.
`TerminateProcess` marks `killed` so `os_proc_wait` reports `OS_PROC_ABNORMAL`. An NTSTATUS exit code (≥ `0xC0000000`) is also `ABNORMAL`. `abort()` exits with the CRT's code 3 and is reported as `EXITED` with code 3, a documented asymmetry the tests must not rely on.

### 3.10 Kinds of reparse-backed files
Finding 8: Tobias's files live mostly on Windows drives (decision 1), where OneDrive placeholders and compact-compressed files are ordinary documents. Only **name surrogates** (`IsReparseTagNameSurrogate`: `IO_REPARSE_TAG_SYMLINK`, `IO_REPARSE_TAG_MOUNT_POINT` and other surrogate tags) are `OS_KIND_LINK`. `OS_KIND_OTHER` is reserved for objects that are not data files: `IO_REPARSE_TAG_AF_UNIX`, the WSL special-file tags (`LX_FIFO`, `LX_CHR`, `LX_BLK`), devices, named pipes. Any other tag on a non-directory (`WOF`, `DEDUP`, `CLOUD_*`, HSM tags) is `OS_KIND_FILE`. Following versus NOFOLLOW: following classifies the target; NOFOLLOW opens with `FILE_FLAG_OPEN_REPARSE_POINT`, reads `FileAttributeTagInfo`, answers `OS_E_LOOP` (open) or `OS_KIND_LINK` (stat) for a name surrogate, and for any other tag re-opens without the flag so the owning filter serves the data, checking that both opens have the same identity. The suite case `reparse` takes a fixture path from `OS_TEST_DATA_REPARSE` (W0.3 creates one with `compact /c /exe:lzx`); unset (Linux), it reports that it had none. Link fixtures for NOFOLLOW are finding 19, backlog edit-pc3s.

### 3.11 Anonymous files
Finding 15: setting POSIX disposition on the retained creation handle leaves the name in place until that handle closes (M, Codex on native NTFS). The recipe: create the data handle under a random name (`CREATE_NEW`, share R|W|D); open a second handle to that name relative to the directory with `DELETE` access; set `FileDispositionInformationEx(DELETE | POSIX_SEMANTICS)` on it; close it before returning. The data handle stays usable. A duplicate of the data handle is the same file object and is not enough. The suite lists the directory while the anonymous file is open and expects no extra entry.

## 4. What the suite pins (both platforms)

`tests/os_test.c` has 17 cases: errors, clocks, threads, wake, noalloc, files, dirs, listing, locks, map, fault, random, utf8, paths, known_dirs, reparse, proc. The driver runs **each case in its own supervised child process** (`--case=<name> <work dir>`): a case that hangs is killed after the case guard and reported (finding 25), and the fault case starts with an uninstalled service. `OS_TEST_CASE=<name>` runs one case; an unknown name exits 2, and a run with no case fails (finding 26). Each item below is checked on both platforms:
- rename NOREPLACE onto an existing name → `OS_E_EXIST`, both files intact (dir-relative and path forms);
- rename REPLACE over a target another handle holds open → OK; the handle reads the old bytes, the name the new ones; the identities show which is which; the same over a **read-only (0444)** target that is open and mapped; unlink of a 0444 file;
- rename REPLACE over a **mapped** target → the view keeps the old bytes;
- unlink of an open file → the name is gone and reusable at once; the handle still reads;
- `*_at` stays bound to the directory object after the directory is renamed;
- write-only opens write but do not read and need no read permission; a truncating open leaves the file empty at once; the stdio bridge writes through a `FILE`;
- positioned I/O at offsets beyond 2^32 in a sparse file, without wrapping onto low offsets; four threads doing positioned I/O on one handle at once;
- locks: EX excludes EX and SH between handles; SH + SH coexist; data stays readable and writable under a lock; duplicates share the lock in both close orders and may unlock it; the session-lease handoff; duplicates share the sequential position; close of the last handle releases; process death releases (child holds the lock, parent kills it);
- directory locks: the same semantics; keyed by identity (renamed-away directory stays locked, a new directory at the old path is free); a held lock adds no entry; a user entry named `.sublimite-dirlock` stays listed and untouched; an empty locked directory can be removed and its name goes at once;
- map at a nonzero aligned offset with a partial last page; misaligned offset → `OS_E_INVAL`; map + read + truncate by another handle: either `OS_OK`, after which past-EOF reads give zeros, the epoch rises and the prefix is intact, or `OS_E_BUSY` with the view intact (Windows NTFS); a range past the end of the file: `OS_OK` with recovered zeros past the end, or `OS_E_RANGE`;
- fault service through `os_fault_test_trigger`: concurrent first registration from four threads at a barrier, each recovered; recovery from the middle of a view twice (prefix intact, suffix zero, epoch +1 each); unmap and re-map after recovery read the untouched file; `OS_FAULT_SLOTS` registrations then `OS_E_NOSPC`; an unregistered fault kills a child;
- wake: starts clear, coalesces, wait does not drain, drain clears, a timeout is honoured, another thread wakes a blocked waiter;
- threads: thread IDs compared while all workers are alive at a barrier (finding 24); recursive mutex nested in four threads and released only by the last unlock;
- clocks: CPU clock advances under work and not over a 50 ms sleep; its reported resolution is not finer than observed; the slice clock resolves below lineidx's 500,000 ns and keeps up with CPU time;
- listing: no `.`/`..`, rewind repeats the listing, the directory handle stays usable during iteration;
- UTF-8: a name with Latin-1, Greek, CJK and a 4-byte emoji round-trips byte for byte through create, list, path stat, open, canonicalisation and the environment; nested Unicode directories with a full path above 260 UTF-16 units; relative paths through the current directory;
- temp/config/data directory resolution: absolute, ending in `<sep>sublimite`, `OS_E_RANGE` on a short buffer;
- processes: exit code, kill, wait timeouts, argv byte for byte (the `CommandLineToArgvW` corners and non-ASCII), no inherited handle beyond the standard streams;
- no allocation in the typing-path set (§2.3), cold and contended, under the counting guard; in a release build an inactive guard is a failure and a positive-control allocation must be seen (finding 21). Sanitizer builds compile the guard out (it is inert under ASan by design) and say so.

Platform-varying results the suite accepts, and prints so W0.3's run records them: `os_file_clone` (`OS_E_NOTSUP` on this box's filesystem), `os_file_open_anon` (`OS_OK` here), `os_file_set_sparse` (`OS_OK` here), truncate-while-mapped (`OS_OK` here, `OS_E_BUSY` expected on NTFS), map past the end of the file (`OS_OK` here, `OS_E_RANGE` on Windows).

Not testable in the portable suite, and why: EINTR on `os_file_pwrite_once` (no portable way to interrupt a regular-file write; a scratch probe interposing `pwrite` shows one attempt and `OS_E_INTR` against two attempts and `OS_OK` for `os_file_pwrite`, report §R2); NOFOLLOW/EXCL precedence on links (finding 22; needs link fixtures, which are finding 19 in backlog); forced pending I/O on Windows (W0.3 can only force it with a filter).

No fuzzer: `os` neither parses input nor mutates a data structure (law 1 asks for a fuzzer only then).

## 9. Migration rules (W0.4, W2)

Where an `os.h` outcome differs from what today's call gives the module, the migrating change applies the rule below so the module-visible outcome stays what it is today (finding 17). Each migration keeps the module's existing tests and adds the regression named here.
1. **Directory opened as a file.** `os_file_open*` returns `OS_E_ISDIR` where today's `open` succeeds and the module's `fstat` then sees a non-regular file. `src/file/file.c` (`prefix_job`, about line 733) reports `FILE_ERR_NOTREG` for that today, and `FILE_ERR_IO` only for a failed open. Rule: map `OS_E_ISDIR` from the open to `FILE_ERR_NOTREG`, exactly where `!S_ISREG` is mapped today. Regression: opening a directory through `file` still reports `FILE_ERR_NOTREG`, not `FILE_ERR_IO`. The same rule applies to every module that classifies after open (journal capture, recovery discovery, fif).
2. **Mapping a file that shrank after it was sized.** On Linux `os_map_file` is today's bare `mmap`, so the shrink race during acquisition is admitted exactly as now: the view maps, touching pages past the end faults, the registered slot recovers zeros, the epoch rises, and file reports the source changed. On Windows the same race gives `OS_E_RANGE` from `os_map_file`. Rule: file maps `OS_E_RANGE` from `os_map_file` (after a successful identity validation) to `FILE_ERR_CHANGED`. Regression: a test that shrinks the file between the size read and the map (through a hook in file's acquisition path; the migrating change adds one if none exists) yields "changed" on both platforms.
