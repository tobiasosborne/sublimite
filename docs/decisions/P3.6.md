# P3.6 — profile-guided first-frame link order (edit-zzj.7)

Recommendation: **reject adoption for now**. B reduces the executable RSS proxy
and has the lowest aggregate warm p50, but the paired launch comparison does not
establish a repeatable latency gain. It grows the current release binary. C adds
advice overhead and is dominated by B. No candidate wins clearly, so there is no
`winner.patch` and no production source or Makefile change.

All timings below are shared-box **TRACK**, not gate verdicts. This was one
interleaved series on the box as it was; there was no quiet-window wait or
benchmark repetition. The required sanitizer suite was also running during the
series. A warm limits are **25/40 ms p50/p99 (G)**. All candidates exceed those
limits in this run; the coordinator owns gate verdicts.

## Variants and common interface

`bench/linkorder_bench.c` executes every candidate through the same interface.
`tools/linkorder_bench.sh` builds independently of Makefile and fixes both
`DISPLAY` and `EDIT_DISPLAY` to `:99`, unsetting the real-display opt-in.

- **A:** original GCC release flags and original source/archive order. Its
  production `.text` was compared byte-for-byte with `make all`'s sublimite and
  matches. No section ordering, garbage collection or prefetch.
- **B:** A plus `-ffunction-sections` and GNU ld `-T order.ld`. The script starts
  from this box's default PIE linker script and puts traced function input
  sections before its normal `.text` wildcards. It includes optimized clone,
  startup/hot/unlikely section suffixes and retains every normally linked
  section. No `--gc-sections`, LTO, stripping or other optimization is mixed
  into the latency comparison. Exact-name symbol addresses in the production
  ELF are checked against the traced order.
- **C:** exactly B's order file/flags plus `madvise(MADV_WILLNEED)` at main entry.
  `dl_iterate_phdr` selects the main executable's executable `PT_LOAD`, rounds
  its bounds to pages and advises that existing mapping. No second mapping or
  explicit page-fault loop. Advice is checked by the benchmark and best effort
  in the production candidate. MAP_POPULATE was not separately tested.

Each directory contains `sublimite` with common endpoint probes and `production`
without them, generated main/X11/raster sources, flags and a README.
The build script creates transient objects/archives in each variant; these
intermediates were removed after verification to keep the retained experiment
small. The probes are compiled without function instrumentation and share
per-launch state through a memfd. Their state is not global. The compiler ABI
hook names are a profiling-only symbol-name exception. `source-manifest.json`
records the original C/header hashes; flags files identify the compiler/linker.
The archive still statically links our code and dynamically links the same
system libraries as Makefile.

## Trace and endpoint

One training launch used `-finstrument-functions` and a non-PIE profiling build
so function-entry addresses resolve directly through `nm`. Entry records are
address/monotonic-time pairs written atomically to one O_APPEND file by all
instrumented threads. Entries after G4a are discarded; the remaining entries
are timestamp sorted and reduced to first occurrence. The training captured
**108,023 pre-endpoint entries and 326 unique function names (M)[AC],
load1=19.29**, with BAT0 `Not charging`. Raw trace, original training ELF,
cutoff and generated order are retained in B. Thread scheduling makes this one
trace order workload-specific; there is no claim of universal function order.

GCC's instrumentation exposed a clobbered-variable warning in
`font_raster_glyph`'s existing setjmp fallback. Only that function was excluded
from instrumentation; the startup ASCII atlas functions remained traced.
The existing malloc interposition object was also uninstrumented to avoid
instrumenting allocator bootstrap. Neither production module was edited.
System-library functions are outside this main-executable placement experiment.

The child stamps CLOCK_MONOTONIC immediately before exec, excluding fork.
The endpoint is the maximum of:

1. actual `plat_map` map request/flush timestamp;
2. actual editor command ingress callback timestamp, proving input acceptance;
3. latest completion timestamp of the initial CPU raster strip jobs.

A single injected `x` command uses the editor's normal queue/mutation path
before the first frame; native keyboard setup and window creation still run.
This exercises acceptance deterministically, without timing an external window
search or an XSendEvent round trip. It adds the same small command/journal work
to all candidates. The original main's file open, renderer setup, journal setup
and index start remain in scope. Errors, missing timestamps, wrong raster job
count, advice failure or nonzero child exit fail the benchmark; no launches
are silently dropped.

The final raster worker records its timestamp, takes mincore residency and stops
all experiment threads before publishing its completion message. The parent
reads smaps while the process is stopped, then resumes/acknowledges it for normal
flush/close. The completed first frame cannot be uploaded/presented before this
snapshot. Earlier completed strips may have been uploaded as in production;
that existing overlap is not removed. Timestamping precedes observer work, so
SIGSTOP, mincore, smaps, cleanup and presentation are excluded from G4a.
A final acquire/release completion-order clarification produced identical
x86_64 probe `.text`; it did not change the measured instructions or require
a second timing series.

**Page interpretation:** executable smaps RSS is a bound on populated code
PTEs, not an exact count of executed instruction pages: fault-around can populate
neighbors and the mincore/probe observer itself uses code. It is sampled at the
first-frame boundary before final completion publication. mincore reports shared
page-cache residency, not per-process touches. Total smaps RSS includes all
libraries, pools, trace storage, font, file and raster buffers. These are memory
proxies; none is used to claim the total cold-start touched-byte gate passed.

## Measurement

The existing `/tmp/edit-corpus/ascii_code.c` fixture was used unchanged,
**1,048,576 bytes (M)[AC], load1=20.89**. Linking and the training/test launches
left executable/corpus caches warm; no eviction or artificial warm-up series
was added. Every launch independently reads BAT0 and load1 before exec. All
samples were **(M)[AC]**, BAT0 `Not charging`, load1 **20.54–25.28 (M)[AC]**.
The run began at `2026-10-09T15:36:52+08:00` and used **200 launches per
candidate, 600 total (M)[AC]**, in exact A/B/C/A/B/C order. The raw CSV validates
that order, all endpoint prerequisites, stamps and page bounds.

Timing and memory columns below are **(M)[AC], launch load1=20.54–25.28**.
Binary bytes are **(M)[AC], load1=20.89**, measured on unprobed production
candidates. Percentiles use nearest rank. Executable pages are
**4,096 bytes/page (M)[AC], load1=14.70**.

Every executable mapping was fully resident in the shared page cache throughout
this warm run. Advice therefore had no cache misses to hide. B/C's median
code RSS falls from **260 to 196 KiB (M)[AC], load1=20.54–25.28**, while the
p99 remains identical. The reduction concerns code PTE population/fault-around,
not a smaller code segment: all three probed executable segments span
**65 pages (M)[AC], load1=20.54–25.28**.

| Variant | exec → map p50/p99 ms | map → accepted input p50/p99 ms | accepted input → CPU ready p50/p99 ms |
|---|---:|---:|---:|
| A | 35.057 / 94.750 | 123.374 / 313.888 | 1.613 / 5.359 |
| B | 34.218 / 98.079 | 115.077 / 278.996 | 1.461 / 5.428 |
| C | 34.970 / 103.346 | 125.528 / 305.203 | 1.579 / 6.080 |

Phase distributions are computed from each launch's timestamp differences;
these percentile columns do not sum. Most startup time on this fixture/box is
before input acceptance, after the map request. This experiment does not
attribute that interval to a particular dependency or change those modules.

The aggregate B p50 improvement is **11.129 ms (M)[AC]**, but within paired
contemporaneous rounds, B minus A has median **+3.834 ms (M)[AC]** and B is
faster in **95/200 rounds (M)[AC]**. A deterministic paired bootstrap estimates
a **95% interval of −5.470 to +14.317 ms (E)**. For C minus A, the median is
**+0.830 ms (M)[AC]**, faster in **99/200 rounds (M)[AC]**, interval
**−10.809 to +10.369 ms (E)**. All paired measurements have the same launch
power/load stamps above. Bootstrap intervals are estimates conditional on this
single series; serial correlation, fixed A/B/C order and changing shared load
limit inference. They are not gate evidence. The disagreement between aggregate
p50 and paired median is a reason not to call B a clear latency winner.

## Pareto and recommendation

With the **actual Makefile release format including debug information**, the
observed Pareto front on `(G4a p50, file bytes)` is **A and B**: A is smaller,
B has the lower aggregate p50. C is dominated by B in both coordinates.
With hypothetical stripped deployment, B is the sole observed front point;
stripping was performed only on auxiliary size copies, not the timed binaries.
The added release-file cost is mostly debug/metadata: B's `size` text category
(including read-only data) is **391,629 bytes**, versus A's **391,661 bytes
(M)[AC], load1=20.89**; stripped B saves **2,464 bytes (M)[AC], load1=20.89**.

Reject adoption now: the page-locality result is useful, but the warm latency
result is not stable under the paired comparison, while the current release
format pays a file-size cost. C has neither a latency nor a residency advantage
in a cache-resident run. Retain this reproducible experiment for a later
startup investigation; there is no clear winner and no production patch.

Cold-cache rows are **SKIP**: dropping caches needs root and was not attempted.
This does not reject a potential cold-cache benefit or test APST latency.

Xvfb cannot show real GPU power states/wakeup, the real compositor/driver,
physical display vblank/scanout or input-to-photon effects. G4a excludes final
upload/presentation, but a native server can change startup round trips,
scheduling and concurrent GPU initialization. A later real-display run would
need the same fixture/builds/common endpoint, warm interleaved launches with
power/load stamps, separately reported T4/T5/T6, and the actual display/backend
configuration. The coordinator must announce that run to Tobias; this worker
ran no real-display session and never set EDIT_ALLOW_REAL_DISPLAY.
