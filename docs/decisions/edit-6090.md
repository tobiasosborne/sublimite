# edit-6090: the wrapped viewport re-anchored at the caret's row on a Return at the bottom row

Bead edit-6090 (trial, Tobias 2026-10-20: "while typing the screen
periodically jumps up until only the last line is showing; every 1-5
minutes"). Worker session s9. Code: `src/editor/input.c` (`finish_edit`,
new `wrapped_one_row_below`), `src/view/view.c` (`finish_move`, new
`one_row_below`). Test: `tests/editor_test.c` `n6090_typing_top`
(`--6090-typing`).

## Trigger

Not a periodic maintenance step. The jump is deterministic and typing-driven
in **wrapped** mode, which is the default for `.md`, `.txt`, `.tex` and
extension-less paths (`view_wrap_default`): a Return typed while the caret
sits on the bottom visual row of the viewport.

Two sites decide the wrapped top after a mutation, both before `layout_edit`
has run, so the layout's `wrap_rows[]` are still the pre-edit rows:

1. `input.c finish_edit`: `cursor.start > bottom->start`, where `cursor` is
   the fresh row containing the caret and `bottom` is the stale last row.
   After the Return the caret's row starts after the old bottom row's start,
   so the branch took the "follow directly" action: `visual_byte =
   cursor.start`, i.e. the caret's row became the top row. Measured in the
   fixture (trace in the worker report): Return at byte 126920, fresh caret
   row start 126921 > old bottom start 126876.
2. `view.c finish_move`: the same shape with `cursor >= bottom` where
   `bottom` is the old last row's `next`; it fires when nothing follows the
   caret on its line (typing at the true end of the file), since then the
   old `next` is at or before the post-edit caret.

The period Tobias observed is one screenful: after the jump the caret is on
the top row; 26 more typed lines (27 text rows minus one) bring it back to
the bottom row, where the next Return jumps again. In the fixture the jumps
fall at keys 924, 1851, 2735 (every ~27 typed lines of 40 chars); at a
typing rate of a few keys per second that is minutes apart. Typing at the
end of a file leaves exactly the caret's (last) line visible at the top,
which is the reported picture.

## Why the existing policy was wrong here

The non-edit path (`finish_move`, `!v->edited`) already distinguishes
"one row down" (`r.start==bottom`: advance the top by one visual row) from a
far jump (follow directly). After an edit that test cannot be made against
the cached rows, so both sites fell through to the far-jump action for every
edit that moved the caret past the stale bottom row, including the most
frequent one, a Return.

## Fix

Prove the one-row case with one fresh query (`layout_visual_row_fresh`) of
the row above the caret's row (`cursor.start - 1`): it is the old bottom row
exactly when its start equals `wrap_rows[last].start`. An edit inside or
after that row leaves every earlier row start unchanged, so a match is
certified by the bytes, not by the cache; an edit earlier in the viewport
shifts the old start and the match fails, keeping the direct follow for far
jumps (paste, undo). In the one-row case the top advances to the old row 1
(`wrap_rows[1]`: start, line, line_start), which the edit did not touch, the
same outcome as the non-edit one-row path.

Cost (P): one additional bounded wrapped row query per Return typed at the
bottom row, beside the fresh caret-row query both sites already make; no
allocation, no change on the typing path for keys that do not move the
caret past the bottom row.

## Ruled out, with evidence

The unwrapped fixture (`.wrap_mode = -1`, journal live, 3000 keys with
Returns, paragraph breaks and Backspaces, 3000-line fixtures crossing
`LINEIDX_CHUNK` boundaries, the journal's 1 s durability tick between
batches, retention and checkpoint running) never moved the top by more than
the typed newline: journal checkpoint, retention publish (edit-fi2), index
maintenance (`lineidx_refresh`/worker rebuild), snapshot adoption and the
resident scroll resolver (`scrollctl.c`) do not touch the displayed top
while typing. The scroll module's own policies clamp every top to
`max_top = lines - rows`, so none of them can show a single last line.

## Found, not fixed (outside the bead; reported)

Unwrapped mode, Return on the bottom row: `editor_scroll_follow`'s fast path
reads `e->row_byte[]` before the relayout; `layout_edit` leaves the row
starts after a newline-changing edit stale, so the stale row 26 "contains"
the caret, the top is kept and the caret sits on the hidden 28th layout row
for one keystroke; the next key's view follow corrects it. Same stale-rows
family, different site; no jump.
