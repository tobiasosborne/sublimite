# Prepaying the piece tree's copy-on-write pool

**Decision.** A leaf, a branch and a snapshot header each occupy one interchangeable **400-byte slot**. A leaf holds up to **24** piece descriptors and a branch up to **16** children (P, layouts derived below). One UI-owned process reserve funds the next command. The buffer owns its live and retiring objects. Old revisions affect occupancy, and a new command claims a scalar number of free slots. The private ADD boundary remains a separate chunk.

Sources identified by v1 symbols are pinned at `6fec2e8`. (P) marks arithmetic or a consequence of a stated representation. (G) marks a product or admission contract. Counts below are derived, with no new memory or latency measurements.

## Revision ownership in v2

PLAN §2 assigns modules; §§4.1–4.5 and amendment A6 determine which operations need immutable text. The unit of node accounting is the physical node. Count it once even when several roots reach it. For headers, count each actual uncached take; a retain of an existing handle adds an owner. A restored root can acquire a new header after abort. Revision numbers alone cannot deduplicate either allocation.

| V2 holder | When text is retained and by whom | When it ceases to occupy storage |
|---|---|---|

V1 evidence is `src/piece/piece.c` `piece_snapshot_take`, `cow`, `snapshot_uncache`. | UI replaces or closes its tree. Outstanding snapshots continue to own the old core through reload and close. |

On yield, `replay` can keep a guard on a different, intermediate active revision. | UI commit or abort releases the pre-edit checkpoint. Resume releases the guard before further mutation; group completion, abort or teardown drops the pre-group view. A separately published inside snapshot can survive rollback. |

V1 evidence **excluded as independent v2 holders** includes the raw buffer pointer in the old session graph, the copied metadata fields themselves, tabs' borrowed tree/undo pointers, the separate resident `scroll_snapshot` in `src/editor/scrollctl.c` `editor_scroll_retire`, the old full-buffer map job in `src/editor/minimap.c` `editor_map_service`, and v1-specific large-file warm/goto/find jobs (`src/editor/large.c` `editor_large_start`, `editor_large_goto_byte`, `editor_large_find_begin`). The old `findui` slot array, clipboard desired/primary/command slots and separate direct save entry points are not fixed seats in the v2 architecture. Their useful behaviors are covered by the named owners above. The v2 plan defines no piece-wide concurrency limit for them.

A mapped snapshot retain also acquires the backing via the map hooks. A lineidx fault token can outlive all revision headers. Worker last-release in `src/piece/piece.c` `snapshot_drop` can enqueue retirement; `reclaim_drain` and `piece_reclaim` return the physical node and header slots. Keep queued and detached objects charged until this return. The process allocator and its return path outlive all its cores, including final releases after UI buffer close.

## Choosing the slot and fanouts

The invariant is that **any free slot can satisfy the next node or header allocation**. In `src/piece/piece.c` the node prefix is 16 B, a leaf entry uses two 4 B fields and one 8 B source offset, and a branch entry uses two 8 B counts and an 8 B pointer. Thus `16 + 24 × 16 = 16 + 16 × 24 = 400 B` (P, pinned ABI and struct-of-arrays fields). Use the existing node-kind discriminator to select capacity. Keep descriptors in order and preserve the full widths. Assert both layouts, header fit and alignment at build time. A header occupies the same storage with its own typed lifetime. Each public take/retain/release continues to own exactly its required root/backing reference.

**The simplest change** would pad a 16-entry leaf to 400 B and keep a single fanout everywhere. This already permits scalar admission. It leaves eight usable descriptor positions empty in every full leaf (P, `(400−272)/16`). The following calculations compare **live tree slot payload** at identical text, before headers, slab tails, spare slots, ADD data and page rounding. Those costs enter the allocator ledger separately.

| Public workload | Compact v1, leaf/branch fanout 16/16 | Single 400 B slot, 16/16 | Selected single 400 B slot, 24/16 |
|---|---:|---:|---:|
| Packed 10 GiB mapping | 10,240 leaves + 684 branches = 3,058,880 B | Same node counts = 4,369,600 B | 6,827 leaves + 457 branches = 2,913,600 B |
| 64 KiB of one-byte pieces, repeated prepends | 8,191 leaves + 1,166 branches = 2,694,352 B | Same node counts = 3,742,800 B | 5,461 leaves + 778 branches = 2,495,600 B |

All table entries are (P). For the PLAN mapped fixture, `ceil((10 × 2^30)/2^16) = 163,840` chunk descriptors. Divide by the leaf capacity, rounding up, then repeatedly divide by the branch fanout. Branch levels are `640+40+3+1` or `427+27+2+1`. With padding alone, the advisor's delta is exactly **1,310,720 B = 1.25 MiB** (`10,240 × 128`). With the wider leaf the packed tree uses **145,280 B less** than compact v1 (P, subtract the table totals).

For the fragmented fixture, seed a valid one-byte ADD ref, then prepend it `65,536` times (P, one descriptor per byte of the 64 KiB document; `piece_insert_ref` bypasses append coalescing). On leftmost overflow, a full even-capacity node of capacity `c` leaves `c/2` entries in its new right sibling. Thus the number of nodes needed at that level for `m` entries is one through `m=c`, then `1+ceil((m−c)/(c/2))` (P, from `splice`). Apply first to leaves and then to each branch level: the branch sums are `1,023+127+15+1` and `682+85+10+1`. Padding alone costs **1,048,448 B** in this small document (`8,191 × 128`); the wider leaf saves **198,752 B** versus compact v1 for this sequence (P, table subtraction). Other edit histories have different fill. In particular a nearly empty leaf pinned across versions still costs a full slot.

There is also a concrete memory-gate counter-example to leaving both fanouts at 16 **and** putting headers in the 400 B class. In v1 `tests/piece_mem_test.c` `version_headers`, 10,000 one-byte prepends already reach height four: the first such root growth is at 8,777 pieces (P, start at 17 and add `15×(8+8²+8³)` for successive left-spine root splits). The test then holds 5,000 successive snapshots and inserts after each take. Even a coalescing insert clones the shared path. At least `5,000 × (5 path slots + 1 header) × 400 = 12,000,000 B` are live (P, every immediate successor is retained or active). The fixture's own ceiling is **at most 11,608,382 B** (G formula, P substitution): `65,536+4,096+96×20,000+1.25×15,000+1,920×5,000`, allowing even two extra pieces per subsequent insert. Padding and changing only the allocator therefore fails this specific gate. Wider leaves keep the initial tree at height three for this workload (P, first height-four growth at 13,165 prepends under the recurrence below). This removes the demonstrated lower-bound failure; the implementation must still run the whole fixture.

**Headers.** A compact second class would save up to `400−80 = 320 B` of slot payload per actual header (P, `SNAPSHOT_SZ` at the pin), or `1,600,000 B` across the 5,000 changed-version handles in `tests/piece_mem_test.c` `version_headers` (P, isolating header cost). Many retains of the same cached header pay the difference once. Equal or restored roots can have separate headers; deferred releases still occupy slots. A compact header class admits fewer allocation orders: space freed by a header could not satisfy a leaf split even though a single shared slot suffices. No independent header-size contract requires that partition. Use one class for all three and count actual headers. This spends an extra 320 B on a lone historical header even if the document is small; a constrained base allocator may genuinely refuse earlier on header-heavy workloads. Preserve the memory fixtures, including `thin_leaves`, `version_headers` and `small_memory_test`; the examples above do not predict their whole-allocator high-water marks.

**What changes.** Leaf operations use leaf capacity and leaf merge threshold; branch operations use branch capacity and branch merge threshold. This affects `build`, staged promotion, `splice`, `maybe_merge`, cursor fast paths and traversal fixtures. Splitting the 25th leaf entry gives 13/12; splitting the 17th branch entry gives 9/8 (P, round the larger half up). Use the kind of the **child being merged**. Keep a reference insertion batch within leaf scratch capacity, including the two possible boundary fragments; a split must fit in two nodes. No second allocator dispatch follows from the two capacities. There is no invariant requiring a leaf and an interior node to have the same arity.

## Tree geometry and mutation reserves

**Document size and height.** Use `D = UINT64_MAX = 2^64 − 1` logical bytes as the supported **L1 piece-document maximum** (P, width of `piece_tree.len`, subtraction-before-growth checks in `piece_insert` and `piece_insert_ref`, and the exact-EOF fixture in v1 `docs/decisions/P1.4d.md`). Repeated references can describe more document bytes than there are physical ADD bytes. Source offsets have a separate tag bit (`TOP`, `add_reserve`). PLAN specifies a **10 GiB** mapped-file integration case (G, Wave 2 exit fixture) and gives no universal maximum for files the application must open. The integrated path also has address-space, backing and index limits. For example, v1 `src/lineidx/lineidx.c` `lineidx_create_reserved` requires chunk count plus spare entries below `UINT32_MAX`; `lineidx_create` supplies 64 spare entries (P, default call argument). Its largest representable dense open with that default is `(UINT32_MAX − 1 − 64) × LINEIDX_CHUNK` bytes (P, last admissible entry count times chunk width), even before considering available memory. `D` sizes the piece arithmetic without promising a mapping of that size or imposing a new application file cap.

Let `F=16` be branch fanout, `L=24` leaf capacity, `h` the number of branch levels, and `p` the number of nonempty pieces. Then `p ≤ length ≤ D` and full capacity at height `h` is `L × F^h` (P, at least one byte per piece). Even a fully fragmented packed tree needs at most `h_pack=15` (P, `24 × 16^14 < D ≤ 24 × 16^15`). For a mapped original substitute `ceil(length/CH_SIZE)` for `p`. The open builder packs leaves first, then branches.

**Height gate and reachability.** Full fanout bounds the packed representation. `maybe_merge` leaves a small child beside a full sibling, and the builder can leave a short right edge. V1 does not maintain a half-full minimum after deletion. Accept height through `H = h_pack + 1 = 16` (G, the packed maximum plus a split level); check prospective root growth, including delete and bulk operations. `H + 1 ≤ MAXH = 32` (P, leaf-inclusive traversal stack in `piece.c`). A height-`H` tree is valid. Only growth **above** it needs off-path dense rebuilding and revision-validated retry. Preserve piece order, ADD offsets, snapshots and append state. Height is a structural constraint with its own result, never a “memory is full” diagnosis.

**Lower bound.** Starting empty and using mutations alone requires at least **16** calls to `root_grow` (P, initial height zero, each grow adds one, promotion only subtracts). Even initialization from the largest representable original gives at most 11 branch levels (P, at most `2^48` original chunks, between `24 × 16^10` and `24 × 16^11`), hence at least **five subsequent root splits** on that route. At the first mutation growing to height 16 the two old-root halves have at least eight children each (P, `splice` on branch overflow). In a public-operation tree those 16 child subtrees are disjoint within this revision, each height 14 and containing at least 14 branches and one leaf. Thus at least `(1 + 2 + 16 × (14 + 1)) × 400 = 97,200 B` of live node payload is necessary at that instant (P, new root, two halves, minimal surviving paths). This intentionally weak lower bound cannot establish impossibility. Snapshot COW shares across roots; the test-only shared-DAG builder does not establish public reachability.

**Constructive public fixture.** The following sequence reaches the gate within a 47-bit user-address budget (P below). It uses one real ADD byte, no snapshots and no synthetic tree. The fixture parameter is the height at which to thin completed subtrees, `t = 8` for target height 16 (G, mid-height to bound both halves of the construction).

1. Insert a byte and delete it into a `piece_ref`. Repeatedly prepend that same ref with `piece_insert_ref(tree, 0, ref)`. Each call creates one descriptor; the original ADD byte suffices throughout. All splits follow the leftmost spine. A branch overflow splits 9/8 and a leaf overflow splits 13/12 (P, the upper-midpoint rule above).
2. Each time the leftmost node of height `t` splits, remember its new immediate right sibling. Continue prepending until the left node has 16 children again, **before** its next split. In that right sibling keep just its first byte: call `piece_delete` on the suffix ending exactly at the sibling end, with a null output ref. Track the two byte extents by the split rule in the fixture's independent shape oracle. The operation only deletes ADD spans and does not append data. At each level within the sibling, `del_rec` drops the other children, leaving a unary chain. Above it, `maybe_merge` can merge the trimmed sibling with its right neighbour if their counts fit. Its left neighbour is full, so the insertion spine survives. The newest pair always remains together even if its parent splits, since it occupies the first two positions. The very first pair can be children of the root.
3. Each older trimmed sibling is a root over unary paths. Repeated mergers accumulate at most 16 such paths in one sibling (P, branch fanout); after that a further unary child cannot merge with it. Hence repeats eventually add another child to the parent. When that parent splits its new left half starts with nine children and pruning can remove at most one, leaving at least eight. Higher ancestors therefore do not merge on that pruning pass. Subsequent splits propagate upward by ordinary leftmost insertion. Stop on the first root growth to 16, even if a thinning step is pending.

A fixture can generate these byte operations without private node access. Put `q=F/2=8` and `a=L/2=12`. In the initial unpruned prepend run the first growth to height one is at `g(1)=25` entries. For `j≥1`, `g(j+1)=g(j)+15a q^(j−1)` (P, after a root split, 15 more child splits each spaced by `a q^(j−1)` prepends). At the first split of the cut-level node its right sibling holds `s=a q^t` bytes. The left needs `d=(16−9)a q^(t−1)` more prepends to fill. Make the first cut after `g(t+1)+d` prepends, with left prefix length `P_left=g(t+1)−s+d`. Delete `s−1` bytes at offset `P_left+1` and repeat the same delete range every `s` prepends. Pruning preserves the active spine and the carry schedule. At cut one, the first cut follows 289 prepends, deletes 95 bytes at offset 194 and repeats every 96 prepends (P, substitute `t=1`).

For the address bound, before the last split the height is at most 15; immediately afterwards the new root has two children. Thus at most `2 × 16^7` nodes of height eight are present at either point (P, maximum fanout from the two height-15 roots). Apart from the active subtree and its newest untrimmed sibling, each contains at most `1 + 16 × 8 = 129` nodes. Each of the two dense exceptions contains at most `(16^9 − 1)/15` nodes (P, full tree through height eight). Upper nodes number at most `1 + 2 × (16^7 − 1)/15`. Charging 400 B per node puts the sum of those three bounds below 32 TiB (P, multiply the geometric sums by the uniform slot size; `32 TiB=2^45 B`). The stated address budget also covers reusable allocator extents, per-operation reserves and the fixed ADD store. Logical byte length fits `D` since each leaf holds at most 24 single-byte entries (P, leaf capacity). This bound describes address space; the scaled test below exercises the sequence in CI.

Make this parameterized sequence the public growth fixture. For routine red/green use the same split/trim sequence with a low height gate and cut (e.g. gate three, cut one, G, exercises a trimmed node, its parent and root growth). Exercise a further growth request at the gate, repack and retry, and assert preserved bytes and prior snapshots. The full-depth parameters specify the reachability witness; the scaled run checks the algorithm on ordinary test hardware. No full-depth execution or new measurement is claimed.

**One shared descent.** `cow` copies each shared node on the edited path once and retains the children of a copied branch. A fully shared descent occupies `400(h+1) B` of new slots (P, one leaf and `h` branches). Count actual fields copied separately from occupied bytes. An exclusive cursor extension can consume zero nodes. In compact v1 the payload was `272+400h`: at height four the path, header and amortized slab tails already cost `1,872+80+6×8=2,000 B`, and at height fifteen the path alone cost `6,272 B` (P, v1 `deeper_snapshots` and `docs/decisions/P1.4e.md`). The historical `1,920 B` allowance (G, v1 MEMORY BOUND) fails even before the private ADD case.

**Scalar reserve at entry.** The requirement is a safe upper bound on *simultaneously needed free slots*. Hold it across a mutation; after success, release its unused portion. With interchangeable slots, discard the v1 per-class minima, full-root special cases and delete-class reserve on snapshot take. Keep only the geometry that can actually consume a slot:

| Operation | Free common slots | Derivation (P) |
|---|---:|---|
| Insert one segment at height `h` | `2h+3` | At most `h+1` path clones, one split sibling per level, and a new root. Inserting into the middle of a piece may add a second descriptor but still produces at most one sibling per level. |
| Insert or reinsert `n>0` segments | `n × (2 min(H,h+n−1)+3)` | Bound by separate descents. Each segment can grow the root at most once. Batching fits at most one leaf split per descent. Check products and compute the capped height without unsigned wrap. |
| Delete a range | `4h+3` | At each depth below the root, at most two partial boundary nodes are changed plus at most two merge destinations across those boundaries. Fully covered children are unlinked. An interior cut in a single piece can instead split along one path, with at most a clone and sibling per level. Up to three slots cover root clone, root sibling and new root, including a leaf root. Delete-all needs only a fresh empty leaf. |
| Uncached take, including checkpoint begin on cache miss | `1` | One header; increment the existing root ownership. Any inside-checkpoint ADD boundary is funded independently. Refill before further mutation. |
| Cached take/retain, no-op mutation | `0` | A checked owner increment or an empty operation allocates no object. |

The delete count is deliberately conservative. In the two-boundary case `del_rec` descends both sides only at their common ancestor. Each resulting prefix/suffix recursion follows one partially kept child and tries at most one merge; at the common ancestor it can try both. In the interior single-piece split, new halves already meet the merge threshold. Above the last split the remaining ancestors can each clone a merge destination. The bound survives the change in leaf capacity because it counts boundary and sibling **nodes**, not entries. Preserve middle-of-full-leaf deletion and split cascades as acceptance cases.

For ordinary insert, `n = ceil(((add_len mod C)+len)/C)` for a nonempty input, `C=CH_SIZE=2^16 B` (P, chunk boundary). For `piece_insert_ref` sum the same expression over nonempty ADD spans using each span's own offset and length. The scalar upper bound allows any legal batch size; the pinned implementation batches `FAN−2=14` (P, room for split endpoints). Check all growth and span arithmetic before mutation.

**Private ADD boundary.** `piece_checkpoint_begin` retains a restore view at the ADD mark. On the first uncached inside take for which the mark is unaligned, the root's `add_high` exceeds the mark, and the restore boundary is still shared, `checkpoint_snapshot_storage` installs a private writable copy in the restore view *before* publishing the snapshot. It copies the prefix bytes and newline prefixes and restores the prefix newline total. Prepay **one complete `sizeof(add_chunk)` per open checkpoint that may publish such a view** (P, `boundary_private` makes this once per checkpoint). On the pinned ABI this is `65,800 B = 65,536 + (65,536/512) × 2 + 4 + 4` (P, data, `uint16_t nl_prefix[]`, `nl_total`, refcount). Bill the actual aligned allocator stride. An aligned mark, unobserved extension or cached take requires no new private chunk. The ordinary pre-begin take itself does not trigger the copy.

On abort the UI restores the logical mark, swaps the directory and repairs the restored tail's newline state. A surviving inside snapshot continues reading its original bytes, including the transaction tail, while new edits can append at the restored mark. On commit the unused restore view is dropped. If the last observer is gone at abort, the ordinary boundary can be reused. Older detached chunks and directories remain charged until physically freed, across any number of subsequent checkpoints. Prepay the checkpoint descriptor, restore-view metadata and any private directory path needed for the boundary exchange as well. For the v2 shared directory require a prepaid, bounded path for that exchange and a constant-time retain at begin. V1 `add_store_prefix` allocates a pointer table and retains every prefix chunk at begin; plain take retains the existing `add_store`.

## Pool sizing and admission

**One command, one count.** Let `O` be all *physically occupied* common slots in the process, including cache, live headers and queued retirements. For command steps in order, take the maximum of prior possible consumption plus the next step's entry requirement. Do this before journal acceptance. A normal replacement covers a checkpoint begin, deletion, single-segment insertion and publication. At height `h` its conservative scalar claim is

`W(h) = 1 + (4h+3) + (2 min(H,h+1)+3) + 1` (P).

The two unit terms are header takes, the deletion can grow the root once before insertion, and the final take only needs its own header. A snapshot alone need not prepay a deletion. At a leaf root `W(0)=10`; at `H=16`, `W(H)=104` (P, formula above). A paste across chunks, compound command or replay uses its actual sequence. An exclusive cursor fast path may prove a smaller claim. Distinguish a conservative successful preflight from an allocation failure for storage genuinely required by the planned path.

**Process provision = `O + outstanding claims + W` common slots** (G, one UI command at a time). The resulting byte target is `B_nodes = 400 × (O + outstanding claims + W)` (P, slot stride); add extent metadata and page rounding once per actual extent. Compute the independent ADD and metadata requirement below. An older revision can keep an entire disjoint tree live. Once counted in `O` it requires no second reservation per command. No service concurrency limit follows from this formula.

**Cut the nested node allocator.** Use the app's existing base fixed-block pool directly for the common stride. Admit a scalar claim on its funded free slots, lend objects to a core when needed, and return them after physical retirement. Pool segments remain owned by the app allocator through orphaned cores; close or reclaim completely unused extents off-path. Recycling a slot initializes the new kind before publication and respects alignment, object lifetime and ASan poison/unpoison requirements. For returns to a segmented base pool use the owning extent's address range and `edit_pool_put`; keep allocator metadata outside the 400 B objects. During normal use UI alone changes the shared base pool. Worker releases enqueue through their owning core. A final orphan-core drain must hand its returns to the allocator owner or use the same allocator-level serialization as every concurrent get/put; a per-core mutex cannot protect one pool shared by two cores. Delay final pool teardown through that handoff. Remove v1's per-core `pool[3]`, `slot_size(pi)`, repeated `pool_reserve_class`, type-routed `pool_get/free`, per-class trim loops/counters, two-slot occupancy queues and tagged `slot_slab` marker. Keep logical leaf/branch kinds, root/child ownership and deferred reclamation. Those determine which children, backing and ADD view to release. Slot width only determines where an object fits.

For comparison only, the old v1 slabs requested `2×272+16=560`, `2×400+16=816` and `2×80+16=176 B` (P, two same-type slots and a tail). A scalar process pool can reuse a slot freed by a header in buffer A for a branch in buffer B. The old arithmetic and its per-core trailing half slabs do not enter the new target.

**Empty tabs.** The incremental per-tab working reserve is zero (P, one UI writer). A bare empty root consumes 400 B. Publishing its first snapshot adds another 400 B; retains of that header cost no additional slot. The process working reserve from scratch at empty height is `10×400+65,800=69,800 B` in raw storage, or `69,808 B` with 16-byte boundary alignment (P, `W(0)` and the private chunk stride). A hundred bare empty tabs plus one raw working reserve therefore use `100×400+69,800=109,800 B`; with every empty tab published, `100×800+69,800=149,800 B` (P). These are node/header and spare-boundary totals. Account separately for tree/core structures, completed but unreturned jobs, other ADD storage, directory metadata, scratch and VM page rounding. Independent per-tab prepayment loses cross-buffer reuse: the earlier three-class proposal was `52,848+65,800=118,648 B` raw for each bare empty tab (P, former nine divergence credits, working vector, root and boundary). The selected design gives up concurrent writer guarantees; a yielded transaction keeps any irrevocable outstanding claim until safe release.

### Refill contract

- **Invariant and owner.** After every committed command's submit and before dispatching the next ordinary input, the UI must fund the active buffer's scalar working count and one available private boundary, or record the base allocation failure for that attempted refill (G). Apply the same check initially, on a buffer switch, after abort or yielded replay, and after any snapshot admission that used the reserve. Do not rely on an idle timer, a future cancel or an empty input queue. The UI serializes dispatch and reserve ownership; a worker can publish a return but cannot spend or mutate the UI's pool. Keep an allocator owner alive through orphaned cores and arrange safe final draining or synchronized finalization after UI shutdown.
- **Amount.** With `f` funded, unclaimed free slots, buy `max(0,W−f)` common slots (P, scalar deficit). A fresh header costs one of them, and a cached retain costs none. Refill any separate boundary/companion deficit. Credit physically returned slots before asking base for more. Slots already claimed by suspended work remain unavailable.

- **Source.** Use app-owned `src/base/base.c` `edit_pool_init/get/put` for the common slot and an independent fixed-block supply for complete ADD chunks, and `edit_arena_init/alloc` for scoped variable scratch. Keep independently lived snapshot/directory objects in storage valid through their last owner. Base pools have fixed capacity per VM reservation. When a segment fills, try a further base extent for the missing blocks; exhausting a locally chosen batch is not a terminal OOM. Budget and obtain its bookkeeping from base too. Stage whole blocks, make their pages writable and touch the pages needed for the hot operation in maintenance, then publish their counts. In v1 Linux `base.h` documents lazy first-touch on writable `MAP_NORESERVE`; a reserved address or a `fresh` index alone is not evidence of residency. The admission guarantee concerns recoverable allocator refusals, not survival of a kernel OOM kill.
- **Ordering and bulk.** Ordinary refill runs **after submit, outside the preceding input → submit guard, before the next input is consumed**. At admission use the exact request if it exceeds the ordinary envelope: compute the scalar peak of prior possible consumption plus the next step's entry reserve, including reference segment counts, all mandatory takes/guards, ADD and directory paths, undo and journal staging. A smaller operation may already fit even if speculative funding for the next maximum failed. For a known bulk command fund its exact requirement in advance. If the need is first discovered after input, retain the command and its payload in order, ahead of later edits, with no mutation or acknowledgment. Dispatch its exact deficit to base-backed maintenance, keep input → eventual submit covered by the Law 2 guard, and resume once funded. Fallback may obtain base VM extents; no libc allocation, guard exemption, artificial submit or loss of the input. Revalidate revision, selection and destination before use. Include this wait in input → submit latency. Joined completion or a worker's return merely wakes this path; refill has priority even with continuous input.
- **Failure.** Try the actual deficit against returned blocks and the base allocator. If a preferred larger extent fails, try the necessary amount. Only a base refusal of necessary storage after this check permits the user-visible memory error. A speculative refill failure, a queued refill, a delayed service retirement or an empty local batch cannot by itself refuse an edit. Return unused claims on every error; a partly funded refill may retain valid free blocks for the retry. Under a permanently pinned BASE, each committed disjoint edit can raise `O`. The mandatory next refill buys the resulting deficit while capacity is available.
- **V1 comparison.** `src/piece/piece.c` `pool_reserve_class` calls `pool_grow` synchronously until free slots meet the request, under the pool lock. That happens in `reserve_insert` / `reserve_delete` before mutation and in `piece_snapshot_take` before publishing a fresh header. A cached take skips growth. In `tests/piece_mem_test.c` `deeper_snapshots`, `mem_alloc` counts every hook request; the live-byte baseline is sampled **after** the take and before the insert, so slab prepayment at take is already in the baseline and any further growth during insert still counts. In `tests/piece_test.c` `t_random` the counting hooks are installed from creation. Separately, `tests/piece_mt_test.c` `typing_allocator_test` warms the arena-backed tree, then starts the libc malloc guard around edits and takes. Slab growth via an arena hook can occur inside that interval with zero libc calls. Neither test demonstrates a between-command refill invariant in v1.

**Companion ADD budget** (P). At admission count physically occupied chunk slots across all views, including sealed or retiring ones. Add ordinary *new* chunks required to append the operation's bytes at the current tail, and one additional free private-boundary slot for a transaction that might expose its partial mark (G, recommended to reserve at begin). Multiply the resulting chunk count by `align_up(sizeof(add_chunk), class_alignment)`. An occupied private slot is already in the first term. Reserve the ordinary COPY/ADD payload, ref fallback, directory nodes, view/checkpoint descriptors, undo records and journal staging in their own classes, outside `B_nodes`. In particular, a requested deletion ref with more than `PIECE_REF_SPANS = 8` runs (P, `src/piece/piece.h`) may append **the entire range**, including existing ADD bytes (`piece_delete`, `collect`); use length as its safe append bound. A new chunk reservation for appended data and a private boundary serve different purposes and can both be due. For v2 directory metadata use the actual chosen layout's maximum touched entries/levels and allocator strides; its representation has no frozen byte size at this pin. A companion-storage deficit also goes through refill before a genuine base refusal can reject the transaction.

## Exhaustion and verification

Use an exhaustive `enum piece_pool_state` with `PIECE_POOL_READY`, `PIECE_POOL_REFILL_PENDING` and `PIECE_POOL_EXHAUSTED` (G, funded, deficit awaiting service, and actual base refusal). The UI owns transitions and records the destination, revision, claim and allocator outcome. A failed warm-up has no user command to reject.

| State and event | Result and next state |
|---|---|
| READY, request fits | Claim the full sequence before publishing or mutating; release unused slots after use. At submit run the mandatory readiness check. A deficit enters REFILL_PENDING. |
| READY or EXHAUSTED, valid request exceeds current supply | Enter REFILL_PENDING, preserve the ordered input and try its checked deficit. A previous error for a different request cannot reject this one. A cached retain or small edit already funded can go straight to READY and proceed. |
| REFILL_PENDING, capacity obtained or physically returned | Revalidate the pending command and its complete claim. Enter READY and execute it once. Pending work is never reported to the user as memory exhaustion. |
| REFILL_PENDING, base refuses the necessary request | Enter EXHAUSTED. Failed piece begin sets its output to null, a new snapshot returns null, and a mutation returns `PIECE_ERR_NOMEM`. For a user edit show **“Edit not applied — buffer memory is full.”** Preserve text, selection, undo cursor, saved cutoff and journal sequence. An optional service may defer or shed its own work. Range errors and owner-count saturation remain distinguishable at admission from allocator pressure. |
| EXHAUSTED, resources return or new demand arrives | UI credits actual frees, tries any remaining base deficit and uses REFILL_PENDING → READY on success. Preserve the saved BASE; workers may still be reading cancelled work. A visibly refused edit is complete with an error. Only fresh user input can retry that edit. |

Preflight precedes the PLAN §4.2 journal acceptance point. Abort of an unfinished checkpoint remains allocation-free; previously committed replay groups survive. After RAM acceptance use the journal/frame fence and recovery rules. A deficit cannot reach `pool_get`'s free-list assertion.

## Why each remaining mechanism exists

| Mechanism and invariant | Simplest alternative considered | Counter-example or disposition |
|---|---|---|
| Common slot; all funded slots can satisfy any node/header allocation | Retain the compact v1 classes and count their free slots together | A spare header slot cannot fit a branch. Keeping separate admission checks fixes that failure at the cost of three-way reservation. Cut the classes, use scalar admission and accept the quantified header padding. |
| Different leaf and branch capacities; a full node uses its available entry storage | Pad a 16-entry leaf to the branch width | The mapped and fragmented fixtures above incur the calculated leaf waste with no extra useful entries. The kind is already required to read children versus pieces. Reuse it for the capacity. |
| Bounded command claim; an admitted mutation can finish its structural steps | Reserve for one path, or grow just when each recursive step needs a node | An interior deletion in a full leaf can split up through the root; a range deletion can own both boundaries and neighbours. Late failure may leave half a replacement. The scalar table covers those cases; the separate v1 class-specific shallow-root checks have no remaining correctness case. |
| Shared working reserve and refill; a ready command can proceed, and a missed refill cannot lose input | Prepay every tab, refill only on idle, or debit a path for every old revision | Many empty tabs multiply the same single writer's headroom. Continuous input while saved BASE pins disjoint old leaves can exhaust idle-only credit with base storage still available. One node copied from a multiply held root serves all its old readers. Cut per-tab headroom and per-revision path credits. |
| Base extents, prefunding and physical occupancy; a claimed slot is writable, available and backed by a live allocator | Rely on one fixed pool's nominal capacity, VM addresses alone, or recycle on logical release | A full first extent can coexist with ample new base capacity; a reserved page can still require first touch. A cancelled reader may still be inside a tree after UI close. Fund the exact deficit, return only physically freed slots and keep allocator lifetime through final release. |
| Pending input and explicit exhaustion states; every valid command gets one completion | Immediately report OOM on a low-water mark, or blindly replay after a visible failure | An oversized paste can need one additional slot available from base. Rejecting early loses it; replay after a moved caret can insert it twice or in the wrong place. Keep the input through refill, revalidate, and separate pending from terminal base refusal. |
| Immutable revision, cache and backing ownership; every observer reads its captured bytes | Borrow the mutable buffer, equate an fd identity with text, or allocate a new header on every alias | Typing during save changes the active revision; an fd identity supplies no diff bytes. Repeated takes of unchanged text would consume unbounded headers and break the cached-identity assumption of v1 undo's replay guard. A completed line index only needs its backing alive. Retain exactly the resource read. |
| Checkpoint, shared ADD directory, prepublished private boundary and independent append storage; abort restores exact state without allocating | Rewind the ADD cursor and share a writable tail, copy the directory at begin, or keep only node slots for the edit | A worker can read the intermediate tail while the restored writer appends at the same offset. A large prefix makes a table copy linear at begin. A deletion whose output ref overflows the span limit can append its entire range while a private boundary is occupied. Fund those distinct resources and preserve the saved root/controls. |
| Height check and off-path repack; all traversal stacks fit and capacity-legal text stays editable | Assume full fanout at every level or refuse further edits when the height limit is met | The public prepend/trim sequence reaches the height gate with sparse subtrees that can still be packed below it. A dense rebuild checked against the current revision makes the next growth possible without invalidating old snapshots. |

The physical retirement and extent handoff invariants also cover final release from a worker after the owning UI tree dies. The implementation tests above exercise normal use, injected base refusal and concurrent rollback/release. No performance or peak-RSS result is inferred from the arithmetic.
