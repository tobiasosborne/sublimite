# Prepaying the piece tree's copy-on-write pool

**Decision.** A leaf, a branch and a snapshot header each occupy one interchangeable **400-byte slot**. A leaf holds up to **24** piece descriptors and a branch up to **16** children (P, layouts derived below). One UI-owned process reserve lends whole extents to cores. Admission grows the reserve synchronously when the current command needs more. The buffer owns its live and retiring objects. Old revisions affect occupancy, and a new command claims a scalar number of free slots. The private ADD boundary remains a separate chunk.

Sources identified by v1 symbols are pinned at `6fec2e8`. (P) marks arithmetic or a consequence of a stated representation. (G) marks a product or admission contract. Counts below are derived, with no new memory or latency measurements.

## Revision ownership in v2

PLAN §2 assigns modules; §§4.1–4.5 and amendment A6 determine which operations need immutable text. The unit of node accounting is the physical node. Count it once even when several roots reach it. For headers, count each actual uncached take; a retain of an existing handle adds an owner. A restored root can acquire a new header after abort. Revision numbers alone cannot deduplicate either allocation.

V1 evidence **excluded as independent v2 holders** includes the raw buffer pointer in the old session graph, the copied metadata fields themselves, tabs' borrowed tree/undo pointers, the separate resident `scroll_snapshot` in `src/editor/scrollctl.c` `editor_scroll_retire`, the old full-buffer map job in `src/editor/minimap.c` `editor_map_service`, and v1-specific large-file warm/goto/find jobs (`src/editor/large.c` `editor_large_start`, `editor_large_goto_byte`, `editor_large_find_begin`). The old `findui` slot array, clipboard desired/primary/command slots and separate direct save entry points are not fixed seats in the v2 architecture. Their useful behaviors are covered by the named owners above. The v2 plan defines no piece-wide concurrency limit for them.

A mapped snapshot retain also acquires the backing via the map hooks. A lineidx fault token can outlive all revision headers. Worker last-release in `src/piece/piece.c` `snapshot_drop` can enqueue retirement; `reclaim_drain` and `piece_reclaim` return the physical node and header slots. Keep queued and detached objects charged until this return. The process allocator and its return path outlive all its cores, including final releases after UI buffer close.

## Choosing the slot and fanouts

The invariant is that **any free slot can satisfy the next node or header allocation**. In `src/piece/piece.c` the node prefix is 16 B, a leaf entry uses two 4 B fields and one 8 B source offset, and a branch entry uses two 8 B counts and an 8 B pointer. Thus `16 + 24 × 16 = 16 + 16 × 24 = 400 B` (P, pinned ABI and struct-of-arrays fields). Use the existing node-kind discriminator to select capacity. Keep descriptors in order and preserve the full widths. Assert both layouts, header fit and alignment at build time. A header occupies the same storage with its own typed lifetime. Each public take/retain/release continues to own exactly its required root/backing reference.

**The simplest change** would pad a 16-entry leaf to 400 B and keep a single fanout everywhere. This already permits scalar admission. It leaves eight usable descriptor positions empty in every full leaf (P, `(400−272)/16`). The following calculations compare **live tree slot payload** at identical text, before headers, slab tails, spare slots, ADD data and page rounding. Those costs enter the allocator ledger separately.

| Public workload | Compact v1, leaf/branch fanout 16/16 | Single 400 B slot, 16/16 | Selected single 400 B slot, 24/16 |
|---|---:|---:|---:|
| Packed 10 GiB mapping | 10,240 leaves + 684 branches = 3,058,880 B | Same node counts = 4,369,600 B | 6,827 leaves + 457 branches = 2,913,600 B |
| 64 KiB of one-byte pieces, repeated prepends | 8,191 leaves + 1,166 branches = 2,694,352 B | Same node counts = 3,742,800 B | 5,461 leaves + 778 branches = 2,495,600 B |

All table entries are (P). For the PLAN mapped fixture, `ceil((10 × 2^30)/2^16) = 163,840` chunk descriptors. Divide by the leaf capacity, rounding up, then repeatedly divide by the branch fanout. Branch levels are `640+40+3+1` or `427+27+2+1`. With padding alone, the advisor's delta is exactly **1,310,720 B = 1.25 MiB** (`10,240 × 128`). With the wider leaf the packed tree uses **145,280 B less** than compact v1 (P, subtract the table totals).

For the fragmented fixture, seed a valid one-byte ADD ref, then prepend it `65,536` times (P, one descriptor per byte of the 64 KiB document; `piece_insert_ref` bypasses append coalescing). On leftmost overflow, a full even-capacity node of capacity `c` leaves `c/2` entries in its new right sibling. Thus the number of nodes needed at that level for `m` entries is one through `m=c`, then `1+ceil((m−c)/(c/2))` (P, from `splice`). Apply first to leaves and then to each branch level: the branch sums are `1,023+127+15+1` and `682+85+10+1`. Padding alone costs **1,048,448 B** in this small document (`8,191 × 128`); the wider leaf saves **198,752 B** versus compact v1 for this sequence (P, table subtraction). Other edit histories have different fill. In particular a nearly empty leaf pinned across versions still costs a full slot.

There is also a concrete memory-gate counter-example to leaving both fanouts at 16 **and** putting headers in the 400 B class. In v1 `tests/piece_mem_test.c` `version_headers`, 10,000 one-byte prepends already reach height four: the first such root growth is at 8,777 pieces (P, start at 17 and add `15×(8+8²+8³)` for successive left-spine root splits). The test then holds 5,000 successive snapshots and inserts after each take. Even a coalescing insert clones the shared path. At least `5,000 × (5 path slots + 1 header) × 400 = 12,000,000 B` are live (P, every immediate successor is retained or active). The fixture's own ceiling is **at most 11,608,382 B** (G formula, P substitution): `65,536+4,096+96×20,000+1.25×15,000+1,920×5,000`, allowing even two extra pieces per subsequent insert. Padding and changing only the allocator therefore fails this specific gate. Wider leaves keep the initial tree at height three for this workload (P, first height-four growth at 13,165 prepends from 25 entries for the initial split and successive left-spine increments of 15×12, 15×12×8 and 15×12×8²). This removes the demonstrated lower-bound failure; the implementation must still run the whole fixture.

**Headers.** A compact second class would save up to `400−80 = 320 B` of slot payload per actual header (P, `SNAPSHOT_SZ` at the pin), or `1,600,000 B` across the 5,000 changed-version handles in `tests/piece_mem_test.c` `version_headers` (P, isolating header cost). Many retains of the same cached header pay the difference once. Equal or restored roots can have separate headers; deferred releases still occupy slots. A compact header class admits fewer allocation orders: space freed by a header could not satisfy a leaf split even though a single shared slot suffices. No independent header-size contract requires that partition. Use one class for all three and count actual headers. This spends an extra 320 B on a lone historical header even if the document is small; a constrained base allocator may genuinely refuse earlier on header-heavy workloads. Preserve the memory fixtures, including `thin_leaves`, `version_headers` and `small_memory_test`; the examples above do not predict their whole-allocator high-water marks.

**What changes.** Leaf operations use leaf capacity and leaf merge threshold; branch operations use branch capacity and branch merge threshold. This affects `build`, staged promotion, `splice`, `maybe_merge`, cursor fast paths and traversal fixtures. Splitting the 25th leaf entry gives 13/12; splitting the 17th branch entry gives 9/8 (P, round the larger half up). Use the kind of the **child being merged**. Keep a reference insertion batch within leaf scratch capacity, including the two possible boundary fragments; a split must fit in two nodes. No second allocator dispatch follows from the two capacities. There is no invariant requiring a leaf and an interior node to have the same arity.

## Tree geometry and mutation reserves

**Document size and height.** Use `D = UINT64_MAX = 2^64 − 1` logical bytes as the supported **L1 piece-document maximum** (P, width of `piece_tree.len`, subtraction-before-growth checks in `piece_insert` and `piece_insert_ref`, and the exact-EOF fixture in v1 `docs/decisions/P1.4d.md`). Repeated references can describe more document bytes than there are physical ADD bytes. Source offsets have a separate tag bit (`TOP`, `add_reserve`). PLAN specifies a **10 GiB** mapped-file integration case (G, Wave 2 exit fixture) and gives no universal maximum for files the application must open. The integrated path also has address-space, backing and index limits. For example, v1 `src/lineidx/lineidx.c` `lineidx_create_reserved` requires chunk count plus spare entries below `UINT32_MAX`; `lineidx_create` supplies 64 spare entries (P, default call argument). Its largest representable dense open with that default is `(UINT32_MAX − 1 − 64) × LINEIDX_CHUNK` bytes (P, last admissible entry count times chunk width), even before considering available memory. `D` sizes the piece arithmetic without promising a mapping of that size or imposing a new application file cap.

Let `F=16` be branch fanout, `L=24` leaf capacity, `h` the number of branch levels, and `p` the number of nonempty pieces. Then `p ≤ length ≤ D` and full capacity at height `h` is `L × F^h` (P, at least one byte per piece). Even a fully fragmented packed tree needs at most `h_pack=15` (P, `24 × 16^14 < D ≤ 24 × 16^15`). For a mapped original substitute `ceil(length/CH_SIZE)` for `p`. The open builder packs leaves first, then branches.

**Height admission (review 7).** Use `H=MAXH−1=31` (G, last valid branch depth for the pinned leaf-inclusive `cursor[MAXH]` and range stacks with 32 entries). Check a **prospective** root increase before modifying externally visible state or indexing the next stack level. At the limit accept an edit whose root will still fit. Predict overflow from the insertion/split frontier, or keep a fallible edit under its unpublished rollback checkpoint. Include delete-side splits, builders and intermediate bulk steps. A failed request leaves the original tree, history, ADD mark and journal untouched and returns `PIECE_ERR_RANGE`. Assert the internal post-admission stack invariant in debug. Refusal of a valid but unsupported shape is an ordinary checked result in both builds; no debug assertion depends on an adversarial caller failing to construct it.

**The eight-split lemma is false as stated.** At the pin initialize **17 full leaves** with `piece_init_mapped`: `17×16=272` chunk descriptors (P, v1 leaf capacity). `build` directly constructs a root with two branch children, the first containing 16 leaves and the other one. It uses **zero** child splits. Prepend one byte into the full first leaf. `ins_batch_rec` and `splice` split that leaf once, then split its already-full parent. The root now has three children. Its net gain of one cost **one**, rather than eight, net leaf splits among that parent's children. The same shape in v2 takes `17×24=408` chunk descriptors (P, selected leaf capacity). There is an even sharper mutation: delete one **interior** byte of one full leaf's long ORIGINAL piece instead. `del_rec` replaces the descriptor by its two nonempty ends and triggers the same cascade with **zero public descriptor insertions**. The staged builder also promotes full nodes directly. Bulk insertion can add several descriptors in one splice; deletion/thinning changes occupancy and `merge_children` can make a full node by combining siblings. None restores the premise that every split starts at the left half's post-split occupancy.

There is a restricted counting result. Starting from the empty tree, exclusively prepending single descriptors through the same left edge, a newly split leaf needs 12 further entries and a newly split left branch needs eight child additions to split again (P, overflow halves 13/12 and 9/8). On that trace the increment from first reaching height `j` to first reaching `j+1` is `15×12×8^(j−1)` descriptors (P, the new root starts with two children and overflows at 17). The review's approximately `2.23×10^29` at `j=31` and `6.33×10^15` at `j=16` are correct **for that trace**. They are neither a universal lower bound nor an address-space proof. “The count is (P) and the fallback is a defined refusal” is sound only with those two independent scopes: the trace count is (P), the checked shape limit is (G). The refusal stands even if a shorter trace exists. A supported-length document can hit a representation limit before its byte limit. Cut the former height-16 gate, repacker, off-path copy/swap, revision revalidation on repack and full-depth thinning fixture. Test grow-at-the-last-level versus an edit that fits at that level using a reduced test stack limit, plus the public builder/delete counter-example; no astronomical run is required.

**Lower bound.** Starting empty and using mutations alone requires at least **16** calls to `root_grow` (P, initial height zero, each grow adds one, promotion only subtracts). Even initialization from the largest representable original gives at most 11 branch levels (P, at most `2^48` original chunks, between `24 × 16^10` and `24 × 16^11`), hence at least **five subsequent root splits** on that route. At the first mutation growing to height 16 the two old-root halves have at least eight children each (P, `splice` on branch overflow). In a public-operation tree those 16 child subtrees are disjoint within this revision, each height 14 and containing at least 14 branches and one leaf. Thus at least `(1 + 2 + 16 × (14 + 1)) × 400 = 97,200 B` of live node payload is necessary at that instant (P, new root, two halves, minimal surviving paths). This intentionally weak lower bound cannot establish impossibility. Snapshot COW shares across roots; the test-only shared-DAG builder does not establish public reachability.

For a simple address-space witness at the old gate, seed a one-byte ADD reference, then call `piece_insert_ref` at zero repeatedly. No snapshots, coalescing, extra ADD bytes or synthetic nodes are needed. First height 16 occurs at `g(16)=25+180(8^15−1)/7=904,740,996,569,965` descriptors (P, sum of the increments above). All non-root leaves have at least 12 entries and non-root branches have at least eight children on this trace. Leaf count is at most `g(16)/12`; branch count is at most that many divided by seven plus the root (P, count edges). At ten 400 B slots per 4,096 B page, densely allocated in this insert-only core, the final tree needs under 32 PiB (P, `ceil((g(16)×8/84+1)/10)×4096 < 2^55`). This fits a 56-bit user address range on a sufficiently provisioned host (P, `2^56` bytes). It makes no claim about a 47-bit process or installed RAM. Use the same public prepend trace with a reduced stack limit as the executable fixture. Height 16 is now an ordinary supported depth.

**One shared descent.** `cow` copies each shared node on the edited path once and retains the children of a copied branch. A fully shared descent occupies `400(h+1) B` of new slots (P, one leaf and `h` branches). Count actual fields copied separately from occupied bytes. An exclusive cursor extension can consume zero nodes. In compact v1 the payload was `272+400h`: at height four the path, header and amortized slab tails already cost `1,872+80+6×8=2,000 B`, and at height fifteen the path alone cost `6,272 B` (P, v1 `deeper_snapshots` and `docs/decisions/P1.4e.md`). The historical `1,920 B` allowance (G, v1 MEMORY BOUND) fails even before the private ADD case.

**Pinned reserve classes.** In `src/piece/piece.c`, `slot_size` and `pool_grow` buy two like slots plus a 16 B slab tail. The allocator requests `2×272+16=560 B` for leaves, `2×400+16=816 B` for branches and `2×80+16=176 B` for headers (P). `reserve_insert(t,n)` generally asks for `2n+1` leaves and `(2h+3)n+1` branches. At a leaf root with room for `2n` entries it asks for only the shared-root clone, otherwise `n+1` branches at height zero. At height one with one segment it asks for three branches if the root is full, one otherwise. `reserve_delete` asks for two leaves at height zero, four otherwise. Its branch count is one or zero at height zero and three or one at height one (full root first), then `4h−1`. An uncached `piece_snapshot_take` adds one header to that delete reserve (all P, the pinned predicates). These are free-list entry requirements. The v2 scalar table below counts allocation opportunities directly.

**Scalar reserve at entry.** The requirement is a safe upper bound on *simultaneously needed free slots*. Hold it across a mutation; after success, release its unused portion. With interchangeable slots, discard the v1 per-class minima, full-root special cases and delete-class reserve on snapshot take. Keep only the geometry that can actually consume a slot:

| Operation | Free common slots | Derivation (P) |
|---|---:|---|
| Insert one segment at height `h` | `2h+3` | At most `h+1` path clones, one split sibling per level, and a new root. Inserting into the middle of a piece may add a second descriptor but still produces at most one sibling per level. |
| Contiguous bulk insert/reinsert of `n>0` chunk segments | Initial shared-path clones + split siblings + newly created roots | The batch frontier below gives the exact structural count. Sum separate operations if their gaps or snapshot owners change. |
| Delete a range | `4h+3` | At each depth below the root, at most two partial boundary nodes are changed plus at most two merge destinations across those boundaries. Fully covered children are unlinked. An interior cut in a single piece can instead split along one path, with at most a clone and sibling per level. Up to three slots cover root clone, root sibling and new root, including a leaf root. Delete-all needs only a fresh empty leaf. |
| Uncached take, including checkpoint begin on cache miss | `1` | One header; increment the existing root ownership. Any inside-checkpoint ADD boundary is funded independently. Refill before further mutation. |
| Cached take/retain, no-op mutation | `0` | A checked owner increment or an empty operation allocates no object. |

The delete count is deliberately conservative. In the two-boundary case `del_rec` descends both sides only at their common ancestor. Each resulting prefix/suffix recursion follows one partially kept child and tries at most one merge; at the common ancestor it can try both. In the interior single-piece split, new halves already meet the merge threshold. Above the last split the remaining ancestors can each clone a merge destination. The bound survives the change in leaf capacity because it counts boundary and sibling **nodes**, not entries. Preserve middle-of-full-leaf deletion and split cascades as acceptance cases.

For ordinary insert, `n = ceil(((add_len mod C)+len)/C)` for a nonempty input, `C=CH_SIZE=2^16 B` (P, chunk boundary). For `piece_insert_ref` sum the same expression over nonempty ADD spans using each span's own offset and length. The batch planner uses the actual batch schedule; the pinned implementation batches `FAN−2=14` (P, room for split endpoints). Apply cursor/run coalescing first where eligible. Count only the descriptors still to insert, and charge any COW needed by extension once on its actual path. A bulk paste whose first bytes extend an adjacent run must follow that same plan. Check all growth and span arithmetic before mutation.

### Bulk insertion and the undo representation (review 10)

**What was overpaid.** The comparison fixture has an empty tree retained by one snapshot, then inserts an existing valid ADD reference covering `n` chunk segments at EOF. Count new **400 B tree slots** only; the old root and header are already occupied. A packed build is a footprint comparator. The actual editor batch is a different shape. Use `B=22=24−2` descriptors per full v2 batch (P, room for two leaf fragments); the pinned `piece_insert_ref` uses 14 with 16-entry leaves. Use the same bounded descriptor stream for a new multi-chunk paste after funding its input bytes. The pinned `piece_insert` inserts individual segments; batch replay and paste must not silently use different bounds.

| Segment count | Rejected claim at old H=16, slots and bytes | Packed tree slots; old claim/packed | Exact batch slots; old claim/batch | Keeping the rejected formula at H=31, slots; claim/batch |
|---:|---:|---:|---:|---:|
| 513 | 17,955 · 400 = 7,182,000 B | 25; 718.2× | 27; 665.0× | 33,345; 1,235.0× |
| 16,384 | 573,440 · 400 = 229,376,000 B | 730; 785.5× | 837; 685.1× | 1,064,960; 1,272.4× |
| 163,840 | 5,734,400 · 400 = 2,293,760,000 B | 7,284; 787.3× | 8,378; 684.5× | 10,649,600; 1,271.1× |

All entries are (P), ratios rounded. The discarded formula saturates at `35n` or `65n` in these cases. Packed levels are `ceil(n/24)`, then successive `ceil(children/16)`. At EOF a pair of full 22-entry batches splits 44 entries evenly, so each such later batch adds one leaf. A final partial batch adds a leaf only when the frontier would exceed 24. Successive branch counts for `m>1` children are `1+ceil(max(0,m−16)/9)`: at overflow the fixed left child has nine entries and the active right one eight. This gives levels `24+2+1`, `745+82+9+1` and `7,448+827+92+10+1`. The retained empty root makes the first leaf a clone, so the **entire** new tree equals new slot demand. With an exclusive empty root subtract one new slot. At the largest size the exact batch asks for **3,351,200 B** and the packed tree **2,913,600 B** (P, multiply counts by 400). The review's estimate of 2.3 GB for about 3 MB of structure is confirmed. For comparison, the pinned 16-entry leaf and 14-entry batch give actual tree counts 42, 1,316 and 13,164 (P, the same EOF recurrence with 14/14 leaf splits). The pin's `reserve_insert` on this empty-root fixture asks for `2n+1` leaves plus `n+1` branches; the rejected `35n` was a proposed v2 bound. Fresh paste still needs its actual ADD bytes; reference replay does not copy that payload on insertion.

**Tight batch claim for an arbitrary gap.** For a contiguous series of batches with no intervening publication, the next insertion is at the end of the preceding batch. `ins_batch_rec` resolves an exact child-end tie to the left. After any split the next gap is in the original owned path or in a newly created sibling, never in an unrelated old subtree. Thus there is at most **one initial COW descent** (`c≤h+1`, P); cloning a shared ancestor makes its chosen child shared as well. A fresh checkpoint is a real owner for this calculation. Nodes allocated by insert alone remain live until the operation ends. Therefore **`new_slots = c + total_splits + root_grows`** (P, one sibling per split and one extra parent per growing root). No per-batch COW credit, header or fixed path multiplicity appears. This tracks allocator demand rather than the repeated CPU cost of descending.

For a safe amortised bound take the initial path occupancies `o₀…oₕ`, leaf first. Put `x=1` for an initial cut inside an existing descriptor and zero at a boundary. Let `s₀=ceil(max(0,o₀+n+x−24)/12)`; at each old branch level let `sᵢ=ceil(max(0,oᵢ+sᵢ₋₁−16)/8)` (P, upper bounds on new siblings). After each split at least 12 leaf entries or eight branch children are in the half no longer on the insertion frontier; that half receives no further input. Just before the last split all earlier frozen halves already exist and the current node must overflow. This proves the recurrence even with an initially full path. If the old root splits, count one new parent and apply the same branch recurrence above it, starting with one original child and the propagated siblings, until all fit or the height limit refuses. Summing the geometric tail yields **`O(h + n/12)` slots**, with leading worst-case allowance at most `(n/12)×8/7` plus additive height/rounding terms (P, the sum of successive factors 1/8). A stream of noncoalescing entries necessarily occupies at least `ceil(n/24)` leaf slots in the resulting tree. This gives tight order; the literal rounded bound need not be attained.

For exact admission simulate just the **counts and gap indices** of the frontier, then execute the same batch schedule. A leaf batch updates its count and gap, including the first descriptor split. On overflow charge a sibling, partition with the same upper midpoint as `splice`, retain the half containing the post-insert gap, and carry one child into the parent. Repeat carries and charge a new root if needed. Unchanged higher levels require no simulated descent for that batch. Initial path inspection determines `c`; an inherited shared ancestor forces copies below it. Scratch is bounded by the traversal stack. This takes `O(h + ceil(n/B) + total_splits)` count/carry steps (P), reads no payload twice and yields the exact claim above, including height overflow **before** mutation. Branch splitting, leaf splitting and endpoint tie decisions must use the same rules in planning and mutation. Growing ad hoc at every split under an open checkpoint could eventually produce the same tree, but a last-split failure could discard a nearly completed large paste. Reserving the counted structure up front establishes the admitted-operation invariant before writing those bytes. The amortised bound is an audit oracle; it is not a reason to touch excess pages or reject on a rounded-up claim. Exclude single-key edits from this bulk planning pass.

**Choose stable byte references and batch replay for Wave 1.** Required invariants are byte-exact undo after external backing change, immutable surviving snapshots through abort, bounded history-record admission, and journal replay after process loss. A mapping reference preserves the lifetime of an inode/view. It cannot preserve bytes subsequently truncated or rewritten in that inode; a fault epoch can detect loss but cannot reconstruct the previous bytes. The pinned public `src/piece/piece.h` contracts for `piece_delete` and `piece_iter_next_source` explicitly preserve deleted bytes in ADD and keep ORIGINAL spans ordered and nonoverlapping. At delete, validate mapped reads and materialize the needed ORIGINAL bytes into private append storage before accepting the edit. Reuse already immutable ADD spans. If a requested inverse exceeds the inline span cap (`PIECE_REF_SPANS=8` at the pin, G for this representation), explicitly fund copying the **whole range** to one sequential ADD span. With no requested ref, fragmented ADD alone needs no such duplication. Preflight actual copy bytes, ordinary chunks and fallback writes independently from node slots. On failed validation or allocation, keep both text and history unchanged. Stable offset/length records let history eviction and branching release records without owning tree nodes; append storage has the lifetime of its owning buffer/view. This design pays `O(length)` for deleted ORIGINAL bytes and potentially for duplicate ADD bytes above the cap, and `O(n)` descriptor work on large replay. Count duplicated ADD separately. In particular, the ninth discontiguous ADD span can force a large copy even when no original byte is present (P, cap plus one; v1 `piece_delete`, `collect` and `tests/piece_mem_test.c` `overflow_delete`). The corrected node claim does not erase this cost.

**Split/join alternative.** Two boundary splits can isolate a removed run. A height-aware join can stitch compatible trees with `O(h)` spine work, retaining untouched interior nodes; a paste can build `ceil(n/24)` packed leaves and join the resulting tree at the gap. This eliminates repeated mutation descents and the eight-span copy cliff for already-private text. It still requires reading/writing new paste bytes, computing summaries, handling unequal heights, root collapse and sparse fringes, maintaining per-view ADD and original-source ownership, and safe failure/abort before journal acceptance. Restoring or duplicating arbitrary ORIGINAL subtrees would also require proving source-order semantics for checkpoint diff consumers. An undo record would now hold the detached root plus the backing/view needed to interpret it. Shared nodes count once in `O`, detached exclusive subtrees and their storage remain charged until history eviction/redo-branch discard or final reader release. Record-count caps no longer bound this retained node storage. Ordinary history would cease to retain zero roots; a hybrid that keeps key edits as span records requires two inverse representations and both lifetime paths. A raw detached mapped subtree **fails** the truncate-then-undo example. Making that subtree independent still costs original-byte materialization or obtaining a demonstrably immutable private backing. An external variable-length span vector also preserves ADD bytes without a whole-range copy. It needs allocation and lifetime accounting proportional to the number of discontiguous spans, plus rollback, trim and redo ownership for this second record store. A one-byte-per-span delete can demand a descriptor per byte. The fixed inline record and sequential copy instead bound inverse metadata and make its byte cost visible in ADD admission. Revisit this choice against measured fragmented-delete costs.

Both strategies journal forward deletion as a byte offset and length and restoration as insertion bytes (or an explicitly durable source defined by the wire protocol). No process pointer or volatile subtree ID can be a replay record. Even a constant-spine undo must stream the inserted bytes for the existing journal before acknowledgment (`src/journal/journal.c` `journal_delete`, `journal_insert_step`, `journal_apply_piece`; `src/editor/input.c` `editor_journal_staged`). Do not credit a tree join with constant end-to-end save/recovery cost. For this wave, cut split/join, subtree-valued undo records, their retained-root budget and join-specific balancing/rollback tests. Keep the single-key cursor/coalescing path, packed open builder, the corrected contiguous batch path, explicit copy funding and grouped journal fencing. Test exact deleted bytes after external truncation, above-cap ADD-only fallback, rollback with inside snapshots, and journal replay across group boundaries. **Keep the >32 MiB delete+undo exit case**: `lineidx` degradation and off-path regrowth measure changed byte geometry independently of inverse representation. The 513-aligned-chunk example crosses its 512-chunk incremental limit (P, PLAN §4.3). No PLAN amendment is needed for this choice.

**Private ADD boundary.** `piece_checkpoint_begin` retains a restore view at the ADD mark. On the first uncached inside take for which the mark is unaligned, the root's `add_high` exceeds the mark, and the restore boundary is still shared, `checkpoint_snapshot_storage` installs a private writable copy in the restore view *before* publishing the snapshot. It copies the prefix bytes and newline prefixes and restores the prefix newline total. Prepay **one complete `sizeof(add_chunk)` per open checkpoint that may publish such a view** (P, `boundary_private` makes this once per checkpoint). On the pinned ABI this is `65,800 B = 65,536 + (65,536/512) × 2 + 4 + 4` (P, data, `uint16_t nl_prefix[]`, `nl_total`, refcount). Bill the actual aligned allocator stride. An aligned mark, unobserved extension or cached take requires no new private chunk. The ordinary pre-begin take itself does not trigger the copy.

On abort the UI restores the logical mark, swaps the directory and repairs the restored tail's newline state. A surviving inside snapshot continues reading its original bytes, including the transaction tail, while new edits can append at the restored mark. On commit the unused restore view is dropped. If the last observer is gone at abort, the ordinary boundary can be reused. Older detached chunks and directories remain charged until physically freed, across any number of subsequent checkpoints. Prepay the checkpoint descriptor, restore-view metadata and any private directory path needed for the boundary exchange as well. For the v2 shared directory require a prepaid, bounded path for that exchange and a constant-time retain at begin. V1 `add_store_prefix` allocates a pointer table and retains every prefix chunk at begin; plain take retains the existing `add_store`.

## Pool sizing and admission

**One command, one count.** Let `O` be all *physically occupied* common slots in the process, including cache, live headers and queued retirements. For command steps in order, take the maximum of prior possible consumption plus the next step's entry requirement. Do this before journal acceptance. A normal replacement covers a checkpoint begin, deletion, single-segment insertion and publication. At height `h` its conservative scalar claim is

`W(h) = 1 + (4h+3) + (2 min(H,h+1)+3) + 1` (P).

The two unit terms are header takes, the deletion can grow the root once before insertion, and the final take only needs its own header. A snapshot alone need not prepay a deletion. At a leaf root `W(0)=10`; at the former height 16 the claim was 104 slots, and at the new `H=31`, `W(H)=194` slots (P, `1+127+65+1` at the cap). A paste across chunks, compound command or replay uses its actual sequence. An exclusive cursor fast path may prove a smaller claim. Distinguish a conservative successful preflight from an allocation failure for storage genuinely required by the planned path.

**Process provision = `O + outstanding claims + W` common slots** (G, one UI command at a time). The logical slot-payload target is `B_nodes = 400 × (O + outstanding claims + W)` (P, slot stride). Physical provisioning also pays for slack trapped in other cores, metadata and rounding. Use the extent bounds below for mapping bytes. Compute the independent ADD and metadata requirement below. An older revision can keep an entire disjoint tree live. Once counted in `O` it requires no second reservation per command. No service concurrency limit follows from this formula.

### Extent ownership and closing tabs (review 9)

**Keep scalar slots; transfer ownership by whole extent.** Unassigned funded extents belong to one UI-owned process reserve. A core first consumes free slots in its own non-full extents, then draws whole extents from the reserve. Every leaf, branch and header in an attached extent belongs to that core. No service or tab can allocate into another core's partial extent. Empty extents can return immediately to the shared reserve; unmap physical surplus above the foreground target after a bulk command, tab close or final orphan retirement. A large exact paste claim must not become the new idle high-water mark.

The mixed-slot alternative has a real retention bound. With extent size `E`, `k` usable slots per extent and `S` live/physically retiring survivor slots, an adversarial allocation order leaves **one survivor in each of `S` extents**. After returning fully empty extents the mapped amount can be `S×E`, with up to `S×(E−400)` bytes outside those live slots (P, plus the separately funded process working reserve). Closing the large tab can return almost none of its former pages. A common free-slot count obscures this. Core-owned extents cost internal slack but eliminate cross-tab stranding: after the closed core's last physical reference retires, **zero of its occupied extents remain attached**. The reserve may retain only currently required whole empty extents. For surviving cores with `sᵢ>0` occupied slots, each has at most `sᵢ` nonempty extents (P, worst case one slot per extent), so charged nonempty extent bytes are at most `E Σsᵢ`. Ordinary densely packed allocation needs only `E Σceil(sᵢ/k)`. The latter is a lower bound, not a promise after arbitrary frees. Charge old snapshots to the dying core until physically read/reclaimed, including worker returns not yet drained. There is no bound solely in *open* tabs before that retirement.

Choose `E = one native VM page` (G, smallest independently returnable extent and smallest empty-tab bill). Reserve space for the base pool descriptor, core owner and intrusive list links on that page; derive `k=floor((E−aligned_descriptor_bytes)/400)` and check alignment and positive capacity. At a 4,096 B page on the pinned 64-bit ABI, `sizeof(edit_pool)=56 B` (P, seven pointer/size fields in `src/base/base.h`), plus three pointer-width fields gives 80 B aligned to 16 and **10 slots/page** (P, floor((4096−80)/400)). Use actual layout and page size on other platforms. Keep full/nonfull extent lists per core and a list of whole free extents at the app. A returned pointer in a single page identifies its extent by its page base. One implementation with `edit_pool_init/get/put/free` puts the descriptor in the reserved tail beyond the slots in its page-rounded mapping; copy the base descriptor to live local storage for `edit_pool_free` before unmapping its page. Count additional metadata explicitly if the implementation chooses external descriptors. Page granularity means more VM reservations on large buffers; no larger extent has earned a larger per-tab retention allowance in this design.

**Empty-tab cost.** Each bare or published empty core now costs **one extent** (4,096 B on the example platform; one occupied root or a root plus one header, P). The other slots on that page can serve only that core. Per-tab *additional working reserve* is still **zero**. The process working supply from scratch for `W(0)=10` uses one such page plus its separate boundary chunk (`65,800 B` raw; a standalone allocation rounded to 17 pages or `69,632 B`, P). On this basis a hundred empty tabs plus that shared supply cost `100×4,096+4,096+69,632=483,328 B` in mappings (P, node/header extent and spare-boundary mappings only). Free slots in the active core reduce the deficit; never count another core's slack as transferable. The previous per-buffer vector and boundary proposal prepaid `52,848+65,800=118,648 B` raw per empty tab (P, former node bill plus private chunk). The shared policy assumes a single UI writer; a yielded checkpoint keeps already assigned claims and a private boundary until safe release. This explicitly supersedes prior 400/800 B **slot-payload** figures as the per-tab physical charge. Root/header payload, tree/core objects, other ADD data and VM rounding have different ledgers.

**What is removed.** No process-wide mixed partial extents, individual-slot lending across cores, cross-core occupancy migration, compaction of live nodes or address-to-core directory. The shared reserve needs serialization only for whole-extent handoff, refill and teardown. UI owns ordinary base operations; worker returns follow the core's existing retirement path. Serialize final orphan handoff with the process allocator's lifetime. Test a closed core returning all its pages while another tab keeps live objects, and an old worker holding the last page across close. Drop tests that require a free slot in one tab's partial extent to satisfy a request in another. No v1 two-slot per-type slabs, marker decoding or leaf/branch/header reservation matrix returns.

### Synchronous admission (review 8)

Admission is a **function** of the current claim and actual storage; no pool FSM is stored. It returns success with a reservation, `PIECE_ERR_NOMEM` for a necessary base allocation that failed, or `PIECE_ERR_RANGE` for an invalid or unsupported request. Snapshot APIs translate their allocation refusal to their existing null result. The enum result is tested at the calling edit boundary; there is no persistent EXHAUSTED or REFILL_PENDING state.

- **Invariant.** After submit on UI, before consuming the next ordinary input, replenish the current buffer's `W(h)` and the spare private boundary or observe an actual base refusal. Repeat on initial admission, active-buffer switch and after an operation changes occupancy. A speculative refill failure rejects no input. At dispatch recompute the claim, use funded local slots and whole reserve extents, and synchronously try base for the remaining deficit. A smaller command that already fits proceeds. If the cheap upper estimate cannot be funded, try the command's actual plan and only its necessary new extents before reporting the memory error. For a deletion, account from its two boundary paths, fully dropped children, actual merge destinations, and shared/exclusive owners. A compound edit can stage each exact step under its unpublished checkpoint and release unused claims between steps. Reserve journal capacity before its acceptance fence. Serialize the ownership sample, physical retirement and reservation on the core; readers may keep using their already captured immutable bytes. An already completed return that reduces the deficit must be visible to the final admission attempt.
- **Amount and source.** For needed slots `w`, funded unclaimed local slots `f`, and `u` whole free reserve extents, acquire `max(0,ceil(max(0,w−f)/k)−u)` new extents (P, `k` slots per extent). Reserve companion chunk, descriptor, undo and journal capacity in the same preflight. Check all byte products and page rounding. Reuse and reclaim physically returned extents before going to base. Use `src/base/base.c` `edit_pool_init/get/put/free` for fixed storage and base arenas for scoped scratch; a chosen local segment limit alone cannot reject the edit. Hold claims before mutation and return all unused storage on partial failure.
- **Guard and latency.** The normal post-submit top-up runs outside the preceding Law 2 interval. A first-seen bulk command or a cold tab can require base at admission **inside the still-active input → submit guard**. Base's Linux VM path uses `os_vm_reserve` and writable pages on first touch; libc malloc/realloc and guard exemptions are unnecessary. Touch the needed new pages synchronously and leave the guard active until true submit. At height 16 the former maximum command paid `104×400=41,600 B` in slot payload. The corrected worst height-31 envelope is `194×400=77,600 B` (P, `W`, plus page rounding and companion storage); typical top-ups buy only the actual deficit. An 8,378-slot bulk claim can touch up to 838 such pages from cold node storage (P, round up by ten slots per example page). A requested range copy also touches its own payload pages. Both costs can delay submit. Moving the same critical-path acquisition to a worker does not complete this command before the storage is ready. A successful speculative worker could overlap preparation with unrelated UI work if it guessed the next demand; the guarantee for an unpredicted command would still need synchronous progress. Measure input → submit including page faults and record input queueing behind post-submit top-up. Async refill would need dispatch, cancellation, revalidation and completion ownership. No correctness counter-example justifies those here.
- **Failure and retry.** A valid command either executes once or returns a visible refusal after actual base failure. Show **“Edit not applied — buffer memory is full.”** A failed preflight leaves bytes, selection, history cursor, save cutoff and journal sequence unchanged. Unpublished checkpoint rollback is allocation-free. After journal RAM acceptance the §4.2 frame fence applies. The next user command tries current capacity afresh. Cut pending input storage for refill, the refill worker/mailbox, pool state transitions and stale error latching. Test failed post-submit warm-up followed by a fitting key, exact synchronous top-up inside the active guard, injected necessary base refusal, and a later successful command; remove park/resume/revalidation tests for a refill task. Physical worker retirement remains a separate lifetime concern.

- **V1 comparison.** `src/piece/piece.c` `pool_reserve_class` calls `pool_grow` synchronously until free slots meet the request, under the pool lock. That happens in `reserve_insert` / `reserve_delete` before mutation and in `piece_snapshot_take` before publishing a fresh header. A cached take skips growth. In `tests/piece_mem_test.c` `deeper_snapshots`, `mem_alloc` counts every hook request; the live-byte baseline is sampled **after** the take and before the insert, so slab prepayment at take is already in the baseline and any further growth during insert still counts. In `tests/piece_test.c` `t_random` the counting hooks are installed from creation. Separately, `tests/piece_mt_test.c` `typing_allocator_test` warms the arena-backed tree, then starts the libc malloc guard around edits and takes. Slab growth via an arena hook can occur inside that interval with zero libc calls. Neither test demonstrates a between-command refill invariant in v1.

**Companion ADD budget** (P). At admission count physically occupied chunk slots across all views, including sealed or retiring ones. Add ordinary *new* chunks required to append the operation's bytes at the current tail, and one additional free private-boundary slot for a transaction that might expose its partial mark (G, recommended to reserve at begin). Multiply the resulting chunk count by `align_up(sizeof(add_chunk), class_alignment)`. An occupied private slot is already in the first term. Reserve the ordinary COPY/ADD payload, ref fallback, directory nodes, view/checkpoint descriptors, undo records and journal staging in their own classes, outside `B_nodes`. In particular, a requested deletion ref with more than `PIECE_REF_SPANS = 8` runs (P, `src/piece/piece.h`) may append **the entire range**, including existing ADD bytes (`piece_delete`, `collect`); use length as its safe append bound. A new chunk reservation for appended data and a private boundary serve different purposes and can both be due. For v2 directory metadata use the actual chosen layout's maximum touched entries/levels and allocator strides; its representation has no frozen byte size at this pin. A companion-storage deficit also goes through refill before a genuine base refusal can reject the transaction.

### Disposition of the round-2 challenges

7. **Height.** The public `build` → `del_rec` fixture refutes the universal eight-split lemma. Keep the height-31 check and atomic range error in both builds. The restricted prepend count is (P). The representation gate is (G). Remove the repacker and its retry suite.
8. **Refill.** Use synchronous UI admission and an enum result for the command. Post-submit top-up covers ordinary input. Exact synchronous base growth covers a cold or bulk command under the live Law 2 guard. Remove the refill worker, pending input, persistent exhaustion states and resume tests.
9. **Extent ownership.** A core owns whole native-page extents. On the example ABI an empty tab costs 4,096 B of node/header mappings and zero additional working-reserve bytes. Remove cross-core lending of individual slots and test physical whole-page return after close and worker release.
10. **Bulk operations.** Adopt the contiguous batch claim and stable ADD-span undo. In the largest comparison 8,378 slots suffice for the batch versus the discarded claim of 5,734,400 at the old height cap (P, counted shapes above). A detached ORIGINAL subtree cannot meet byte-exact undo after truncation. Remove per-segment path prepayment, split/join and subtree-history tests. Retain the explicitly budgeted whole-range ADD fallback and the Wave 1 line-index regrowth gate.

VERDICT: Adopt the 400 B node/header slot with 24-entry leaves and 16-child branches, synchronous command admission from core-owned page extents, and a checked height limit of 31.
