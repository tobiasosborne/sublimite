# P1.9 — bounded hot-exit journal

This bead implements the journal transport and recovery API, not the editor's
startup/save UI. Callers restore buffers using BASE records and
`journal_apply_piece`, and handle VIEW/TABS/WINDOW records. A base conflict
returns `JOURNAL_BASE_CHANGED`; the application must surface the §2.14 choice
and discard the partially constructed recovery session, rather than applying
remaining operations to a different original.

## Wire contract

Format version 1, little endian, no persisted C structs. Each record has:

| Offset | Bytes | Value |
| --- | ---: | --- |
| 0 | 4 | magic `0x314c4e4a` (`JNL1`) |
| 4 | 4 | total length, including 32-byte header |
| 8 | 4 | type: PAD=0, BASE=1, INSERT=2, DELETE=3, VIEW=4, TABS=5, WINDOW=6 |
| 12 | 4 | CRC32C (Castagnoli, reflected polynomial `0x82f63b78`) |
| 16 | 8 | sequence: contiguous starting at 1; PAD uses 0 |
| 24 | 8 | buffer id; PAD/session-wide records use 0 |

CRC covers the entire header (CRC field treated as zero) and payload. It uses
an instance/local table, initialized outside append, with no mutable global
state or architecture requirement. Payload schemas:

- BASE: size, mtime in ns, inode, device (four u64); prefix CRC and prefix
  length (two u32); NUL-terminated path, at most 4096 bytes excluding NUL.
- INSERT: u64 byte offset, followed by exact inserted bytes (invalid UTF-8
  preserved). DELETE: u64 offset and u64 length.
- VIEW: u64 cursor, anchor, first visible byte, horizontal scroll offset.
  Cursor/anchor encode selection including its direction. Scroll units are
  chosen consistently by the caller.
- TABS: u64 count, u64 active **index**, then count u64 buffer ids in order.
  Empty tab set has active index zero. WINDOW: u32 width, u32 height.
- PAD: all-zero payload, checked by CRC, ends exactly on a 4096-byte boundary.
  It is at least a header long, so even a batch ending just before a page
  boundary adds another page when necessary. PAD does not increment sequence.

Records can straddle pages. Maximum wire record is 1 MiB (E: bounded parser
allocation); larger pastes/scratch checkpoints must be split into contiguous
INSERT records. The configured batch is a tighter bound: default INSERT bytes
per record <=256 KiB-72; preserve space for both its offset and PAD header. Parser checks length, schema, magic, sequence, CRC, and PAD
before callback delivery. CRC is accidental-corruption detection, not an
adversarial authentication mechanism. A syntactically valid edit can still be
out of range for a particular base: callbacks must reject it atomically.

Replay visits a valid prefix, stopping before the first short/bad record.
`journal_replay_file` streams through a 1 MiB base arena and truncates plus
fdatasyncs at that record's start. If EOF is exactly a record boundary, the
prefix is valid even without PAD. It does not scan for later magic, skip bad
records, or require an entire torn page to survive. Callback failure and base
conflict leave the file unchanged. `journal_replay_bytes` provides the same
parser without I/O or base checking for fuzzing and explicit recovery tools.

## Base identity and save

Capture opens the file, stats before/after reading the first min(size,4096)
bytes, and also stats the path to detect replacement during capture. Identity
includes path + size/mtime/inode/device + CRC32C of that prefix. Always taking
the small prefix hash catches same-size writes with restored mtime in the
prefix; this is not a full-file cryptographic identity. A change outside the
prefix with deliberately restored metadata is outside this detection model.
The base loader must check identity again around loading/copying; it must not
keep using an externally mutable mapping after a detected change (§2.14).
Missing, replaced, changed, or unreadable bases are conflicts.

Never-saved files use empty path and all-zero identity. Start from an empty
piece tree and replay inserts/deletes; this restores untitled buffers without
requiring a file on disk. BASE is metadata, not a reset operation. Each buffer
must have one BASE before its ops in a checkpoint; session bookkeeping and
id-to-tree mapping belong to the recovery caller. The generic parser does not
allocate an unbounded buffer-id registry.

After the save worker acknowledges atomic file replacement and directory
sync, flush then rotate a **complete session checkpoint**. Saved buffer: use
new BASE identity and omit obsolete ops. Other buffers: preserve their bases
and remaining edits. Never-saved buffers can snapshot complete text against
empty bases; named buffers retain their BASE path and identity.
Always include views, ordered tabs/active index, and window size. A save at
sequence S while later edits occur requires those later edits against the
saved snapshot; discarding all edits would be wrong. For a small named buffer, caller may instead checkpoint a DELETE of the
whole saved base followed by INSERTs of the immutable current snapshot, keeping
the new BASE path/identity. Large buffers should retain post-save deltas to
avoid materializing deleted originals or exceeding the file bound.

Rotation builds a same-directory temporary journal, writes/syncs it, atomically
renames it, and fsyncs the directory. Failures before rename leave the old
journal intact. A failure after rename is reported as IO and recovery remains
suspended until the application resolves it. A crash between successful save
and rotation leaves the old journal with a changed base: surface recovery
choice; do not silently rebase. No backing copy of every original file is
created here. The file module/application owns save snapshots and any retained
original needed for a richer conflict recovery choice.

## Thread ownership, bounds, cadence

`journal_open` preallocates and touches two aligned buffers from `edit_arena`:
default 256 KiB each (E: bounded queue sizing). Appends only check bounds, copy,
encode and CRC; no allocation, syscall, lock, worker submission, or printing.
Creation also fsyncs the parent directory before returning, so its new
pathname is not left outside the durability protocol. All UI fields belong to the UI. Batch bytes plus job context are immutable
snapshots while the worker writes them. Only completion addresses (checked
against the active batch) cross through `work_publish`/mailbox acquire.

Call `journal_pump` from an event-loop timer, outside input->submit. A <=5 ms
tick (E: integration allowance, not a typing-path operation) is recommended
while the journal is dirty; turn it off once durable==accepted. A partial page
is coalesced until the 1 s deadline (or explicit force), rather than writing
4 KiB of padding for each key. Full pages are submitted promptly. The job writes
4096-aligned page batches, slicing at the next 64 KiB unsynced boundary. It
fdatasyncs at 64 KiB or 1 s since its last sync, or on explicit force. The timer
also submits a zero-data sync job when the final short batch needs its time
sync. OS scheduling, I/O, and a busy bulk worker can extend wall-clock cadence;
statistics expose sync interval, byte volume, accepted/written/durable sequence.
A sync in the middle of a record acknowledges only the preceding complete
record. SIGKILL can leave additional complete unsynced records in the page
cache; those also replay as a valid, more recent prefix.

The worker parks after publishing completion, until UI consumption cancels it.
This keeps its work slot busy and prevents `work_submit` from reusing its epoch
and silently dropping an unread completion. After publication it only reads
`work_ctx`, so acquired completion returns ownership of batch/disk state
immediately, without an UI wait for the worker's 1 ms cancellation poll (E).
Mailbox-full publication retries while cancellable; UI must route/drain the
shared pool. Blocking flush/close/rotate are setup/save/exit operations, with
a registered application message handler for unrelated shared-pool messages
(or a private pool). Ordinary async pump/receive preserves the caller's router.

Default disk limit is 64 MiB (E), configurable page-aligned. Reservations
include all pending PAD pages; neither memory nor file grows without bound.
At memory/disk saturation an append returns sticky `JOURNAL_FULL` immediately.
Already accepted records still flush; **subsequent records are refused** until
complete rotation. This prevents applying later byte offsets after a missing
edit. The UI may continue editing, but must surface recovery suspension and
schedule a full checkpoint; it must never block the input path or pretend that
unaccepted edits are protected. Callers journal only successful piece edits.

Under normal scheduling, the intended data-loss window is the 1 s/64 KiB sync
window plus timer/worker delay (E). Under sustained back-pressure it includes
bounded pending buffers plus unsynced disk bytes; record atomicity can discard
a record straddling the last sync boundary. There is no unconditional zero-loss
promise for unacknowledged edits: that would contradict fsync-light hot exit.
Once fdatasync completion is acknowledged, replay includes at least that entire
record prefix. Clean exit must check the return from `journal_flush` before cleanup;
`journal_close` attempts a best-effort flush and then releases resources. Startup should replay, then checkpoint
into a new journal; `journal_open` refuses nonempty files so it cannot overwrite
a crashed session. Single-instance application code owns exclusive use of the
journal pathname and must ensure replay is not run on a live writer.

Rejected alternatives: synchronous append/write/fsync (UI latency); heap-backed
unbounded queue (memory/no-malloc); overwriting a partial last page (tears can
destroy earlier records); skip-and-continue corruption recovery (wrong offsets);
resuming ops after saturation (missing edit makes later ops unsafe); truncating
old ops in place after save (crash destroys recovery); whole-file base hashing
on startup (unbounded latency for multi-gigabyte originals).

## P1.9d — recoverable save, retryable I/O, crash oracle (edit-4w1.32)

This section supersedes the earlier save/rotation order and the parked-worker
paragraph. It leaves the accepted-edit loss window unchanged; the PRD decision
in edit-4w1.34 remains Tobias's decision. Findings outside 2, 3, and 8 remain
edit-4w1.33's scope. Removing the P1.8b worker workaround is folded-in
edit-4w1.31 work, within this bead.

### Save transaction and exact file integration

`journal_save_prepare` receives a **complete session checkpoint of the current
UI state**, one matching previous BASE for the saved buffer, and a zeroed
`journal_save` token. It flushes accepted records, retains the previous named
base inode using a unique hard link beside that base, checks its identity,
fdatasyncs it, and fsyncs that directory. It substitutes the retained pathname
in every matching checkpoint BASE, appends PREPARED metadata, and atomically publishes and
directory-syncs this checkpoint **before allowing file replacement**. Empty
bases need no link. Named paths supplied to this new API must be absolute
(`file_path` supplies that); this does not change general path handling.

The call order is:

1. On the UI owner, build that complete checkpoint. Call
   `journal_save_prepare(j, id, previous, checkpoint, count, &save)` off the
   input path. Require success. Do not mutate the saved tree between this
   checkpoint snapshot and `file_save_begin`.
2. Call `file_save_begin(f, tree, flags, generation)` on the same state. Its
   return acknowledges enqueue, not replacement durability. It takes the piece
   snapshot before returning. UI mutation/journal appends can resume afterward.
3. Route shared-pool messages with `journal_set_message_handler`; wait for
   `FILE_MSG_SAVE_DONE` with `FILE_OK`. On enqueue/save failure (including
   `FILE_ERR_DIRSYNC`) retain the prepared generation and resolve/retry the save.
   Do not follow a failed prepare with file replacement.
4. Capture the new identity with `journal_capture_base(file_path(f), &saved)`.
   Construct a complete checkpoint of the **current** session: this buffer's
   saved BASE plus post-save deltas, every other buffer and its edits, views,
   tabs and window. Preserve other in-flight saves' BASE and SAVE records. Call
   `journal_save_finish(j, &save, &saved, checkpoint, count)` without intervening
   mutation. It flushes accepted records and includes the saved cutoff and new
   identity in the replacement checkpoint, syncs it before rename, publishes
   and directory-syncs the new checkpoint, then unlinks the old generation and
   syncs its directory. Any failure retains the recovery generation unless
   checkpoint publication was already durable and only retirement failed.

No file.h hook is required: retaining the previous generation *before*
`file_save_begin` closes the replacement-to-identity-capture gap. New inode
identity is only available after the file save, but during that entire gap
recovery uses the retained old BASE and all its operations. Once the new
identity/checkpoint is durable, recovery loads the saved BASE and applies only
its remaining deltas. Selection is encoded by BASE itself; recovery requires
no live token or sidecar lookup and never reapplies old DELETEs to a saved base.
The real `file_save_begin` path is covered by the unit test.

SAVE is wire type 7, per buffer, and is metadata:
u64 saved cutoff; u32 phase (1 PREPARED, 2 SAVED); u32 zero; encoded BASE payload.
PREPARED stores the intended target/previous identity; SAVED stores the new
identity. The cutoff is the record count of the snapshot checkpoint **before**
the PREPARED marker; stats sequence numbers are local to a checkpoint generation,
as with existing rotation. The appended marker is not a content edit. When
recovering a PREPARED generation, the application must retain the marker's
intended target path for the buffer's file association; the BASE path is only
its retained content source. A caller which already knows that association may
ignore the marker. To decode its embedded identity, pass a copy of the record
with type BASE, data advanced by 16 bytes, and size reduced by 16 to
journal_decode_base. Tests inspect both phases, the persisted cutoff, and every
identity field. If several buffers shared the exact replaced BASE path and
identity, their content sources are all retained. The PREPARED marker maps
that retained source back to its intended target association for all of them.

Caller-owned tokens allow saves of multiple buffers. Every intermediate
complete checkpoint must preserve the retained BASE paths and SAVE metadata
of other in-flight saves. Finish validates that the supplied checkpoint references the saved
identity and does not reference the generation it is retiring. The caller
already owns and must correctly construct complete checkpoints; the journal
cannot infer semantic snapshot completeness from arbitrary ops. Preparing and
finishing may block/allocate and remain off the typing path.

Atomic editor saves do not modify the linked old inode. External in-place
changes still fall under existing BASE conflict handling. Crash/ambiguous
prepare failures can leave retained links; keep them until recovery has
published a complete checkpoint which no longer references them. Startup
cleanup belongs to the application, which owns buffer recovery. A hard-link
or durability failure stops preparation before authorizing replacement.

Rejected: save then rotate (old BASE disappears); guessing a rebase from the
new file (wrong offsets); keeping only a RAM piece snapshot (lost on crash);
copying every potentially large base on each save (unnecessary with rename
saves). Publishing a complete prepared checkpoint uses the existing bounded
checkpoint machinery rather than introducing a separately recoverable manifest.

### Worker completion, retry and checkpoint failure

The worker returns immediately after successful mailbox publication. P1.8b's
pending-message slot reservation protects its epoch and its immutable completion
address; it no longer polls/sleeps waiting for UI cancellation. Mailbox-full
publication remains cancellable. No journal memory is touched after publication.

Each batch now retains exact byte progress, its sealed bytes, offset and forced
sync state after I/O failure. Completion returns ownership without clearing it.
`journal_retry` (off path, after receipt) clears IO suspension, preserving FULL
suspension, and pump/flush retries this batch **before** the second buffer.
Short successful writes contribute to unsynced volume; failed fdatasync does
not advance durable sequence. A retry at a failed 64 KiB boundary retries the
sync before writing more bytes. Accepted records are never discarded by retry.

Alternatively, after receiving worker IO failure, `journal_rotate` accepts a
complete replacement checkpoint including both buffers' accepted state. A
failed build/rename keeps the old recovery prefix and failed-batch retry state.
A directory-sync failure after rename suspends IO: the new generation reports
`durable_sequence=0` until `journal_retry` successfully repeats the directory
barrier. This prevents new acknowledgements against a nondurable pathname.
Retained base generations are not retired on failed checkpoint publication.
The SAVED marker is built into the replacement checkpoint, so a sticky FULL
append state does not require an extra append before finishing the save; the
existing complete-rotation escape remains usable. FULL/flush semantics are
otherwise unchanged.

The per-journal `journal_io` seam intercepts off-path writes, data/directory
syncs and rename, including temporary checkpoint jobs and creation-directory
sync. NULL hooks use POSIX calls; no global syscall state and no append hook.

### Exact current crash guarantee and test acceptance

Successful append means accepted into bounded RAM, **not** durable. The protected
commit point is successful fdatasync of complete records, followed by completion
receipt publishing `durable_sequence`; checkpoint generations additionally need
their pathname's directory barrier. A sync inside a record protects only the
preceding complete record prefix. On process kill, complete unsynced bytes may
still replay from the live kernel page cache. Simulated power loss discards
those volatile bytes and nondurable namespace changes.

For an append-only generation, let A be the received durable acknowledgement,
I the issued accepted edit count, and K the complete recovered edit count.
Acceptance is exactly **A <= K <= I**, every recovered op equals the seeded
script prefix, and the actual recovered **piece tree bytes equal an independent
byte model after K edits**. K can be zero when A is zero. This is the current
promise, not a claim of recovery of every accepted/UI edit. The independent
oracle has its own edit-choice generation and byte-array loops; it neither
calls the writer's operation helper nor decodes the replay records. Replay
actually invokes `journal_apply_piece` on a real tree.

Under normal scheduling the intended window remains 1 s / 64 KiB plus event
loop and worker delay (E); there is no unconditional wall-clock bound when I/O
or worker scheduling stalls. It can include both bounded pending buffers and
unsynced disk bytes; record straddles drop their incomplete suffix. FULL refuses
later ops, so UI edits which were never accepted have no bounded recovery window.
The existing FULL/flush API behavior and large-paste/untitled limits are unchanged
here and remain edit-4w1.33. Already acknowledged edits stay recoverable across
an editor save using the transaction above, subject to the existing external
base-conflict model.

Deterministic tests maintain **separate volatile POSIX files, synced inode byte
images, and a directory-synced journal-name selection**. Data sync updates only
an inode's durable bytes; directory sync updates only its durable pathname.
They exercise short write then EIO with another accepted batch, sync failure
and sync-only retry, a record crossing 64 KiB with exactly one earlier record
surviving, creation-directory failure, failures before rename and after rename
before directory sync, failed directory-barrier retry, complete-checkpoint
replacement from worker IO suspension, and save/new-checkpoint selection with
two buffers and acknowledged post-save edits. SIGKILL trials are supplementary,
not power-loss evidence. The default kill count remains 50 (G: >=50 in check).
Fuzz scripts also inject short-write/EIO and fdatasync failure before roundtrip
comparison against their byte model and piece tree.

Cadence is now an initialization parameter in journal_options: sync_bytes is
a page multiple at least 4096 bytes, and sync_interval_ns is an interval
in nanoseconds. Zero fields select the existing defaults,
JOURNAL_DEFAULT_SYNC_BYTES = 65536 and JOURNAL_DEFAULT_SYNC_NS = 1000000000
(E: existing policy, pending edit-4w1.34). Ordinary pump coalesces partial pages

wall-clock bound: the default window is still the intended 1 s / 64 KiB plus

P1.9d's save transaction, retry state, directory-barrier acknowledgement and
crash-prefix contract remain in force. The configured sync cadence and its

### Suspension and complete checkpoints

`journal_flush` drains every accepted record even in sticky FULL, then returns
`JOURNAL_FULL`. A worker I/O error takes precedence and returns `JOURNAL_IO`.
Thus a clean-exit success check detects incomplete recovery even when
`accepted_sequence == durable_sequence`. The exit sequence is: flush; on FULL,
construct a complete checkpoint of the CURRENT UI session, including omitted
edits; rotate successfully; require successful flush; close. Close remains a
best-effort cleanup operation, not a substitute for that success check.

Save prepare/finish explicitly accept the drained FULL result because their
caller-supplied complete current checkpoint resolves the suspension. They still
stop on I/O errors, retain the preceding base generation through failure, and
clear FULL only after replacement. The inherited save test now saturates the
new pool rather than depending on the old maximum INSERT length.

Rotation preflights every record's schema, ID, size, batch packing and PAD
reservation before creating a temporary file. The new bound is the exact
checkpoint wire size **plus the originally configured operation-log budget**.
`max_file_bytes` therefore bounds a fresh journal and supplies post-checkpoint
log headroom; rotation can explicitly rebuild a larger content checkpoint.
Appends cannot grow the bound. Subsequent rotations recompute it from their
own checkpoint and the original budget, not from the already expanded limit.
Overflow beyond the signed file-offset range returns FULL. Stats expose the
current `file_limit_bytes`, `checkpoint_bytes`, and fixed queue data capacity.

This admits an untitled snapshot beyond the default log budget without a
separate content store or changing its empty-BASE semantics. The regression
uses 65 MiB + 1 byte of text (E: fixture), restores every byte through a real
piece tree, retains session records, and successfully resumes appending.
Failure before rename preserves the old prefix and limit; failure after rename
retains P1.9d's directory-pending I/O state and zero new-generation durable ack.
Temporary build memory is bounded by another journal pool plus the caller's
checkpoint record array/content snapshot. Old and replacement files can coexist
until publication. A caller with a hard total storage quota must account for
checkpoint content and temporary space, as well as operation-log headroom.

### Paste admission, worker CRC and memory cost

The default batch is 1 MiB + 4 KiB; the two touched buffers total 2 MiB + 8 KiB
= 2,105,344 bytes (E: configured capacity). Relative to the previous two
256 KiB buffers, the increase is 1,581,056 bytes, approximately 1.508 MiB (E).
The arena additionally reserves 16 KiB plus `sizeof(journal)` (E) for alignment,
path, instance table, stats and completions. Checkpoint construction temporarily
owns two such journal arenas. Explicit smaller batches remain supported.

This is **one session-wide journal pool**, additional to G10f's per-file
piece/undo/content accounting. It must be counted in the integrated G10 RAM
measurement; creating one default journal instance per buffer would repeat the
cost and is not the intended session integration. Captured BASE paths use a
caller-owned approximately 4 KiB buffer (E) per live identity. These changes do
not establish a whole-editor G10/G10f verdict or amend those gates. The
coordinator still owns integrated RAM accounting and quiet-box measurements.

`journal_insert` now admits one logical mutation atomically: preflight all
chunk headers, queue capacity, sequence space, offset arithmetic, and reserved
PAD/disk bytes, then copy and encode. FULL accepts no portion of that call.
It splits at the smaller of the wire maximum and configured batch record
maximum. An empty default current batch admits decimal 1 MB and binary 1 MiB
pastes (E: fixtures), including ordinary session metadata, without pump, wait,
allocation, syscall or submission. Already queued data or exhausted disk can
still suspend recovery; the UI must handle FULL. Callers which manually issue
separate INSERT calls own their logical grouping; the split-paste regression
also proves those calls fit the idle default queue.

CRC calculation belongs to the worker. UI append encodes zero CRC placeholders;
the worker completes every record and PAD CRC before any write. It polls
cancellation between page-sized CRC slices. A sealed batch is exclusively
worker-owned; successful mailbox publication transfers ownership back to the
UI. Failed writes retain the checksummed bytes/progress for exact retry, with
no recalculation or overwrite of that failed generation. Parsing and BASE
capture retain their bounded off-path CRC work. Admission is atomic, while
individual wire records still obey the existing acknowledged-prefix crash
contract; a large split mutation can have an unacknowledged suffix.

### Stable names and BASE conflicts

Capture resolves a named base with `realpath` into `base->captured_path`, then
checks the opened identity before/after its exact expected prefix read and
against the canonical path. The captured object's `path` points into its owned
storage. A shallow struct copy borrows the original captured object's path;
keep that object alive, or copy the path into separate caller storage. Decoding
continues to use caller-provided path storage. No heap/global path registry is
introduced. Manually constructed BASE/SAVE payloads must contain a canonical
absolute pathname; writer/parser reject relative named paths. Legacy relative
records require an explicit checkpoint in their known original directory;
recovery never guesses a directory or silently rebases.

Journal setup canonicalizes its existing parent, owns the full absolute
pathname and leaf name, and retains the parent directory fd. Creation,
checkpoint temporaries, replacement, cleanup and directory-barrier retry use
that fd (`openat`, `renameat`, `unlinkat`, `fstatat`, fsync). Rotation creates a
short independent `.edit-journal-...` leaf using exclusive/no-follow creation.
Neither the original leaf nor the complete original pathname needs suffix
space. Regressions cover cwd changes, symlink canonicalization, a renamed parent,
a 255-byte basename and a 4,095-byte full pathname (E: fixtures). The optional
rename fault hook still receives absolute paths for the existing fault harness;
the hook is responsible for its own pathname semantics.

Missing, unreadable, short-read, replaced or concurrently changing base contents
are conflicts (`JOURNAL_BASE_CHANGED`); journal-transport read errors remain IO.
Named BASE schemas require the exact expected prefix length. The per-instance
read seam applies only to BASE prefix reads, allowing EIO and premature EOF
injection through capture and file replay. Conflict/callback failure leaves the
journal untruncated. Invalid setup options are validated before file creation;
a regression caught and corrected that ordering during the directory-fd refactor.
