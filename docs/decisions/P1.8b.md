# P1.8b: finished slot reused before drain (edit-4w1.28)

Bug (M, reproduced in tests/work_test.c): submit A, A publishes and finishes, submit B reuses A's slot (epoch bumped), drain drops A's messages as stale.

Fix: per-slot atomic `pending` counter. work_publish increments it before releasing the mailbox tail; work_mailbox_drain decrements it after delivering or dropping each message; work_submit skips slots with busy or pending != 0. A slot's epoch therefore cannot change between publish and drain except through work_cancel, so cancel suppression (G6c) is unchanged. No allocation, API and 64 B message unchanged (work_slot gained 4 bytes, internal).

Rejected: epoch per submission with a separate cancel flag per message (needs a larger message or a per-submission table); slot release at drain only (that is this fix).

Cost: a slot with undrained messages is unavailable (64 slots); the UI drains every frame. A pool left undrained can exhaust slots (submit returns epoch 0).

src/journal's workaround (job spins until work_should_stop to hold its slot) is no longer necessary for message validity; journal may now return from the job after publishing. Not edited here.
