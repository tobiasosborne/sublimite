# P3.1 layout (edit-zzj.1)

`src/layout/layout.{h,c}`: piece tree/snapshot viewport -> `render_grid` cells. No wrap.

## Decisions

- **Glyph identity.** `render_grid_validate` requires `cell.glyph_index == glyphs[slot].glyph_index`, so layout copies it from the table. ASCII: slot = cp - 0x20 (`layout_ascii_glyphs` fills 95 entries, page 0 = baked row; space = `RENDER_NO_SLOT`). Non-ASCII clusters go through `layout_glyph_fn`; no callback, failure or out-of-range slot draws `?`. Invalid bytes and controls draw `?` with `RENDER_ATTR_INVERSE`, width 1 (PRD 6.2).
- **Zero-width clusters** that stand alone (lone mark, ZWJ) are dropped; marks attached to a base are part of the base cluster and reach the callback with it (the rasteriser composes them, render.h "marks merge before submit").
- **Wide clusters** take WIDE_LEFT + WIDE_RIGHT (same colours/attrs); at the right edge (one cell left) or cut by the horizontal offset they become blank cells. Never an orphan half.
- **Rows without scanning.** `row_byte[]` (start byte per row, `LAYOUT_VOID_ROW` past EOF) and `row_used[]` (written extent) are caller storage. `row_used` makes a relayout write only the text plus clear stale cells to the old extent, instead of filling 360 cells per row: a full 2.1 MB cell fill alone would cost ~200 us (E), over the 150 us gate. `layout_init` blanks the grid once; changing the gutter width sets every `row_used` to cols so all stale cells are cleared.
- **Byte window.** Text is read with `piece_read` into a 16 KiB window inside `layout`; the window survives across rows (next line start is usually inside it), refills when < 128 bytes remain, so a cluster is cut at 128 B at worst (bounded work, a base with 1M marks is not a stall). The iterator was rejected: clusters straddle chunk boundaries.
- **Slices.** `layout_run` stops between characters after `slice_clusters` units (default config 500 from the caller; 0 = unlimited). One unit per cell-producing character, one per 256 skipped bytes; skipping the tail of a long line is resumable (memchr over the window). State lives in `layout`; a sliced run equals a one-shot run (tested).
- **Dirty rows.** `layout_edit(off, old_len, new_len, old_nl, new_nl)` after the mutation: no newline in either side -> that row only (rows below get their start byte shifted); otherwise that row to the bottom; edit wholly before the viewport -> shift bytes, redraw only if lines changed (full); edit crossing/ending at the viewport start returns `LAYOUT_RESET` (caller re-runs `layout_begin`); gutter digit change or busy layout -> full restart. Scroll = `layout_begin` (full). Line count is tracked by layout (`viewport.line_count`, 0 = ask the buffer) because the stub kernel's `piece_line_count` is a ~1 ms scan (M) [AC]; the editor's line index should pass it.
- **Line numbers**: `viewport.first_line` or exact `piece_byte_to_line`; hook for the P1.6 estimate path = the caller passing first_line.
- **Long lines**: horizontal offset above `LAYOUT_MAX_HSCROLL` (65536 columns) is clamped and `layout_approximate()` is true. Not done (follow-up): the 4 KiB column checkpoints for lines > 64 KiB, so a deep hscroll on a huge line still scans cluster by cluster (resumably) up to 64Ki columns.
- **Cursor / selection** colours are resolved in layout from byte offsets (cursor beats selection; cursor on a tab colours its first cell; cursor at end of line draws a blank cursor cell). Moving them needs `layout_relayout_rows`.
